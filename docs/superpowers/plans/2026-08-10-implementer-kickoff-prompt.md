工作流程：

**第一步：摸清现状**

- 看 `git log` 和 `git status`，弄清旧模型提交了什么、还有哪些未提交改动。
- 浏览 `src/`、`tests/`、`config/` 的目录结构，对照计划各阶段的“新增文件”清单。
- 用 `.\.venv\Scripts\python.exe -m pytest -q` 跑全量测试（没有 `.venv` 就按计划 A1 的方法创建并安装）。

**第二步：逐阶段对照**

按 A1 → A7 逐节对照计划里的“实现步骤”“实现内容”和“完成出口”，给每个阶段标注：已完成且正确 / 已完成但有问题 / 部分缺失 / 完全缺失。重点核对：

- `contracts.py` 的模型字段是否与计划 A1 的原文一致；
- A3 的沙箱、风险规则表、三种审批模式和审查智能体是否存在；
- A5 是否有输入区左下角的模式下拉框和输入区下方的审批区；
- A6 的 `schema.sql` 是否含 `projects.approval_mode`；
- CLI 演示和工具卡片、TTS 静音规则是否真的按设计工作。

**第三步：报告**

先输出审查报告，逐阶段列出结论和证据（文件路径、测试输出），把“必须修”和“可以不动”分开。报告之后再动手改。

**第四步：修补**

- 只修报告里确认的问题和缺失，不做任何不必要的重构、改名、整理。
- 能小改的不大改；旧实现能用的部分一律保留。
- 如果发现需要大面积重写的地方，先停下来报告，等指示再动。

硬性规则：

1. 代码注释、提交信息一律用简体中文；终端命令用 PowerShell 语法。
2. Python 解释器一律用项目虚拟环境：`.\.venv\Scripts\python.exe`。
3. 全程使用测试适配器：不调用真实模型 API，不执行真实的文件修改工具，不启动真实 Codex 进程。
4. 修补后跑通相关阶段的验收命令，最后跑全量测试确认没有回归。
5. 每完成一处修补单独 commit，提交信息说明修了什么、为什么。`git add` 时只添加本次涉及的文件，禁止使用 `git add -A` 或 `git add .`。
6. 不修改 `E:\AI\二次元情感陪伴助手` 里的任何文件，那是只读参考仓库。
7. 拿不准的行为以设计文档原文为准；仍然不确定就停下来报告，不要猜测。
