## 1. 路线图结论

原计划中分散在 V0.4.0、V0.5.0、V0.6.0 的最终能力全部前移。V0.4.0 不是中间版本，而是本轮产品路线的最终完整状态。本修订在原角色卡主线之上并入手机远程控制（手机连回 PC 对话与操控）的完整分期。

V0.3.2 之后只安排以下正式功能版本：

1. V0.3.3
2. V0.3.5
3. V0.3.7
4. V0.3.9

V0.3.2、V0.3.4、V0.3.6、V0.3.8 等偶数版本号只保留给调试、修复和临时验证，不作为功能里程碑，也不得在上述五个阶段之间另插偶数功能版本。

各阶段主题：

| 阶段 | 角色卡主线 | 手机远程主线 |
| --- | --- | --- |

## 4. V0.4.0 最终产品状态

V0.4.0 必须达到原路线图预计在 V0.6.0 才达到的最终结果，同时包含用户角色卡能力和手机远程控制。最终状态包括：

- 同一项目内可同时开展多个聊天，不同项目之间也可同时开展工作；各聊天的运行状态、队列、工具事件、审批和错误互不串线。
- 助手可连续经历多段思考、自然语言回复和工具调用，前端按真实事件顺序展示，不把一次任务压成单次思考和单次回复。
- 每个用户可创建、保存、编辑、复制、启用自己的角色卡，并可让自定义角色与现有助手组成配对。
- 可导入酒馆 Character Card v2/v3 JSON 和 PNG 角色卡，可导出酒馆兼容的 v3 JSON 和 PNG 角色卡。
- 角色卡包含头像信息；PNG 导出把头像与角色卡元数据合并为可移植的酒馆角色卡。
- `mufy角色卡参考.md` 中酒馆格式没有覆盖的有效字段和运行能力进入 HSR 扩展，不重复维护已有标准字段。
- 提供单独的角色创作页，帮助普通用户从基础信息逐步完成完整角色卡，也允许熟悉角色卡的用户直接编辑高级字段。
- 语音设置页允许为用户创建或导入的角色上传参考音频，并使用用户自己的 DashScope 账号创建和保存该角色的音色 ID。
- ASR、TTS、声音复刻模型始终锁定，用户不能切换。
- 只有角色自然语言回复可进入 TTS。助手永远不使用 TTS，工具、命令、路径、日志、思考和系统事件继续静音。
- 助手提示词继续只注入一个 Markdown 文件。发生上下文压缩后，必须把该 Markdown 文件重新注入新的有效上下文，不能把角色卡、世界书或角色扩展混入助手提示词。
- 具备长期对话所需的上下文投影、结构化摘要、配对记忆、增量持久化、使用量统计和可诊断的提示词装配结果。
- 手机可以作为远程客户端安全连回 PC：完成配对后可对话、发起委派、查看执行结果、处理审批、使用角色语音并接收任务通知；所有业务状态与执行都留在 PC。
- 真实失败保持失败；供应商请求、工具执行、并发任务、音色创建、导入导出、压缩或远程连接失败时，不合成成功结果。

## 5. 双轨并行开发方式

从 V0.3.3 起，每个正式版本都由“强逻辑 AI”和“强视觉 AI”双轨并行推进。双轨共享数据契约和验收目标，但分开负责文件和决策，减少互相覆盖。

### 5.1 强逻辑 AI 职责

强逻辑 AI 负责：

- Python 业务规则、SQLite 数据结构、迁移和持久化。
- Sidecar JSONL 协议、前端 ViewModel 所需的明确状态和事件。
- 角色卡标准化模型、酒馆兼容映射、导入导出、未知字段保留和头像资产管理。
- 角色提示词、世界书、扩展模块、上下文压缩、长期记忆和助手单 Markdown 注入规则。
- DashScope 请求、固定模型、音色 ID 生命周期和助手禁用 TTS 的底层约束。
- 手机远程的传输与安全：WS 服务器模式、鉴权与配对、事件扇出、PWA 伺服、移动端命令与审批路由、电源状态数据。
- 并发隔离、失败传播、测试、构建和版本验收。

强逻辑 AI 不替强视觉 AI 规定最终画面风格，只提供真实、稳定、足够表达界面状态的数据和事件。

### 5.2 强视觉 AI 职责

强视觉 AI 负责：

- 角色库、角色创作页、角色详情、导入导出流程和语音设置页的整体视觉体验。
- 手机端 PWA 与移动壳的整体视觉体验：移动布局、配对流程、连接状态、远程对话与执行卡片、手机审批与语音交互。
- 页面信息架构、视觉语言、布局、层次、动效、反馈、空状态、加载状态、失败状态和完成状态。
- 基础模式与高级模式的交互组织、渐进式填写、头像选择与预览、角色预览、世界书和高级字段编辑体验。
- 多聊天并行状态、后台运行状态和跨项目切换的清晰呈现。
- 桌面窗口尺寸变化、键盘操作、长内容编辑和高密度信息下的可用性；移动端小屏、单手操作和弱网状态下的可用性。

本文只规定功能、数据边界和必须呈现的状态，不限制强视觉 AI 的审美、构图、动效、材质、色彩或具体控件形态。强视觉 AI 可在不改变业务协议和真实状态的前提下自由完成高端、人性化设计。

### 5.3 每个阶段的协作顺序

1. 强逻辑 AI 先冻结本阶段最小数据契约、状态枚举和事件含义。
2. 强视觉 AI 可基于冻结契约和明确样例数据并行完成界面，不需要等待全部后端逻辑完成。
3. 双方各自在约定文件范围内工作；涉及共享类型时先更新契约，再分别同步。
4. 集成时必须接入真实 Sidecar 状态。模拟数据只能帮助视觉开发，不能作为阶段验收通过的证据。
5. 阶段结束时共同完成一条真实主路径验收，确认界面没有把失败、等待、取消或后台运行伪装成完成。

## 6. 角色卡兼容与内部数据契约

角色卡契约已在双AI并行任务中产出（`docs/character-card/角色卡数据契约.md`、`酒馆字段与HSR扩展字段映射表.md`），V0.3.3 起按该契约落地到数据库、Sidecar 和前端，后续阶段只补齐实现，不频繁改名或另造互不兼容的格式。

### 6.1 酒馆标准字段

下列内容优先使用 Character Card v3 标准位置保存：

- `name`
- `description`
- `personality`
- `scenario`
- `first_mes`
- `mes_example`
- `creator_notes`
- `system_prompt`
- `post_history_instructions`
- `tags`
- `creator`
- `character_version`
- `alternate_greetings`
- `group_only_greetings`
- `character_book`
- `data.extensions`

导入 v2 卡时统一规范化为内部模型；导出默认生成 v3。读取样例卡时必须同时处理根级兼容字段和 `data` 中的正式字段。

### 6.2 HSR 扩展字段

`mufy角色卡参考.md` 中未被酒馆标准直接覆盖的内容统一进入 `data.extensions.hsr`，字段清单以 `角色卡数据契约.md` 为准，至少包括：

- `schema_version`
- `world_architecture`：世界基础、时代与技术、地理、关键地点、社会制度、文化与价值观。
- `character_architecture`：身份、外貌与感官印象、语言系统、行为状态、心理核心、关系结构、生活方式和经历。
- `relationship_system`：关系阶段、阶段门槛、退行条件、关键节点和与用户的关系设定。
- `event_system`：开场场景、绝对/相对时间线、条件事件和随机事件池。
- `narrative_rules`：叙事视角、节奏、对话规则、明确禁区和剧情钩子。
- `command_panels`：声明式面板和展示数据；不得把导入卡中的任意脚本当作应用代码执行。
- `avatar_asset`：内部头像资产引用、来源和导出信息。
- `voice_profile`：角色与音色 ID 的绑定、参考音频资产引用和创建状态；不保存明文 API Key。

酒馆已有字段不在 `extensions.hsr` 中重复保存。编辑器可把分散的引导式输入组装到标准字段，但最终保存只能有一个权威位置。

### 6.3 运行规则

- 世界书关键字、常驻条目、插入顺序、位置、深度提示和启用状态按角色卡声明运行。
- 世界书关键字匹配只用于角色卡内容激活，不用于判断用户是否要求委派、工具调用或任务是否成功。
- 关系阶段、行为状态和叙事规则由角色模型根据角色卡执行；代码不通过自建关键词表猜测角色情绪或用户意图。
- 明确的轮次、时间和启用条件可由运行时执行；无法确定的语义条件交给模型，不伪造确定性状态。
- 角色卡只能影响角色对话、角色记忆和角色 TTS，不能赋予角色工具执行权限，也不能覆盖助手职责。

### 6.4 头像与文件可移植性

- 用户上传头像后，应用把头像复制到受管理的角色资产目录，不长期依赖原始文件路径。
- 导入 PNG 角色卡时，PNG 本身作为头像，同时读取其中的 Character Card 元数据。
- 导入 JSON 时读取并保留 `avatar` 信息；若用户另选头像，则内部卡绑定受管理头像副本。
- 导出 PNG 时把 v3 元数据写入头像 PNG，形成酒馆可导入的单文件角色卡。
- 导出 JSON 时保持标准 JSON 兼容；界面同时允许用户另存头像。不能用 HSR 私有包替代酒馆 JSON/PNG 导出。
- 导入后重新导出时，未被应用识别但合法的 `extensions` 字段应原样保留，避免编辑一次就丢失第三方扩展。

### 6.5 导入与导出结果

导入和导出必须给出真实结果：

- 成功时显示角色名称、格式版本、头像、世界书条目数、问候语数量和已识别扩展。
- 存在不支持字段时明确列出被保留但未运行的字段。
- 文件损坏、元数据缺失、格式不支持或写入失败时直接失败，并保留可读错误与底层日志。
- 不用空角色卡、默认头像或合成成功提示掩盖导入失败。

## 7. 手机远程控制架构与分期总则

### 7.1 架构原则

1. 手机是远程客户端，PC 是唯一大脑。业务状态、模型调用、Codex/Reasonix 执行、项目文件和 SQLite 数据全部留在 PC Sidecar；手机端不复制业务权威状态，不提供离线后台执行。
2. 传输复用现有 JSONL 协议。手机连接（WebSocket）上的请求与事件使用和桌面 stdin/stdout 相同的消息结构，进入同一个 `SidecarRouter` 分发与 `service.handle_command` 执行路径；不为手机另建第二套业务协议。
3. 事件扇出不改业务语义。服务器模式下同一事件同时写桌面 stdout 与所有已鉴权远程连接；`JsonlWriter` 仍是唯一的 stdout 写入器，stdout 断开仍触发有序退出；单个远程连接的故障不得影响桌面链路。
4. 鉴权先于能力。任何能触发命令执行的网络入口必须先完成配对与 token 鉴权；未鉴权连接只能调用配对命令，其余一律拒绝并记录。应用不得在任何无鉴权端口上暴露命令执行。
5. 用户自带网络。远程访问仅限局域网与用户自组网（推荐 Tailscale）；发布方不提供中继、信令、语音或推送服务器，与语音 BYOK 边界一致。
6. 审批跟人走。审批请求事件推送到所有在线客户端，任一客户端可应答；应答走同一命令协议并保持任务归属。电脑端无人时，手机是有效审批通道。
7. 手机端不弱化既有边界。助手消息、工具事件、思考和系统事件在手机端同样静音（无 TTS）并结构化展示；来源标记保留。
8. 真实失败保持失败。连接断开、超时、鉴权失败、电脑休眠在手机端如实呈现；重连后通过事件序号对齐增量，不合成离线期间未收到的事件。

### 7.2 分期总表

| 分期 | 融入阶段 | 范围 |
| --- | --- | --- |
| P0 | V0.3.3 | WS 传输与事件扇出、配对与 token 鉴权、PWA 伺服、手机对话/委派/执行查看（局域网与 Tailscale，无语音） |
| P1 | V0.3.5 | 手机语音（HTTPS 前置）、手机端审批应答、多设备管理与撤销 |
| P2 | V0.3.7 | Tauri 2 Android 壳与本地通知、电源计划检测与提示 |
| 最终验收 | V0.3.9 | 真机/网络/并发/语音/电源全矩阵真实验收 |
| 发布 | V0.4.0 | 手机远程随版本正式发布：文档、分发与发布门槛 |

### 7.3 安全与边界

- 配对码短期有效、一次性使用；token 保存在 PC 本地账号数据，可在桌面端查看在线设备并撤销。
- 远程连接日志记录连接、鉴权失败与命令来源，但不记录消息正文与密钥。
- PWA 与移动壳只伺服静态资源和既有命令协议，不在手机端保存明文 API Key。
- 电脑休眠、关机或 Sidecar 退出导致的断连是预期行为，界面如实提示，不伪造“后台仍在运行”。

## 11. 最终完成定义

V0.4.0 完成时，HSR Partner Harness 应当是一款可由普通用户直接使用的多项目、多聊天、角色—助手协作桌面应用：用户能创建或导入带头像的角色卡，编辑深度设定，为角色配置由自己账号生成的声音，与现有助手组成配对，并在多个聊天中同时工作；角色保持自己的提示词、世界书、记忆和 TTS，助手保持单 Markdown 身份、工具职责和永久静音；酒馆 JSON/PNG 卡可双向交换，长对话可压缩并继续。用户还能把手机变成远程搭档终端：配对后用手机对话、委派任务、查看执行、处理审批、听角色语音并接收完成通知，而全部执行与数据都安全地留在自己的 PC 上。所有真实失败都如实显示。

达到这一状态即视为本路线的最终结果，不再把同一目标延期到 V0.5.0 或 V0.6.0。
