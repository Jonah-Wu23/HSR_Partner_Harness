## 结论

架构层面是对的，我不会改。问题全在策略层——**「最近 12 条」这个窗口规则**，它同时踩了三个坑：记忆断崖、成本不可预测、把 prefix cache 命中率打到接近零。这三个都能在不动架构的前提下修掉。

先说为什么架构对：无服务端会话、DB 是唯一权威、每轮重新组装，这是三件正确的事。它带来的好处不只是"能恢复"——它让每一轮请求都是纯函数（历史 + 角色卡 → prompt），意味着可回放、可快照测试、可随时换服务商、可以在出问题时精确重现当时发的是什么。有服务端会话的方案（Assistants API 那种）反而会让你失去这个。你选对了。

下面是我认为有问题的地方，按严重度排。

---

## 一、可能是 bug：窗口只按 `source` 过滤，没看 `target`

你的架构文档里消息归属是按 `user+target=character` 和 `user+target=assistant` 区分的，但 `recent_roleplay_context()` 的筛选条件写的是 `source=user` 和 `source=character`。如果确实没带 `target`，那么**用户直接发给编程助手的指令会混进角色的对话历史**。

症状会是这样：用户在工作台敲了一句"把 login.py 里的重复逻辑抽出来"，这条以 `user` 身份进了角色上下文，但助手的回复（`source=assistant`）被过滤掉了。角色看到的是一条没有任何回应的悬空 user 轮次，模型很自然会去接这句话——于是角色开始对一句根本不是说给它听的指令做出反应，或者误以为上一轮自己失职了没回。窗口只有 12 条的时候，几条这样的污染占比很高。

这个请优先确认。修法就是加一个 `target == character` 的条件。

---

## 二、固定条数是错误的计量单位

12 条消息可能是 300 token，也可能是 15000 token——角色扮演的消息长度方差比编程对话大得多。用条数计量的直接后果是：成本和首字延迟随机波动，你既没法预算也没法优化；而且在短消息场景下你白白浪费了大量本可以用的上下文预算。

应该改成 **token 预算为主、轮次上下限为辅**：给一个预算（比如 6k token），在预算内尽可能多装，同时设下限（至少保留 6 轮完整往返，哪怕超预算）和上限（不超过 40 轮，防止短消息场景把窗口拉得过长导致注意力稀释）。

另外两个细节：窗口边界要**对齐到完整的一问一答**，不要出现窗口从一条角色台词开始、而它对应的用户输入被切掉的情况；以及要保证映射出来的 messages 不出现连续同角色（用户在角色生成期间连发、或队列派发都可能造成），必要时合并相邻同角色消息。

---

## 三、最大的一笔性能账：prefix cache 你现在基本没吃到

这是我认为收益最高、改动最小的一处。

DeepSeek 和 OpenAI 都是自动 prefix 缓存，按**最长公共前缀**匹配，命中部分的 input token 只收一折左右，而且首字延迟明显下降。你每轮全量重发的做法，本来是吃这个红利的最佳姿势。但现在有两个东西把它废掉了：

**第一，滑动窗口每轮都在滑。** 第 N 轮发 `system + m1..m12`，第 N+1 轮发 `system + m2..m13`。公共前缀在 system 结束的那一刻就断了，消息体一个 token 都缓存不到。

改法是**阶梯式窗口**：窗口起点固定不动，一直往后追加，直到超出预算才一次性向前跳一整块（比如砍掉最老的 6 轮），然后又固定住。这样连续若干轮里，前缀是逐字节相同的，每轮只有最新那条用户消息是未缓存的，缓存断裂大概每 6 轮才发生一次。顺带还有个行为上的好处：角色"记得什么"不再每轮都在悄悄变化，人格稳定性会更好。

**第二，时间时区被注入进了 system。** 你的文档里写了运行上下文包含"模式、项目名、时间时区"。如果时间精确到分秒，那 system 块本身每轮都在变，公共前缀直接归零——**连角色卡都缓存不到**。

改法是把 system 严格切成两部分：稳定前缀（角色卡 + 搭档身份 + 输出格式约定）放最前面，绝不含任何每轮会变的字段；易变的运行上下文（时间、模式、项目名、任务进度摘要、`CharacterResultSummary`）全部挪到窗口之后、紧贴当前用户消息之前。时间本身也建议降精度到"日期 + 时段"这种粒度，既够角色用，又几乎不变。

再加一条：角色卡每轮从文件重读，逻辑上没问题（热更新很好用），但要在内存里按 mtime 缓存解析结果。否则除了 IO，还有个隐患是用户正好在流式生成中途保存了角色卡文件，同一轮的前后两次读取不一致。

这三项做完，我的预期是稳态下 input 侧的有效计费 token 降到现在的三到四成，首 token 延迟同步改善。

---

## 四、记忆断崖：第 13 条之前的内容凭空消失

这是质量上最伤的一点，而且它是**静默失败**——角色不会说"我不记得了"，它会自信地编一个。用户在第 3 条里说了自己的名字、在第 8 条里角色许了个承诺，到第 20 条全没了。对编程助手来说这只是效率损失，对角色扮演来说这是产品可信度的塌方。

注意你现在的取舍其实是"成本有界、记忆有损"，成本这边没有问题（固定窗口天然封顶）。所以优化方向很明确：**用可控的成本把记忆买回来**。

做法是滚动摘要。窗口每次阶梯式前进、要丢弃一块消息时，触发一次异步摘要（用便宜模型，放在关键路径外，失败就下轮重试），把被丢弃的内容合并进一份持续演进的"故事梗概"，存在 conversation 上，作为一个块注入在稳定前缀和窗口之间。

角色扮演的摘要**不能用通用的对话摘要 prompt**，那种会把叙事压成"用户询问了 X，角色回答了 Y"的流水账，情感和关系全丢。要用结构化槽位，我会这样切：

- 已确立的事实（用户是谁、叫什么、职业、偏好）
- 角色当前的情绪与状态
- 关系变化的关键节点
- 未兑现的承诺 / 悬而未决的话题
- 世界设定的增补

注意摘要块的位置：它在窗口之前，而它只在窗口跳步时才更新——这跟阶梯式窗口的更新节奏正好对齐，不会额外破坏缓存。

---

## 五、委派干过的事，在角色记忆里是个洞

`CharacterResultSummary` 是临时注入的，不进历史。所以角色能在当下汇报"重构完成了"，但三轮之后它完全不知道你们一起干过这件事。对一个主打"角色 × 编程"的产品，这个洞挺致命的——协作的积累感是这个产品最独特的部分。

建议在回执落地时，额外写一条**极简的、角色可见的工作笔记**进历史（一两句自然语言，"我们把 login.py 的重复逻辑抽成了 auth_utils，测试通过"），它参与窗口筛选，也参与摘要。工具过程仍然不进，这个隔离是对的，只是结论要留痕。

---

## 六、跨聊天没有角色记忆

同一项目下多个聊天互不共享，这在编程语境下是对的（任务隔离），但在角色语境下反直觉——用户会认为这是同一个"人"。

我建议加一层 **按 (账号, pair) 的角色记忆本**：一个有上限的、结构化的事实列表（比如最多 50 条），在聊天结束或每 K 轮由模型提炼候选、去重合并，注入时作为稳定前缀的一部分（放在角色卡之后，它变化很慢，不影响缓存）。

关键设计要求是**用户可见、可编辑、可删除**。角色扮演产品里记忆出错的代价很高，而模型提炼一定会出错，必须给用户改的入口。这一条比技术实现重要。

至于向量检索——我建议**先不做，也许永远不做**。对叙事文本做语义召回，捞回来的是脱离时间顺序的碎片，塞进上下文会让角色的时间感错乱（把三周前的情绪当成现在的），沉浸感的破坏往往大于记住细节的收益。结构化记忆本 + 滚动摘要能覆盖 90% 的实际需求，先把这两个做扎实。

---

## 七、两个小问题

**重启选中的聊天不对。** 按 `updated_at` 最新选，而切换聊天不更新它，导致"最后打开的"和"最近有消息的"错位。别去改 `updated_at` 的语义（它按活跃度排序是对的），加一个 `last_opened_at` 或者在 `app_state` 里存 `last_active_conversation_id`。十分钟的事。

**`_history` 和 DB 的双源。** 编排器内存里维护一份、DB 里一份，两个写入点。写库失败、消息删改、多入口写入都会让它们分叉，而这类 bug 极难复现。SQLite 查最近 12 条（带索引）是微秒级的，我倾向于**直接查库、去掉内存副本**；如果为了性能要保留，至少补一个不变量测试，断言两者在每轮结束时一致。

## 优化顺序

**第一批（一两天，零风险）**：确认并修 `target` 过滤；窗口对齐完整往返 + 同角色合并；`last_opened_at`；角色卡按 mtime 缓存。

**第二批（约一周，收益最大）**：token 预算窗口；阶梯式前进；把时间/模式/项目名/结果摘要全部移出稳定前缀。这批做完先测数据再往下走。

**第三批（两三周）**：结构化滚动摘要；委派结论落成角色可见笔记。

**第四批（可选）**：跨聊天角色记忆本（带用户编辑入口）。

## 先把度量补上

上面几乎所有判断都需要数据验证，而你现在应该是没有这些数字的。在动第二批之前，先在 dialogue adapter 里记录每轮的：input token、其中 cached token（DeepSeek 和 OpenAI 的响应里都有这个字段）、output token、首 token 延迟、窗口实际条数。

另外强烈建议加一个开发者视图：**「本轮实际发送的完整 prompt」**。你的无状态设计让这件事几乎零成本，而它在调角色行为时的价值大到离谱——角色跑偏时你能一眼看出是提示词问题、窗口污染还是摘要失真，而不是靠猜。配一个 golden prompt 快照测试，以后任何改动对 prompt 的影响都会出现在 diff 里。
