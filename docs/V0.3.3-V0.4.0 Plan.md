> 文档状态：V0.3.2 冻结后路线图
> 当前产品基线：V0.3.1
> 当前并行开发版本：V0.3.2（已冻结，正在由另一个 AI 实施）
> 最终目标版本：V0.4.0
> 本文只规定 V0.3.2 完成后的开发顺序，不修改、不补写、不重新解释 V0.3.2 的冻结范围。

V0.3.2 之后只安排以下正式功能版本：

V0.3.2、V0.3.4、V0.3.6、V0.3.8 等偶数版本号只保留给调试、修复和临时验证，不作为本文中的功能里程碑，也不得在上述五个阶段之间另插偶数功能版本。

## 3. V0.3.1 基线与 V0.3.2 边界

### 3.1 V0.3.1 已有基础

V0.3.1 已经具备 Tauri 2 + React 桌面端、Python Sidecar、SQLite 持久化、角色与助手分工、DeepSeek 与 Codex 接入、结构化工具事件、项目与聊天等基础能力。后续版本在现有架构上收敛，不重新选择技术栈，不把 Python 业务权威迁移到前端或 Rust。

### 3.2 V0.3.2 视为冻结前置条件

V0.3.2 正在开发。本文不要求当前开发者修改 V0.3.2 代码，也不修改冻结计划。V0.3.3 只能在 V0.3.2 完成、验收并形成明确基线后开始。

V0.3.2 交付的多段思考/回复/工具时间线、DeepSeek 工具链修复、多项目多聊天并行、BYOK 语音配置、自带角色参考音频与音色生成等能力，均作为 V0.3.3 的输入。若 V0.3.2 的实际交付与冻结计划存在差异，先记录真实差异并完成 V0.3.2 验收，不能在 V0.3.3 中用兜底代码假装前置能力已经完成。

## 4. V0.4.0 最终产品状态

V0.4.0 必须达到原路线图预计在 V0.6.0 才达到的最终结果，并同时包含本次新增的用户角色卡能力。

最终状态包括：

- 同一项目内可同时开展多个聊天，不同项目之间也可同时开展工作；各聊天的运行状态、队列、工具事件、审批和错误互不串线。
- 助手可连续经历多段思考、自然语言回复和工具调用，前端按真实事件顺序展示，不把一次任务压成单次思考和单次回复。
- 每个用户可创建、保存、编辑、复制、启用自己的角色卡，并可让自定义角色与现有助手组成配对。
- 可导入酒馆 Character Card v2/v3 JSON 和 PNG 角色卡，可导出酒馆兼容的 v3 JSON 和 PNG 角色卡。
- 角色卡包含头像信息；PNG 导出应把头像与角色卡元数据合并为可移植的酒馆角色卡。
- `mufy角色卡参考.md` 中酒馆格式没有覆盖的有效字段和运行能力进入 HSR 扩展，不重复维护已有标准字段。
- 提供单独的角色创作页，帮助普通用户从基础信息逐步完成完整角色卡，也允许熟悉角色卡的用户直接编辑高级字段。
- 语音设置页允许为用户创建或导入的角色上传参考音频，并使用用户自己的 DashScope 账号创建和保存该角色的音色 ID。
- ASR、TTS、声音复刻模型始终锁定，用户不能切换。
- 只有角色自然语言回复可进入 TTS。助手永远不使用 TTS，工具、命令、路径、日志、思考和系统事件继续静音。
- 助手提示词继续只注入一个 Markdown 文件。发生上下文压缩后，必须把该 Markdown 文件重新注入新的有效上下文，不能把角色卡、世界书或角色扩展混入助手提示词。
- 具备长期对话所需的上下文投影、结构化摘要、配对记忆、增量持久化、使用量统计和可诊断的提示词装配结果。
- 真实失败保持失败；供应商请求、工具执行、并发任务、音色创建、导入导出或压缩失败时，不合成成功结果。

## 5. 双轨并行开发方式

从 V0.3.3 起，每个正式版本都由“强逻辑 AI”和“强视觉 AI”双轨并行推进。双轨共享数据契约和验收目标，但分开负责文件和决策，减少互相覆盖。

### 5.1 强逻辑 AI 职责

强逻辑 AI 负责：

- Python 业务规则、SQLite 数据结构、迁移和持久化。
- Sidecar JSONL 协议、前端 ViewModel 所需的明确状态和事件。
- 角色卡标准化模型、酒馆兼容映射、导入导出、未知字段保留和头像资产管理。
- 角色提示词、世界书、扩展模块、上下文压缩、长期记忆和助手单 Markdown 注入规则。
- DashScope 请求、固定模型、音色 ID 生命周期和助手禁用 TTS 的底层约束。
- 并发隔离、失败传播、测试、构建和版本验收。

强逻辑 AI 不替强视觉 AI 规定最终画面风格，只提供真实、稳定、足够表达界面状态的数据和事件。

### 5.2 强视觉 AI 职责

强视觉 AI 负责：

- 角色库、角色创作页、角色详情、导入导出流程和语音设置页的整体视觉体验。
- 页面信息架构、视觉语言、布局、层次、动效、反馈、空状态、加载状态、失败状态和完成状态。
- 基础模式与高级模式的交互组织、渐进式填写、头像选择与预览、角色预览、世界书和高级字段编辑体验。
- 多聊天并行状态、后台运行状态和跨项目切换的清晰呈现。
- 桌面窗口尺寸变化、键盘操作、长内容编辑和高密度信息下的可用性。

本文只规定功能、数据边界和必须呈现的状态，不限制强视觉 AI 的审美、构图、动效、材质、色彩或具体控件形态。强视觉 AI 可在不改变业务协议和真实状态的前提下自由完成高端、人性化设计。

### 5.3 每个阶段的协作顺序

1. 强逻辑 AI 先冻结本阶段最小数据契约、状态枚举和事件含义。
2. 强视觉 AI 可基于冻结契约和明确样例数据并行完成界面，不需要等待全部后端逻辑完成。
3. 双方各自在约定文件范围内工作；涉及共享类型时先更新契约，再分别同步。
4. 集成时必须接入真实 Sidecar 状态。模拟数据只能帮助视觉开发，不能作为阶段验收通过的证据。
5. 阶段结束时共同完成一条真实主路径验收，确认界面没有把失败、等待、取消或后台运行伪装成完成。

## 6. 角色卡兼容与内部数据契约

角色卡契约应在 V0.3.3 冻结，后续阶段只补齐实现，不频繁改名或另造互不兼容的格式。

### 6.1 酒馆标准字段

下列内容优先使用 Character Card v3 标准位置保存：

- `name`
- `description`
- `personality`
- `scenario`
- `first_mes`
- `mes_example`
- `creator_notes`
- `system_prompt`
- `post_history_instructions`
- `tags`
- `creator`
- `character_version`
- `alternate_greetings`
- `group_only_greetings`
- `character_book`
- `data.extensions`

导入 v2 卡时统一规范化为内部模型；导出默认生成 v3。读取样例卡时必须同时处理根级兼容字段和 `data` 中的正式字段。

### 6.2 HSR 扩展字段

`mufy角色卡参考.md` 中未被酒馆标准直接覆盖的内容统一进入 `data.extensions.hsr`。至少包括：

- `schema_version`
- `world_architecture`：世界基础、时代与技术、地理、关键地点、社会制度、文化与价值观。
- `character_architecture`：身份、外貌与感官印象、语言系统、行为状态、心理核心、关系结构、生活方式和经历。
- `relationship_system`：关系阶段、阶段门槛、退行条件、关键节点和与用户的关系设定。
- `event_system`：开场场景、绝对/相对时间线、条件事件和随机事件池。
- `narrative_rules`：叙事视角、节奏、对话规则、明确禁区和剧情钩子。
- `command_panels`：声明式面板和展示数据；不得把导入卡中的任意脚本当作应用代码执行。
- `avatar_asset`：内部头像资产引用、来源和导出信息。
- `voice_profile`：角色与音色 ID 的绑定、参考音频资产引用和创建状态；不保存明文 API Key。

酒馆已有字段不在 `extensions.hsr` 中重复保存。编辑器可把分散的引导式输入组装到标准字段，但最终保存只能有一个权威位置。

### 6.3 运行规则

- 世界书关键字、常驻条目、插入顺序、位置、深度提示和启用状态按角色卡声明运行。
- 世界书关键字匹配只用于角色卡内容激活，不用于判断用户是否要求委派、工具调用或任务是否成功。
- 关系阶段、行为状态和叙事规则由角色模型根据角色卡执行；代码不通过自建关键词表猜测角色情绪或用户意图。
- 明确的轮次、时间和启用条件可由运行时执行；无法确定的语义条件交给模型，不伪造确定性状态。
- 角色卡只能影响角色对话、角色记忆和角色 TTS，不能赋予角色工具执行权限，也不能覆盖助手职责。

### 6.4 头像与文件可移植性

- 用户上传头像后，应用把头像复制到受管理的角色资产目录，不长期依赖原始文件路径。
- 导入 PNG 角色卡时，PNG 本身作为头像，同时读取其中的 Character Card 元数据。
- 导入 JSON 时读取并保留 `avatar` 信息；若用户另选头像，则内部卡绑定受管理头像副本。
- 导出 PNG 时把 v3 元数据写入头像 PNG，形成酒馆可导入的单文件角色卡。
- 导出 JSON 时保持标准 JSON 兼容；界面同时允许用户另存头像。不能用 HSR 私有包替代酒馆 JSON/PNG 导出。
- 导入后重新导出时，未被应用识别但合法的 `extensions` 字段应原样保留，避免编辑一次就丢失第三方扩展。

### 6.5 导入与导出结果

导入和导出必须给出真实结果：

- 成功时显示角色名称、格式版本、头像、世界书条目数、问候语数量和已识别扩展。
- 存在不支持字段时明确列出被保留但未运行的字段。
- 文件损坏、元数据缺失、格式不支持或写入失败时直接失败，并保留可读错误与底层日志。
- 不用空角色卡、默认头像或合成成功提示掩盖导入失败。

## 7. 分阶段实施计划

## V0.3.3：角色卡底座与语音边界冻结

### 目标

在不重做 V0.3.2 的前提下，建立后续角色创作、酒馆兼容和角色语音共用的稳定底座，并落实“助手永远不使用 TTS”。

### 强逻辑 AI

1. 以 V0.3.2 最终数据库和协议为基线，新增内部 `CharacterCard`、`CharacterAsset`、`CharacterVoiceProfile` 数据模型和迁移。
2. 冻结标准字段、`extensions.hsr`、未知扩展保留、头像资产和音色绑定的序列化契约。
3. 建立角色卡仓库服务：列表、读取、创建草稿、更新、复制、归档/删除确认和选择使用。
4. 保留当前内置角色，统一通过角色卡读取接口暴露；不得在第一阶段重写内置内容。
5. 明确角色卡与配对关系：一个角色卡可以与现有助手组成配对；助手仍由现有单 Markdown 提示词定义。
6. 从底层语音策略中移除助手 TTS：助手自动朗读、手动重播、预览、排队和重试全部不可进入 TTS 请求。
7. 删除或停用助手音色开关和助手音色创建入口。V0.3.2 已生成的助手音色 ID 作为无效旧数据保留或迁移忽略，不自动删除用户账号侧资源。
8. 所有助手消息固定为 `tts_eligible=false`；角色自然语言回复才可能为 `true`。
9. 实现助手提示词装配断言：正常上下文只注入一个助手 Markdown；压缩后在新上下文重新注入同一个 Markdown，且只出现一次。
10. 对固定 `qwen-audio-3.0-tts-flash` 做真实参考音频能力验证：用用户选择的本地文件确认服务是否接受文档规定的上传/URL形式。未经真实验证，不承诺本地文件可以直接完成声音复刻。

### 强视觉 AI

1. 完成角色库和独立角色创作页的整体体验方案与可交互实现框架。
2. 设计角色列表、头像、内置/自建/导入来源、草稿状态、音色状态和当前使用状态的表达。
3. 设计从“快速创建”进入“高级编辑”的渐进体验，避免一开始把全部高级字段堆给用户。
4. 完成助手语音入口移除后的语音设置页调整，只展示角色音色和 ASR 相关状态。
5. 使用契约样例数据覆盖空角色库、载入中、保存失败、格式错误和音色创建失败等状态。

### 集成与验收

- 现有内置角色可继续进入对话。
- 可以创建并持久化一张最小角色草稿，重启应用后仍存在。
- 助手文本和工具功能不受影响，任何助手消息都不会发起 TTS 请求。
- 上下文压缩前后，助手 Markdown 均准确注入一次。
- 固定模型不可由用户修改。
- 参考音频真实能力验证有明确通过或失败记录；失败必须作为 V0.3.5 的阻塞项继续解决，不能用假接口替代。

## V0.3.5：角色创作工作室与自定义角色语音

### 目标

交付普通用户可以真正完成角色创建、保存、预览、使用和配置声音的主路径。

### 强逻辑 AI

1. 完成角色卡创建、编辑、复制、保存草稿、发布到本地角色库和选择使用的业务流程。
2. 基础编辑字段接入酒馆标准字段：名称、头像、标签、简介、性格、场景、首句、示例对话、系统提示、历史后指令和备选问候。
3. 建立角色提示词装配器，将标准字段与已启用扩展按确定顺序装配；输出可诊断的模块列表和来源，不改写角色作者原文。
4. 允许自定义角色与当前可用助手建立配对，并保持角色负责对话、助手负责工具的权限边界。
5. 完成最小 v3 JSON 导入和导出，使用 `E:\Tavern\白厄（3.4前）.json` 作为真实回归样例。
6. 完成头像受管理存储、替换、预览和 JSON 导出配套头像保存。
7. 语音设置加入“为角色创建音色”：选择角色、选择本地参考音频、显示要求、提交创建、记录真实状态、保存音色 ID、试听角色语音。
8. 音色创建必须使用用户自己的 Key、服务地址和账号额度。应用发布方不提供统一付费语音中转服务器。
9. 本地音频到供应商请求的路径以 V0.3.3 实测结果为准。若固定模型要求公网可访问 URL，则本阶段必须提供一个不由发布方承担费用的可行用户侧路径并完成真实联调；否则 V0.3.5 不得宣称“上传本地音频即可创建音色”。
10. 一个角色可绑定一个当前音色 ID，并允许重新创建或解除绑定；旧 ID 不自动在用户供应商账号中删除。

### 强视觉 AI

1. 完成独立、高端、人性化的角色创作页，不受本文对视觉风格的限制。
2. 让用户能通过清晰引导完成最小角色卡，也能随时进入高级区域补充深度设定。
3. 提供头像选择、裁切/预览、角色卡实时预览、首句预览、示例对话编辑和保存状态反馈。
4. 设计导入预览与冲突处理：确认名称、头像、版本、世界书数量和是否作为副本导入。
5. 在语音设置页提供角色选择、参考音频选择、上传/创建进度、真实错误、音色试听和重新创建流程。

## 10. 最终完成定义

V0.4.0 完成时，HSR Partner Harness 应当是一款可由普通用户直接使用的多项目、多聊天、角色—助手协作桌面应用：用户能创建或导入带头像的角色卡，编辑深度设定，为角色配置由自己账号生成的声音，与现有助手组成配对，并在多个聊天中同时工作；角色保持自己的提示词、世界书、记忆和 TTS，助手保持单 Markdown 身份、工具职责和永久静音。酒馆 JSON/PNG 卡可双向交换，长对话可压缩并继续，所有真实失败都如实显示。

达到这一状态即视为本路线的最终结果，不再把同一目标延期到 V0.5.0 或 V0.6.0。
