## 0. 总则

### 0.1 双轨并行方式

沿用路线图第 5 节：本阶段由「强逻辑 AI」与「强视觉 AI」双轨并行推进。强逻辑 AI 先冻结本阶段最小数据契约、状态枚举和事件含义（见第 2 节），强视觉 AI 基于冻结契约和样例数据并行施工，不等待全部后端逻辑完成。双方在约定文件范围内工作；集成时必须接入真实 Sidecar 状态，模拟数据只能帮助视觉开发，不能作为验收证据。

分支与协作形态沿用 V0.3.3 的经验：建议 `v0.3.5-logic-ai` 与 `v0.3.5-visual-ai` 双分支（视觉轨基于逻辑轨契约冻结提交起步），视觉轨内部的多人 worktree 拆分由视觉轨自主决定。阶段收尾时保证视觉分支包含逻辑分支全部提交，一次 PR 合入 main。

### 0.2 不可违背的仓库准则

以下边界在本阶段全程有效，任何轨道不得突破：

- **Let It Fail**：供应商请求、音色创建、导入导出、转写、连接失败必须保持真实失败与原始错误，不合成成功、空结果或伪造回执。诊断和真实验收使用真实配置、真实服务和真实 app-server。
- **Let It Go**：代码只做协议一致性检查与安全边界，不做语义猜测。角色卡内容（包括世界书关键字）只用于角色上下文激活，不得用于判断用户意图、委派需求或任务成败；不得新增任何关键词式的意图判定。
- **BYOK**：音色创建与语音请求只用用户自己配置的 DashScope Key、服务地址和额度；发布方不提供任何付费中转。
- **固定模型**：ASR 永久 `qwen-audio-3.0-asr-flash-streaming`；TTS、声音复刻、声音设计永久 `qwen-audio-3.0-tts-flash`。界面、配置、角色卡、手机端都不得提供修改模型名称的入口；导入卡中的其他模型字段一律归一化到固定模型。
- **助手永久静音**：只有角色自然语言回复可进入 TTS（桌面与手机一致）；助手消息、工具、命令、路径、日志、思考、系统事件全部静音且结构化展示。本阶段新增的手机 TTS 下发链路必须复用 `core/voice_policy.py` 的 `is_tts_eligible` 判定，不得另开第二套判定。
- **助手提示词纯净**：助手侧继续只注入一个 Markdown 文件；压缩后重新注入且只出现一次（`core/context.py` 的 `assert_single_markdown` 守卫不得削弱）。角色卡、世界书、角色扩展不得混入助手提示词。
- **提交纪律**：只提交本阶段相关文件并写明路径，不用 `git add -A`；未经用户明确要求不提交、推送、打 tag 或发布。

### 0.3 视觉自主权声明

本计划对强视觉 AI 只约定三件事：**功能必须达成什么、必须如实呈现哪些真实状态、必须遵守哪些业务协议与安全边界**。

除此之外——审美、视觉语言、信息架构、布局、构图、层次、色彩、材质、字体、图标、动效、过渡、反馈形式、控件形态、交互模式（分步、画布、折叠、浮层、快捷键或任何未列出的形式）——**全部由强视觉 AI 自主决定，本文与逻辑轨均不作任何限制、建议或默认偏好**。`docs/design/web-prototype/` 的原型只是历史参考，不是视觉约束；正式界面无需与原型保持一致。逻辑轨不得以任何形式替视觉轨规定「最终画面应该长什么样」，只提供真实、稳定、足够表达界面状态的数据与事件。

5. **自定义角色与助手配对缺失**：pair 只来自 YAML；自定义卡无法与现有助手组成运行配对。
6. **手机端 P1 缺失**：零语音代码（无采集、无上行、无播放）；审批卡只读（`mobileStore.resolveApproval` 是待启用死代码；`ApprovalCard.tsx` 注释明确禁止应答按钮）；HTTPS secure context 处理不存在。

## 2. 阶段第一步：契约冻结（强逻辑 AI 先行，双轨共享）

逻辑轨开工第一件事不是写业务代码，而是产出一份契约冻结文档 `docs/plans/V0.3.5-契约冻结.md`，作为双轨唯一共享入口。视觉轨在契约冻结提交之前，只能基于现有契约做不依赖新命令的准备工作（视觉体系探索、状态清单、组件盘点）。

### 2.1 需要冻结的命令契约（命名可微调，语义与形状必须定稿）

### 2.2 角色提示词装配契约

- 装配器位置建议 `src/pair_harness/core/character_prompt_assembler.py`，装配顺序以 `docs/character-card/角色卡数据契约.md` §9 为准落地。
- 本阶段装配范围：酒馆标准字段（description、personality、scenario、first_mes、mes_example、system_prompt、post_history_instructions、alternate_greetings）＋导入卡自带的 `extensions.hsr` 只读装配；世界书关键字激活运行与高级扩展编辑归 V0.3.7，装配器架构上留模块位但不实现。
- 装配器必须输出可诊断的模块列表（每个模块的类型、来源字段、字符区间），本阶段只要求数据结构与日志可核对，诊断 UI 归 V0.3.9。
- 装配只做拼接与排序，**不改写角色作者原文**（不摘要、不润色、不补全）。

### 2.3 手机音频传输契约（本阶段最重要的技术定案）

上行（手机→PC）：手机采集音频分片，经 WS 上行，PC 侧 `QwenStreamingRecognizer`（已有）转写，文本按 `chat.submit` 正常进入对话。需定案：

- 传输编码：JSON 文本帧内 base64（不破坏现有 JSONL 语义，+33% 开销）或 WS 二进制帧混合（需帧类型标记）。局域网与 Tailscale 场景两者皆可行，由逻辑轨定案并写明取舍理由。
- 采集参数与 ASR 要求对齐：采样率、声道、编码格式对照 `docs/design/dashscope/千问语音识别文档.md` 定稿（手机端 MediaRecorder/PCM 采集能力与文档要求匹配）。
- 说话结束判定：按住说话模式由松开事件结束；自动检测模式用 PC 侧 Silero VAD（已有）还是手机端判定，定案。

下行（PC→手机）：角色自然语言回复经 `is_tts_eligible` 判定后由 `QwenSpeechSynthesizer`（已有）合成，音频下发手机播放。需定案：音频格式、整段或分片流式、播放中断（用户切页/新消息到达）的协议语义、与 `stream_id`/`sequence` 的一致性归属。

**约束**：无论哪种方案，未鉴权连接不得上行音频；音频流必须绑定已打开的 conversation；不得因音频通道故障影响文本链路与桌面 stdout 路径。

### 2.4 契约冻结产出物

`docs/plans/V0.3.5-契约冻结.md` 一份，包含：命令/事件完整 payload 形状、状态枚举（复用 `character_cards/states.py`）、装配顺序、音频传输定案与理由、配对行为定义（见 L4）、前端 TypeScript 契约同步说明。冻结后双轨各自实现；实现中发现契约缺陷时，先改契约文档再改代码，双向同步。

## 3. 强逻辑 AI 轨道任务

### A. 角色卡接入对话（本阶段核心）

**L1. 角色提示词装配器**。新建 `core/character_prompt_assembler.py`，按 2.2 契约把卡字段装配为角色提示词与首句，输出可诊断模块列表。纯函数、可单测，不依赖 Sidecar。
验收口径：白厄样例卡装配结果包含名称、主要设定、五个备选问候的位置信息；装配不改写原文；空卡/草稿卡装配行为有明确定义。

**L2. active 卡接入对话链路**。改造 `adapters/dialogue/openai_compatible.py` 的 `_system_prompt(pair_id)` 路径：对话启动时若存在生效的自定义 active 卡，则角色侧提示词来自装配器而非内置 YAML；助手侧（单 Markdown＋简报＋输出格式）完全不变。内置角色对话路径不回归。
验收口径：`assert_single_markdown` 既有测试继续通过；自定义卡激活后新对话的角色名称、首句、人设来自卡；同一会话内角色身份稳定，不受后续切换 active 卡影响（或按冻结契约定义的语义执行， whichever 必须被测试锁定）。

**L3. 卡切换与对话的生命周期语义**。定义并测试：切换 active 卡是否影响已开对话（建议：不影响，仅新对话生效）；归档/删除正在被对话使用的卡时的行为（如实提示与降级，不静默换人）；重启后 active 卡与会话的角色身份恢复一致。
验收口径：三种场景各有真实测试锁定，无「对话中途角色人设悄悄变更」。

**L4. 自定义角色与助手配对**。建立「自定义卡 ＋ 现有 YAML 助手定义」的运行时配对解析：不复制助手配置、不新建第二套助手提示词；内置 pair（`march7_fourth_mirror` 等）零改动。卡级 `voice_profile.voice_id` 为 ready 时，该卡对话的 TTS 经 `voice_factory.resolve_effective_voice_profile` 优先用卡级音色，否则回退账号级/不可用。
验收口径：自定义角色保存、激活后与现有助手完成真实对话（真实引擎），角色以卡人设说话，助手行为与静音边界不变。

### B. 导入导出与头像资产

**L5. `card.import_json`**。基于已有 `codec.load_card_json`（不重写）：接受文件路径（前端经 Tauri 选择），导入为 `imported` 状态卡；返回卡摘要＋`CompatReport`；名称冲突按冻结契约处理（副本/确认）；导入卡中的音色模型字段归一到固定模型（codec 已做，接命令层验证）。
验收口径：白厄样例导入后，名称、主要设定、五个备选问候、世界书条目数、扩展字段全部保留且可再导出。

**L6. `card.export_json`**。基于 `dump_card_v3`：导出到用户选择路径；支持配套另存头像文件；未知扩展原样保留。
验收口径：白厄导入→导出→再导入往返，标准字段、问候、世界书、未知扩展无故不丢（复用并扩展 `test_character_card_codec.py` 回归）。

**L7. 头像资产服务**。`app_paths.py` 增加角色资产目录；实现资产写入/删除服务，落库 `character_assets`（该表首次产生真实写入方）；`card.set_avatar`/`card.remove_avatar` 命令；`card.list`/`card.get` 返回头像引用（形式按冻结契约）；`card.delete`/`card.archive` 时资产清理策略定稿并执行；上传后不依赖原始文件路径。
验收口径：上传头像→重启应用→头像仍在；删除卡后资产目录与表记录同步清理；`character_assets` 有真实读写测试。

### C. 角色卡级音色生命周期

**L8. `voice.card_bind_reference` / `voice.card_create` / `voice.card_unbind` / `voice.card_preview`**。为指定卡创建音色：参考音频资产化（本地文件转 data URI 提交，沿用 V0.3.3 已验证结论），clone 与 design 两条路径都接真实 DashScope 客户端（`QwenVoiceCustomizationClient` 已有）；进度/成功/失败经 `voice.card_provision_changed` 事件；成功写 `hsr.voice_profile.voice_id`＋状态 ready；失败保留原始错误且状态 failed；同一卡创建中不可重复提交；解绑不删除用户账号侧旧 ID。
验收口径：只用当前账号已存 `voice.api_key`/`voice.base_url`；无 Key 时如实报账号未配置；白名单外说话方/助手侧拦截继续生效。

**L9. 真实联调补齐（并行验证记录遗留项）**。用真实 Key 与真实音频完成：MP3/M4A data URI 提交、超过 10MB/60 秒边界行为、声音设计（`voice_prompt`）真实请求。每项记录真实请求结论到 `docs/character-card/千问参考音频能力验证记录.md` 增补章节。失败保留原始错误，不得用 mock 结论代替。

### D. 手机语音服务端

**L10. 上行链路**。按 2.3 定案实现：WS 音频上行 → PC 侧固定 ASR 转写（复用 `QwenStreamingRecognizer`）→ 转写文本以 `target=character` 进入当前 conversation 队列；说话结束判定按定案实现。
验收口径：手机上行一段真实语音，对话收到正确转写文本并产生角色回复；音频通道异常不影响文本命令与桌面链路；未鉴权连接上行被拒。

**L11. 下行链路**。角色回复 TTS 在 PC 合成，按定案格式/分片下发手机；只有 `is_tts_eligible=true` 的消息可产生下发；助手/工具/思考/系统事件零音频下发。
验收口径：手机端真实听到角色语音；服务端日志可核对「助手消息无任何 TTS 请求」；播放中断语义（切页/断连/新消息）按契约工作。

**L12. secure context 处理与用户文档**。真机 HTTPS 路径写明：浏览器麦克风要求 HTTPS，推荐 `tailscale serve` 提供证书；不内置自签证书方案。PWA 侧无 HTTPS 时由前端禁用语音入口（前端任务），服务端不做环境伪造。产出一份用户指引文档（建议 `docs/手机远程语音说明.md`，位置可定但必须更新对应目录 README 索引），覆盖 Tailscale 配置步骤与 http 场景说明。
验收口径：按文档步骤在 Tailscale HTTPS 下真实可用；文档不承诺任何发布方中继服务。

### E. 手机审批应答

### A. 角色创作工作室（桌面）

**V1. 完成角色创作页的整体创作体验**。在现有快速创建（`desktop/src/ui/character-create/`）基础上，交付完整的工作室体验：用户能从空白开始，经由清晰引导完成一张可用的最小角色卡，也能随时进入高级区域补充深度设定。快速与高级共享同一份卡数据，不得形成两套互相覆盖的内容。
本阶段高级区域覆盖酒馆标准高级字段：系统提示、历史后指令、备选问候、示例对话深化（`mufy` 扩展字段分区继续标注 V0.3.7，占位不得伪造可编辑表单——现有占位语义保留）。现有 `AdvancedPlaceholderPanel` 的替换方案由视觉轨定。

**V2. 头像体验**。本地选择与拖放上传、预览、替换、移除；JSON 导入卡缺头像时的呈现；导出 JSON 时的头像状态呈现。是否提供裁切/构图调整、以及全部交互形式由视觉轨自主决定（契约只保证 `card.set_avatar`/`card.remove_avatar` 与头像引用数据）。

**V3. 创作过程中的实时反馈**。角色卡实时预览、首句预览、保存状态反馈（已有保存状态机可扩展）、完成创建（draft→saved）的节点表达。长文本编辑、重复名称、未保存退出、保存失败需有明确但不打断创作节奏的处理。

**V4. 「使用该角色配对 / 开始对话」入口**（V0.3.3 原型验收遗留缺口）。角色库卡片与创作完成页可直接进入使用该角色的对话主路径；入口动作语义（激活卡＋开新对话）按冻结契约接线。

### B. 导入导出体验（桌面）

**V5. 导入流程**。选择/拖入 JSON → 解析中 → 导入预览（名称、头像、Character Card 版本、备选问候数量、世界书条目数量、已识别扩展、已保留但未运行的扩展——数据来自 `CompatReport`）→ 名称冲突处理 → 作为副本导入 → 成功；解析失败与导入失败呈现原始错误摘要，不得用默认角色或空内容掩盖。现有角色库「导入」占位按钮接通本流程。

**V6. 导出流程**。导出 Character Card v3 JSON：导出前预览（文件名、头像状态、世界书状态、扩展字段状态）、保存位置选择、配套另存头像、完成与失败反馈。现有「导出」占位按钮接通。

### C. 角色语音体验（桌面）

**V7. 语音设置页新增「为角色创建音色」**。完整流程：选择角色（含导入角色）、当前音色状态（未配置/创建中/就绪/失败）、参考音频选择与拖放（格式、大小、时长要求展示）、创建提交、进度、成功绑定、试听、重新创建、解除绑定、失败真实错误展示。账号未配置（无 Key）时给出真实阻塞说明与去配置的路径。界面不出现任何模型名称修改入口；不出现助手侧音色内容。

### D. 手机语音交互

**V9. 手机语音交互**。按住说话与自动检测两种功能模式的移动端表达；聆听中、转写中、朗读中三种过程状态的反馈；朗读与文本阅读的关系（正在朗读哪条角色消息）由视觉轨定。仅角色自然语言回复可朗读；助手、工具、思考、系统消息无任何朗读入口（继续静音边界）。转写失败、TTS 失败的真实提示与恢复入口。

**V10. 语音可用性边界**。HTTPS 未配置（http 局域网场景）时语音入口如实禁用并说明原因（指向用户文档的 Tailscale 方案）；麦克风权限被拒的提示与去授权入口；网络抖动时的表现。不得在不可用时假装可用或在可用时隐藏入口。

**V11. 审批应答体验**。审批卡从只读升级为可操作：批准/拒绝、详情（命令、路径、来源聊天）、提交后结果反馈；审批被另一端处理后的状态收敛表达（本端提交失败 `already_resolved` 时如实呈现并收敛，不显示为双端同时成功）。删除 `ApprovalCard.tsx` 现有「严禁批准/拒绝按钮」注释所代表的 P0 限制，替换为 P1 语义。审批不被伪装成对话消息。

**V12. 状态清单覆盖**。本阶段全部新界面必须覆盖以下状态并使用契约样例数据验证（呈现形式完全自由）：载入中、空、成功、失败（含原始错误）、进行中（创建/上传/转写/合成）、部分成功、重试中、不可用（环境/权限/账号缺失）。mock 数据仅用于视觉开发，验收前全部换真实 Sidecar 状态。

**V13. 双端一致性复查**。手机端新增语音与审批状态后，ConnectionBanner 五态、会话切换、水合恢复与新增状态不冲突；桌面与手机对同一失败（鉴权失败、断连、电脑休眠）的表达语义一致。
