# M0 基线记录：14 项问题复现场景与根因

> 作者：强逻辑 AI
> 状态：M0 完成。本文件把 14 项问题映射到现有代码上的固定场景与根因证据，作为 M1–M4 修复的回归入口。
> 基线验证：`pytest` 297 passed / 5 skipped；`vitest` 25 passed；`tsc --noEmit` 通过；`cargo test` 3 passed（2026-08-12）。

## 约定

- 前端协议权威：`desktop/src/contracts/protocol.ts`
- Python 核心契约：`src/pair_harness/core/contracts.py`
- Sidecar 命令集：`src/pair_harness/desktop_backend/commands.py`
- 消息/事件出口：`src/pair_harness/desktop_backend/application_service.py`、`events.py`
- Reasonix 复用判定已按方案 §「双 AI 分工/严禁重复造轮子」逐项检索本地克隆，见下。

## 1. 第一条用户消息不显示

**场景**：新建聊天 → Composer 输入 → 发送。前端 `Composer.submit` 先 `setDraft("")` 再 `await actions.submitMessage`（`Composer.tsx:50-55`）。

**根因**：
- `chat.submit` 处理器 `_chat_submit` **等待整个回合**完成后才返回（`application_service.py:473-506`：`await self.orchestrator.handle_character_input(...)`）。
- 前端 `submitMessage` 用 `await request("chat.submit", ...)`（`actions.ts:84-94`）。后端回合处理期间请求挂起；若回合失败/耗时异常，`await` 不返回且前端已清空草稿，界面无任何回显。
- 消息本身在回合内才落库并发 `message.created`（`orchestrator.py:298-303`），缺乏「先回执后处理」的快速接受路径。

**验收入口**：M1 后 `chat.submit` 同步落库 → 立即返回真实 `message_id` → `message.created` 立即出现；处理失败时文字仍在气泡内可重试。

## 2. 审核模式触发 DashScope InvalidParameter

**场景**：`/帮我审核`（REVIEW 审批模式）下，角色结构化输出解析失败降级为 `……`，仍进入 TTS。

**根因链路**（已确认）：
```
openai_compatible.py:36  _FALLBACK_SPEECH = "……"
openai_compatible.py:183-198  _parse_output 解析失败 → speech = "……"
  → stream_reply yield character.final（:372-378）
orchestrator.py:921-934  角色结果回应 _message(source=CHARACTER, text="……")
orchestrator.py:275-277  _message 触发 VoiceRuntime.on_message
voice_runtime.py:303-319  is_tts_eligible(CHARACTER, CHARACTER_SPEECH)=True；
                         :311-314 仅 strip 空串检查 → "……" 非空放行 → enqueue
qwen_tts.py:148-150      唯一防护 `if not request.text.strip()` 挡不住 "……"
  → dashscope.streaming_call("……") → InvalidParameter
voice_runtime.py:355-356  捕获 → on_error("语音合成失败：...")
```

**缺口**：`voice_runtime.on_message` 与 `qwen_tts` 都只挡纯空串；`extract_speech_segments`（assistant 路径）不剔除纯标点/省略号。`system.approval`、tool、system 已被 `voice_policy.is_tts_eligible` 白名单排除，不属于缺口。

**验收入口**：M1 后 speech 为空或只含标点时**不创建**可朗读请求；审查/工具/系统文本静音。

## 3. 切推理等级后回到聊天模式

**场景**：协作模式 → 切推理档位（`project.update_settings`）→ 界面回到聊天模式。

**根因**：
- `hydrateSnapshotState` 每次快照水合都用 `snapshot.current_conversation.last_mode` 覆盖本地 `mode`（`desktopStore.ts:173`）。
- `project.update_settings` 返回整份 `self.bootstrap()`（`application_service.py:357-400`），`request()` 自动 hydrate（`actions.ts:26-31`）。
- DB 的 `last_mode` 只在 `_chat_submit` 带 `mode` 参数时写入（`application_service.py:486-489`）；前端 `switchMode` 只改本地 store（`actions.ts:77-79`），不写后端。DB 中 `last_mode` 往往停留在建会话时的 `chat`，于是设置命令一次水合就把界面打回聊天模式。

**验收入口**：M1 后 `conversation.set_mode` 单独读写模式；推理档位/审批方式/发送对象命令不覆盖模式；`hydrateSnapshotState` 在会话未切换时不重写本地 mode。

## 4. 聊天模式错误调用助手

**场景**：聊天模式角色输出 delegation → 后端仍执行。

**根因**：`handle_character_input` 无条件执行 `character_turn.delegation`（`orchestrator.py:340-381`），不检查当前 `conversation_mode`。聊天模式下角色提示词也仍允许形成委派。

**验收入口**：M1 后聊天模式 delegation 一律不执行，角色被注入能力边界；直接交给助手仅协作模式可用，后端裁决。

## 5. 协作模式不知道当前项目

**场景**：协作模式问「这个项目是什么」，角色反问或无法回答。

**根因**：`_build_messages` 只注入角色卡 + 近期对话 + 进度/结果摘要（`openai_compatible.py:121-145`），**没有项目名称/目录/时间/时区/模式**。编排器持有 `self.project`（`orchestrator.py:95`）但未注入对话请求。

**验收入口**：M1 后新增 `ProjectRuntimeContext`（项目名、绝对目录、系统时间、时区、模式），项目创建/选择/路径修复/账号切换时重建并注入角色与助手上下文；协作模式「这个项目是什么」形成委派由助手读取。

## 6. 语音播放严重卡顿

**场景**：连续朗读出现 PCM 块间断裂。

**根因**（已确认）：`AudioPlayer.play_blocking` 每个 PCM 块都 `with sd.OutputStream(...)` 新建并关闭输出流（`sounddevice_io.py:155-164`）。`run_playback_loop` 对每个 chunk 经 `asyncio.to_thread(play_blocking, ...)` 播放（`voice_runtime.py:349-352`）。流建立/关闭开销 + 块间线程调度造成停顿；无长期流、无有界缓冲。

**验收入口**：M2 后改为长期输出流 + 有界缓冲 + 单条/连续队列共享流；停止即时生效；空闲后关闭。

## 7. 交给助手的信息回到角色区

**场景**：协作模式「交给助手」发送 → 用户消息出现在角色区，助手回复在工作台，上下文断裂。

**根因**：`presentAppShell` 只按 `source` 切栏（`presenters.ts:32-41`）：`source !== assistant && source !== tool` 归角色区。用户直发助手消息 `source=user` 落角色区；`Message` 无 `target` 字段（`contracts.py:81-102`）。

**验收入口**：M1 后 `Message.target`（character|assistant）、`origin`（user|character_delegation|system）、`delegation_id` 保存；Presenter 按归属分区；`user+target=assistant` 及后续执行记录只在工作台。

## 8. 聊天与协作模式无法无缝切换

**场景**：聊天 ↔ 协作切换丢滚动/草稿/状态。

**根因**：
- 模式是纯前端状态（见问题 3），后端不持久化实时模式。
- `Composer` 的目标与草稿是组件本地 `useState`（`Composer.tsx:37-38`），不看 ViewModel 的 `composer.target`/`draft`（视觉方案 §1.3）。
- `Workspace` 在聊天模式整栏卸载工作台（`Workspace.tsx:67-69`），工作台内容与滚动随 DOM 卸载丢失。

**验收入口**：M1 后端持久化模式；M4 由强视觉 AI 完成工作台开合动画与草稿/滚动保留（前端 store 收编 Composer 目标与草稿）。

## 9. WebSocket 1011 刷屏 / 错误接管整屏

**场景**：Sidecar/WebSocket 一次抖动 → `error.reported` 置 `status=error` → 整屏「启动失败」，只能重启。

**根因**（已确认）：
- 1011 实际来自 **DashScope 语音 WebSocket**：ASR 错误（`qwen_asr.py:225-232` → `AsrEvent(error)` → `voice_runtime._on_error`）、TTS 错误（`qwen_tts.py:121-126` → `QwenTtsError` → `run_playback_loop` catch → `voice_runtime._on_error`）。当前终点是 `voice.state_changed`（`application_service.py:278-280`）→ Composer 单行小字（`Composer.tsx:61-73`），**并不整屏**。
- 真正整屏 error 只有四处 `error.reported`：Rust 非法 JSON（`main.rs:202-213`）、Sidecar EOF/断开（`main.rs:224-233`）、Python 启动失败（`__main__.py:52-72`）。`desktopStore.ts:292-295` 对 `error.reported` 一律置 `status="error"`；`AppShell.tsx:41-43` 整屏。`disconnected` 状态无任何写入路径（`desktopStore` 只留类型）。
- Rust 无崩溃重启逻辑：EOF 后只发 `backend_disconnected` 并 `fail_pending`，`BackendState.child` 残留死进程引用，`app.reconnect` 不存在，后续 `desktop_request` 写 stdin 失败（`main.rs:280`）。
- `unwrapResponse` 丢弃 `error.code`（`backend.ts:13-18`），前端无法分级；`loadBootstrap` 失败必置整屏 error（`actions.ts:37-39`）。

**验收入口**：M2 后错误分级 `fatal|recoverable|info`；同一错误短时间内只显示一次；WebSocket 有限重试 + 退避；单次语音/模型连接失败不切全局错误页；恢复后发 `connection.restored`；仅启动期 Sidecar 无法拉起才整屏。

## 10. DeepSeek 思考与回复不能流式显示

**场景**：角色回复长时间无反馈，思考一次性出现，正文一次性出现。

**根因**（已确认）：
- `OpenAICompatibleDialogueModel.stream_reply`：`reasoning_delta` 只累积不发射（`openai_compatible.py:367-368`）；`content_delta` 原样作为 `speech.delta` 发射（`openai_compatible.py:369-371`，DeepSeek 下即原始 JSON 分片）。
- 编排器忽略所有增量，只取 `character.final`（`orchestrator.py:322-326`）。
- 角色（character）的增量没有任何桌面通道（`application_service.py` 只转发 assistant 的 delta，:564-598）。
- 无增量 JSON 字段解析器；原始 JSON 可能直接进气泡（视觉方案 §1.4）。

**验收入口**：M2 后增量解析 DeepSeek 结构化输出，只推干净 `reasoning`/`speech` delta；`reasoning_content` 直接进思考通道；原始 JSON 永不进入消息气泡；最终完整对象覆盖预览。

## 11. 忙碌时不能提前提交下一条消息

**场景**：助手忙碌时发新消息 → 静默丢失或阻塞。

**根因**：无 `conversation_inbox`；`handle_direct_input` 在活动任务时把新指令归一为 `TaskAmendment` steer（`orchestrator.py:395-426`），无「排队 followup」语义；无编辑/撤回/调序。

**验收入口**：M2 后持久化 `conversation_inbox`；忙碌时默认 `followup`，明确选择「立即插入」才 `steer`；支持编辑、撤回、调序；重启/断线不丢队列。

## 12. 基础 Harness 功能不足

**根因**：缺 turn/item 生命周期、流式状态、审查生命周期、连接分级、账号隔离、配置中心（分属 M1–M4）。Reasonix 检索结论：持久化队列（`internal/sessioninbox/*`）、流式增量（`internal/provider/openai/readStream`、`think.go`）、错误重试（`internal/provider/retry.go`）、配置分层（`internal/config/*`）、会话恢复（`internal/control/controller.go:Resume`）均为**直接复用（Go 原样/语义迁移）**；账号云服务为独立 TS 服务（部分适配，本项目按方案 §M3.4 走 Codex app-server 官方接口）；**无 VAD/音频实现（确无）**。

## 13. 缺少内置配置和多账号

**根因**：SQLite 无 accounts/provider_configs/secret_refs/conversation_inbox 表；项目无 `account_id`；设置全部来自环境变量（`settings.py`）。无本地注册登录。Codex 登录未接线。

**验收入口**：M3 后双账号项目/聊天/配置完全隔离；Codex OAuth 与 API 登录各一次闭环；安装后真实登录配置可用。

## 14. 审查提示长期常驻

**场景**：审批模式为 `review` 时，无操作也显示「审查智能体正在评估高风险操作…」。

**根因**：`ApprovalBar.tsx:23-49` 在 `mode==="review"` 时无条件渲染；`approval.reviewText` 恒为 `null`（`presenters.ts:87`）；无 `review.started/completed/failed` 事件。审查智能体只在 `ApprovalManager.gate/adjudicate` 的 REVIEW 高风险路径真正被调用（`approval.py:146-163`、`250-266`）。

**验收入口**：M1 后 UI 只消费 `review.started/completed/failed` 真实事件；未实际调用审查智能体时不显示。
