### 3.2 需求窗口的确定方法

在原月需求文件上按时间排序，沿现有 `time_split_ratio=0.3` 规则求出划分点，采用划分点之后的需求作为本次评价来源。检查模型训练记录并登记数据关系。

运行配置直接指向该文件，`time_split_mode` 设为 `null`，使用已登记窗口。输入准备时完成时间划分，环境读取固定请求。两个策略及所有回合共用同一需求文件。

## 5. 指标与请求解释的固定规则

### 5.1 请求守恒与统一分母

定义本次评价的请求计数：

```text
loaded = arrived + not_arrived
eligible = served + waiting_churned + waiting_timeouts + onboard_churned
           + waiting_remaining + onboard_remaining
arrived = eligible + structural_unserviceable_arrived
```

计数按请求计划到达时间、实际事件及结束状态核对。环境在初始化时为全部结构不可服务请求写入终态和带计划时间的状态记录；本次模拟上限采用 `[0,900)`，结构请求按该时间边界分出已到达及尚未到达数量。提前结束时登记实际处理事件的时间边界，按该边界统计。原始结构不可服务计数保存为已加载全量，业务守恒使用已到达部分。守恒失败使该回合评价失败，产物保留具体差异及原始记录。

正式业务服务率为 `served / eligible`，算法流失率为 `(waiting_churned + waiting_timeouts + onboard_churned) / eligible`，等待及车上流失分别使用同一分母。`eligible=0` 时显示“无可服务到达请求”，保存分子与分母，数值表示遵循固定 schema。

现有结果中的字段按自身定义保存，新增正式业务指标通过指标版本明确计算规则。独立验收与报告读取相同版本的结果，历史研究记录按原协议解释。

### 5.2 其他指标与聚合

| 指标 | 核验规则 |
| --- | --- |
| TACC | 成功服务请求的直达行程时间之和，与 `step_tacc_gain` 累计核对 |
| 等待时间 P95 | 使用已产生 `pickup_time_sec` 请求的 `pickup_time_sec - request_time_sec`，与评价器当前定义一致；保存有效样本数 |
| 服务 Gini | 使用全部 Layer-2 站点的上车人数，包含零服务站点 |
| 剩余请求 | 分别列出尚未到达、等待中和车上请求的数量及请求 ID |
| 结束条件 | 保存 `end_reason`、实际步数、模拟时长和已生效的终止规则 |
| 三回合汇总 | 数值指标等权平均，标准差 `ddof=0`；先按种子配对，再计算策略差值 |

报告将等待指标写为“三回合等待 P95 的均值”，保留每回合值。无上车样本的回合同时标明样本数，避免将评价器输出的零误读为实际等待表现。

### 5.3 未服务请求原因

逐请求导出原始状态和原因，依据事件分别统计 `timeout`、`probabilistic_churn`、`onboard_churn` 及 `structural_unserviceable`。结束时的等待、车上及尚未到达请求关联该回合 `end_reason`。

报告说明每类数量、对应比例及来源位置。存在缺失状态或原因时，该要求标记失败并补齐证据。策略解释由模型基于这些真实结果完成。
