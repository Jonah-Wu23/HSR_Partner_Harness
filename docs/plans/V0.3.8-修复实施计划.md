## 2. 修复任务分解（T1–T6）

> 每个任务给出根因证据指针与修复方向；实现细节由执行者定，但不得偏离 Let It Fail / Let It Go。

### T1 后台保活架构（C1，架构级，本阶段最大项）

根因链（证据）：

- wry 0.55.1 `WryActivity.kt` onPause 调 `mWebView.onPause()`，暂停全部 JS/网络处理；`MainActivity → TauriActivity → WryActivity` 壳内无覆写。
- `WsForegroundService.kt:29-140` 只有常驻通知＋30 分钟 `PARTIAL_WAKE_LOCK`＋`START_STICKY`，**零网络代码**。
- 前端 `desktop/mobile/src/lib/wsClient.ts:156-185` 无心跳、onerror 不置状态全依赖 onclose；服务端 `src/pair_harness/desktop_backend/ws_server.py:200-201` `WebSocketResponse()` 不带 `heartbeat`——MIUI 掐网不回 RST，事件写向死 socket 静默丢失。
- 回前台零重同步：全 mobile 端仅通知权限代码监听 visibilitychange；重试 5 档约 31s 耗尽进 `unreachable` 终态永久停摆；`ConnectionBanner.tsx:31-34` 在 connected 时返回 null（zombie 连接无横幅）。
- Manifest 缺 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`、`SCHEDULE_EXACT_ALARM`；targetSdk 36 下 dataSync 前台服务 Android 15+ 有 6 小时上限，长期需换型。

修复方向（选型需在动工前与用户对齐，契约 §9.2 spike 判据已被真机否定，需修订契约）：

1. **原生 WS 常驻通道**（架构解）：前台服务内建 Kotlin 侧 WS 客户端常驻收事件，按通知规则直投本地通知——这是"锁屏收通知"的唯一可靠路径；WebView 前台时事件仍走 JS 通道，双通道去重口径需冻结进契约。
2. **双端心跳**：服务端 `WebSocketResponse(heartbeat=N, receive_timeout=…)`；前端周期 ping＋超时主动断开重连，让半开连接在 2N 秒内暴露。
3. **回前台重同步**：`visibilitychange→visible` 时强制重连或按 `lastSequence` 直接 bootstrap 补拉；`unreachable` 终态回前台自动复位重试，不再永久停摆。
4. **Manifest 与引导**：补 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（＋运行时引导跳电池优化设置）；评估 dataSync 替代类型。

### T2 移动端播放路径改造（C2）

根因链（证据）：

- `desktop/mobile/src/lib/voicePlayback.ts:51` 每条消息新建 `new AudioContext({ sampleRate: 24000 })`（OEM WebView 上最少锻炼的定制混音路径）；`:92-94` 无 `state` 检查、无 `resume()` 强行 `start()`（context 由 WS 事件创建，无用户手势，可能 suspended）。
- `maybeFinish`（voicePlayback.ts:60-74）靠 `onended` 时间线启发式，网络间隔 > chunk 时长即中途误判结束并 `ctx.close()`，后续 chunk 被 `if (finished) return` 静默丢弃——**必现截断缺陷，与崩溃无关也要修**。
- `ttsChunks` 全量驻留 zustand 至 finish（`mobileStore.ts:584-639`），长回复＝渲染进程内存尖峰。
- 服务端格式无问题（`qwen_tts.py` PCM 24000Hz mono s16le，逐 chunk 顺序推送）。
- 全仓无 `<audio>` 降级路径。

修复方向：

1. 播放启动改为用户手势内创建/`resume()`＋`state` 检查；优先验证「默认采样率 AudioContext＋JS 侧重采样」或 `<audio>`/MSE 降级路径，真机 A/B 后定案。
2. 结束判定废弃 `onended` 启发式，改由 `voice.mobile_tts_end` 事件驱动＋尾随等待。
3. `ttsChunks` 加上限/流式消费丢弃，消除内存尖峰；连续消息复用或串行化 AudioContext 生命周期，禁止新旧 context churn。

### T3 渲染进程崩溃恢复与前端兜底（C5）

根因链（证据）：

- wry 0.55.1 `RustWebViewClient.kt`/`RustWebChromeClient.kt` 均未覆写 `onRenderProcessGone`；壳 `MainActivity.kt`/`WsForegroundService.kt` 也没有——渲染进程死亡即永久空白，只能 force-stop。
- 前端 `main.tsx:6-10` 裸 `createRoot`，`App.tsx` 无 ErrorBoundary，React 渲染期未捕获异常整树卸载＝白屏。

修复方向：

1. 壳层覆写 `onRenderProcessGone`：重建 WebView 或提示用户一键恢复，如实呈现"页面已崩溃"，不得假装在线。
2. `onResume` 检测 WebView 健康（如 evaluateJavascript 探活），异常则 reload。
3. 前端加 React ErrorBoundary：崩溃时给可读错误与重载入口，原始错误进日志。
4. 与 T2 联动验证：播放路径改造后真机连续播放长回复，确认不再触发渲染进程死亡。

### T4 委派执行链修复（C4，含多处"静默"清除）

根因链（证据）：真机批次的委派根本没走到审批层——codex app-server 从未成功调用模型。

- `desktop_backend/engine_factory.py:73-77` 把 DashScope base_url/key 以 `OPENAI_BASE_URL`/`OPENAI_API_KEY` 注入 codex app-server，**codex-cli 0.147.0 不跟随该变量**，请求打向 `https://api.openai.com/v1/responses`（不可达）。CODEX_HOME `logs_2.sqlite` 实锤：`Unknown model qwen-plus` → 5 次退避 → "falling back to HTTP" → 约 21s 节奏无限重试 8 分钟以上，ERROR 级 0 条、不向客户端发任何通知。
- `adapters/codex/engine.py:164-198` 600s idle 超时是唯一兜底，且把根因改写成 "idle timeout"。
- 审批 `await future` 无超时（`application_service.py:172`）：审批发出无人应答（如手机退后台）时任务无限期挂起，且生成器暂停在 yield，600s 看门狗也触发不到。
- `codec.py:230` 未识别 method 静默 `return None`；`transport.py:101` app-server stderr 只 DEBUG 排空，默认 WARNING 下引擎诊断全黑。
- 队列不前进：`_dispatch_from_inbox`（`application_service.py:1620-1669`）只在回合链 **completed** 后派发，挂起的 ActiveTurn 永不释放；`task.cancel` 后终态是 cancelled ≠ completed，队列仍不放行。

修复方向：

1. **模型供给断点（根因）**：为 Codex 引擎生成 `CODEX_HOME/config.toml` 的 `model_providers`（受支持的端点覆盖方式）；或在引擎装配时显式拒绝"非 Responses 兼容后端 × codex 引擎"组合并如实报错——二选一，禁止继续静默误配。
2. **可观测性**：app-server 重试期零事件升级为可观测告警（如重试超阈值即向客户端发结构化诊断事件）；idle 超时报错必须携带底层原因；app-server stderr 排空级别与 `PAIR_HARNESS_LOG_LEVEL` 联动。
3. **审批超时**：`broker.request` 的 future 加超时（超时如实失败并释放 busy），或与 idle 看门狗联动。
4. **codec 防线**：未识别的服务端请求/通知不得静默丢弃，至少结构化记 WARNING。
5. **队列前进口径**：明确 cancelled/failed 终态后队列是否自动派发的语义，改契约后改代码；修复期间保持"不自动派发也必须如实呈现阻塞原因"。

### T5 队列 UI 双端接入（C3）

根因链（证据）：

- 后端协议齐全：`queue.edit/withdraw/prioritize` 在 `commands.py:23-25` 白名单；忙时 submit 只入队不建 Message（`application_service.py:1396-1418`），`queue.changed` 全量推送、bootstrap/`conversation.open` 均带 `queue_items`。
- 手机端零接入：`mobileStore.ts:842-851` 忽略 `queued:true` 返回值；事件 switch 无 queue 分支、`queue_items` 字段被丢弃；三个命令在 mobile 非测试代码 0 处调用——忙时消息彻底不可见。
- 桌面端半接入：QueueStrip 有编辑/撤回/插队，但排队消息不进消息流（`presenters.ts:23-27` 只映射 Message，胶囊条 24 字截断），`waitingFor` 硬编码"等待当前回复结束"，queued/processing 不区分，回合失败后条目永显示等待中且无错误提示。

修复方向：

1. **手机端接入**：store 消费 `queue.changed`/快照 `queue_items`；提交回执 `queued:true` 落地本地状态；timeline 增加排队项形态；接 `queue.withdraw/edit/prioritize` 三个命令入口（交互形态自主）。
2. **桌面端补全**：排队消息进入消息流呈现（已发送/排队态可见）；`waitingFor` 按真实状态派生，区分 queued/processing；回合失败导致队列停滞时如实呈现原因。
3. 双端共享 `@shared` 已有协议类型，不为手机端另造形状。

### T6 会话创建幂等与 mode 漂移（C6）

根因链（证据）：

- 服务端 `conversation.create`（`application_service.py:1233-1257`）无条件创建、零幂等；桌面三入口（`ChatColumn.tsx:346` 新建聊天、`CharacterLibraryPage.tsx:102-106` 与 `CharacterCreatePage.tsx:292-300` "使用该角色"）每次点击必建。
- 桌面 `actions.ts:223-229` 提交每次带窗口全局 `mode` → `application_service.py:1373-1377` 直接改写目标会话 `last_mode`（"委派"标签来源）；窗口无活动标签时 `conversation_id` 为空回退全局 current，消息落进没看着的会话。
- 列表时间取 `updated_at`（改名/改模式即刷新），02:35/02:56 并非创建时间。
- 手机端已排除：全部出站请求无创建类命令，`chat.submit` 必带 conversation_id，重连只走只读 bootstrap/open。

修复方向：

1. `conversation.create` 加幂等/复用口径（同项目同角色卡已有活跃聊天时复用或提示，语义先冻结再改代码）；三个桌面入口对齐该口径。
2. 修 `submitMessage` 的 `mode` 顺带改写：只在用户显式切换会话模式时更新 `last_mode`；空 `conversation_id` 回退路径如实报错或显式确认，不静默落会话。
3. 附带修 `_conversation_archive`（`application_service.py:1342-1348`）用全局 `current_project_id` 判断 remaining 的瑕疵：归档非当前项目最后聊天会在当前项目凭空补"新聊天"。
