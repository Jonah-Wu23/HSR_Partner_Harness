## 1. 背景与产品目标

HSR Partner Harness 是一个「角色扮演 × 编程助手」双人桌面应用。用户与一个有性格的虚拟角色对话；在协作模式下，角色可以把真实项目任务委派给本地编程助手执行，助手读取、修改、运行用户绑定的本地项目，过程与结果回流到对话。

产品解决三个核心问题：

1. **让编程助手有人格**：不是冰冷的工具面板，用户通过角色扮演获得自然的对话入口与情感表达。
2. **让对话能做事**：角色不是只会聊天。协作模式下它能委派助手读写项目、运行命令，任务过程与真实结果回流到对话。
3. **让自动化可控**：助手的一切工具操作都经过沙箱与审批闸门，用户始终掌握决定权。

产品目标：单机本地优先、开箱即用（内置 Python 服务与引擎二进制）、隐私可控（账号、密钥、引擎数据全部本地隔离存储）。

## 2. 目标用户与使用场景

| 用户 | 场景 |
| --- | --- |
| 角色扮演 + 编程双栖用户 | 让角色帮忙「看一下项目」「改个东西」，同时享受角色对话体验 |
| 需要审批控制的开发者 | 用「帮我审核」模式让审查智能体放行低风险操作，高风险操作仍需人工确认 |
| 对本地隐私敏感的开发者 | 账号、密钥、会话数据全部本地存储，可离线使用演示模式 |

典型用户旅程：注册本地账号 → 首次引导选择项目文件夹与模型服务商并完成连接测试 → 进入项目 → 与角色对话 → 切换到协作模式，让角色或本人把任务交给编程助手 → 工具操作经审批执行 → 结果由角色如实汇报 → 语音可朗读回复。

## 3. 产品定位与设计原则

- **对话驱动**：一切能力从对话进入，不做功能面板堆砌。
- **双空间呈现**：角色区（对话与情感）与工作台（工具与执行）并列，角色说人话，助手干实事。
- **本地业务权威**：状态、审批、存储由 Python Sidecar 决定，桌面界面只做呈现。
- **可控的自动化**：安全（审批与沙箱）优先于效率，自动化不绕过用户。
- **Let It Fail**：真实失败必须暴露。不吞异常、不合成成功事件、不用默认文本掩盖未执行的任务；角色汇报以真实回执为准，成功、失败、取消不可倒置；界面可把底层异常转成可读提示，但不改变底层失败状态。

## 4. 名词术语

| 术语 | 含义 |
| --- | --- |
| 角色（character） | 由角色卡驱动的对话 AI，说人话，不直接操作项目。当前内置角色为「白厄」 |
| 助手 / 古代机器（assistant） | 本地编程助手，唯一握有工具执行权，执行真实项目任务。当前内置助手为「神秘的古代机械」 |
| 搭档（pair） | 角色 + 助手 + 主题色 + 双音色的最小产品单元，声明式 YAML 配置 |
| 委派（delegation） | 角色在输出 JSON 的 `delegation` 字段中携带的结构化任务（task）或修改（amendment）指令 |
| 直发助手 | 用户以 target=assistant 直接给编程助手下达指令，与角色委派走同一执行管线 |
| 聊天模式 | 会话的能力边界：角色不能读取或操作项目，不产生任何委派 |
| 协作模式 | 允许角色委派、允许助手读写项目的能力边界 |
| 回合（turn） | 一次提交到一次执行完成的生命周期单元：accepted → running → completed / failed / cancelled |
| 引擎（engine） | 编程助手背后的执行体：Codex app-server 或 DeepSeek-Reasonix ACP 子进程 |
| 审查智能体（reviewer） | 「帮我审核」模式下裁决高风险操作的只读智能体，只输出裁决 JSON |
| Sidecar | 本地 Python 后端进程（`pair_harness.desktop_backend`），经 JSONL 与桌面壳通信 |
| 事件序号（sequence） | Sidecar 事件的单调递增序号，是断线重连后前后端对账的基准 |

## 5. 系统架构总览

四层结构，职责单向向下：

- **桌面壳（Rust / Tauri 2，`desktop/src-tauri/`）**：单窗口应用。只做三件事：启动并守护 Python Sidecar 进程、经 `desktop_request` / `sidecar://event` 透明转发 JSONL 请求与事件、提供系统文件夹选择对话框（`tauri-plugin-dialog`）。Rust 层不感知任何业务方法。
- **前端（React，`desktop/src/`）**：分层为 contracts（协议类型）→ services（backend 抽象、actions、eventBatcher）→ Zustand store（事件归并、快照水合）→ presenters（store 转 ViewModel）→ ui（纯展示组件）。Tauri 环境走 `TauriDesktopBackend`，浏览器开发环境走 `MockDesktopBackend`。
- **业务层（Python，`src/pair_harness/`）**：Sidecar 入口 `pair_harness.desktop_backend`，持有全部业务状态（会话、消息、回合、队列、审批、账号、配置），是唯一的业务权威。
- **持久层（SQLite）**：数据库位于 `%LOCALAPPDATA%\PairHarness\pair_harness.db`（schema v7，按 `user_version` 逐级迁移），另有 `cache/` 子目录与按账号隔离的引擎数据目录。

分发形态：Tauri 打包时内置 PyInstaller 产物 `pair-harness-sidecar`、Codex 二进制（`codex.exe` 等）、Reasonix 二进制（`reasonix.exe`）与 VAD 模型，用户无需自行安装 Python 或引擎。

## 6. 功能需求

### F1 角色扮演对话

**目标**：用户与角色进行自然、流畅、有记忆的自由对话，角色由角色卡驱动，具备稳定人格。

**功能点**

- F1.1 流式双通道回复：思考链（reasoning）与正文（speech）分通道流式上屏。思考链以可折叠细条展示，流式时脉动提示「正在思考…」，结束后折叠为「思考了 x 秒」摘要。
- F1.2 角色卡驱动：角色人设、语言禁区（句式与用词约束）、执行边界由 `config/prompts/characters/phainon.md` 声明，剧情时间线锁定、深层剧透默认锁死。
- F1.3 上下文记忆：每轮注入最近 12 条用户/角色对话作为上下文（排除助手与工具内部消息）。
- F1.4 运行上下文注入：以系统消息形式向模型注入当前项目名、目录、本地时间、时区与模式（聊天/协作），角色能感知「当前在哪、能不能动项目」。注入内容不显示为聊天消息。
- F1.5 输出协议：模型每轮输出单个 JSON 对象，纯聊天 `{"speech": ...}`，委派时附加 `delegation` 字段。流式解析器（`IncrementalJsonSpeechParser`）从 content 通道增量提取干净台词上屏；原始 JSON 只进「技术详情」，绝不进气泡与 TTS。解析失败降级为占位台词「……」（不朗读）。
- F1.6 确定性边界修正：用户明确提出本地操作请求、或协作模式下询问当前项目而模型漏输出委派时，后端按用户原文补建结构化委派；角色台词自称「我来执行」时改写为交托助手的话术；结果回应的措辞按真实回执状态强制校准，失败不能描述成成功。
- F1.7 聊天模式能力边界：聊天模式下角色明确告知用户自己看不到项目，并建议切换协作模式；后端对聊天模式下产生的任何委派一律拒绝执行，落系统提示，不依赖前端禁用。
- F1.8 标题生成：首次有用户消息的提交后异步生成会话标题（助手身份、关思考、温度 0.2，失败重试一次加大 token 预算；规范化去引号标点、≤16 字）。用户手动改名后自动标题不得覆盖。Codex OAuth 链路不支持标题生成。

**验收标准**

- 对话流式上屏，思考链与正文分离展示；
- 角色人格与语言风格符合角色卡约束；
- 聊天模式下角色不产生任何项目操作，后端兜底拒绝；
- 回复中的「三个点」流式占位在任何失败路径下都会终结，不永久卡死。

### F2 协作模式与编程助手委派

**目标**：协作模式下，角色可以把任务委派给本地编程助手，用户也可以直接给助手发指令，形成「委派 → 执行 → 汇报」的完整闭环。

**功能点**

- F2.1 模式切换：顶栏 segmented 控件在聊天/协作间切换，按会话持久化（`conversation.set_mode`）；切换即时反映到界面。
- F2.2 角色委派：角色输出携带结构化委派（`task`：instructions + constraints；`amendment`：target_task_id + revision），经编排器转为真实任务执行。
- F2.3 直发助手：用户输入区选择「交给助手」直接下达任务，与角色委派走同一执行管线。聊天模式下该入口禁用。
- F2.4 任务执行：助手真实读写项目文件、运行命令、调用工具，过程以工具卡片实时呈现（运行中/已完成/失败/已否决四态，可展开命令与执行结果明细）。
- F2.5 执行结果回流：任务结束后合成执行结果摘要（状态、摘要、可见变更文件名、局限、待确认项），角色依据真实回执再回一轮台词汇报，禁止虚构成功。
- F2.6 运行中修改指令：任务执行中用户可追加新指令。运行中直发助手视为最高优先级修改（TaskAmendment），经引擎 steer 通道插入（Codex `turn/steer`；Reasonix `_reasonix.io/session/steer`）；角色也可建议修改。无法路由时落系统提示「修改未能应用：…」。
- F2.7 队列：助手忙碌时新提交先入队（持久化到 `conversation_inbox`，重启后恢复），当前回合完成后自动派发。队列条支持编辑（撤回并把原文拉回输入区）、撤回、立即插入三种操作；失败的任务退回队列可重试。
- F2.8 取消任务：顶栏/委派卡「取消任务」一键取消。生命周期先落 CANCELLED 终态，再向引擎发取消（Codex `turn/interrupt`；Reasonix `session/cancel`），角色如实汇报取消状态。
- F2.9 并发规则：全局同一时刻只允许一个活动助手任务。活动任务在另一聊天时，本会话直发助手被系统提示拒绝；角色在忙碌时委派会落可见系统提示「任务仍在执行，本次委派暂未受理」。任务执行期间不阻塞普通聊天轮。
- F2.10 进度摘要：任务执行期间向角色轮注入中性进度（当前步骤标签 + 已完成步骤数），不含命令、路径、输出原文；任务结束后清理。

**验收标准**

- 委派 → 执行 → 角色汇报闭环完整，工具调用过程实时可见；
- 忙碌时提交不丢失、自动排队，重启后队列恢复；
- 取消后用户消息与回执状态一致标记为已取消；
- 结果汇报与真实回执状态严格一致。

### F3 双编程引擎与演示模式

**目标**：编程助手可选择两种本地引擎，共享同一套事件、审批与任务生命周期协议；另提供无凭据的演示模式。

**功能点**

- F3.1 Codex 引擎（默认）：以子进程运行 OpenAI Codex app-server（JSON-RPC over JSONL），支持浏览器 OAuth 登录与 API Key 登录。支持线程 start/resume（会话引用持久化到 `engine_sessions`，重启后恢复）、turn/start（结构化 TaskRequest JSON，携带模型与推理档位）、turn/interrupt、turn/steer；事件映射覆盖助手消息增量、推理增量（summary/content 双通道）、命令执行、MCP 工具、文件变更与三类原生审批请求。
- F3.2 DeepSeek 引擎：以子进程运行内置 DeepSeek-Reasonix 的 `reasonix acp`（ACP v1 协议），复用角色对话的服务商与密钥。支持 session/new、session/resume、session/prompt、session/cancel、厂商扩展 steer；审批策略经 `session/set_config_option` 映射为 ask/yolo；引擎工具集限定为 13 件执行类工具；每账号独立的 `REASONIX_HOME`（config.toml + .env，密钥只走该目录 .env）。
- F3.3 统一供应商约束：角色对话与编程助手始终使用同一家供应商，不可分叉。DeepSeek 供应商 → DeepSeek 对话模型 + Reasonix 引擎；OpenAI 兼容 / OpenAI OAuth → OpenAI 模型 + Codex 引擎。配置写入时校验供应商与引擎、供应商与 Base URL 的一致性，不一致直接拒绝；切换供应商时补默认端点与模型并清空旧密钥。
- F3.4 切换即生效：更换引擎或模型配置后运行时立即重建，下一个任务使用新配置，无需重启应用。
- F3.5 演示模式：无外部凭据时的脚本化流程（Scripted 对话模型 + Scripted 引擎），覆盖委派触发、工具事件序列、文件补丁、成功/失败回执与三种审批模式的离线验证。Sidecar 默认 demo 启动，存在有效 `.env` 或 `PAIR_HARNESS_REAL` 标志时进入真实模式。

**验收标准**

- 两种引擎的工具卡片、审批请求、回合状态在界面上呈现一致；
- 切换引擎后下一个任务立即生效；
- 引擎子进程异常退出时，任务以真实失败回执终结，错误带退出码与 stderr 尾部；
- 演示模式不触碰文件系统、不需要任何密钥即可完成完整体验。

### F4 审批、风险规则与沙箱

**目标**：助手的一切工具操作经过安全闸门，三种审批模式覆盖从全人工到全自动的梯度；沙箱在任何模式下兜底拦截越界写操作。

**审批模式**（按项目持久化，输入区工具条可随时切换）

| 模式 | 行为 |
| --- | --- |
| 请求批准（`request_approval`，默认） | 每次工具操作都弹审批卡片，由用户裁决「允许 / 本对话内允许 / 否决」 |
| 帮我审核（`review`） | 低风险且信息充足的操作直接放行；命中高风险规则或信息不足的操作转审查智能体裁决；审查智能体否决或失败时用户仍可「仍然允许」覆盖 |
| 完全允许（`full_auto`） | 不弹审批，直接执行（引擎策略切到 workspace-write，写操作仍受项目沙箱约束） |

**功能点**

- F4.1 引擎策略映射：请求批准与帮我审核模式下引擎线程以 `untrusted` + 只读沙箱运行，一切写操作执行前挂起等裁决；完全允许模式以 `never` + workspace-write 运行。策略只对新开线程生效。
- F4.2 审批卡片：以卡片形式呈现操作摘要、命令/路径/patch 文件数与审批原因；裁决结果以 `system.approval` 卡片留痕在对话时间线。
- F4.3 「本对话内允许」缓存：按签名缓存——shell 取前两个词元（放行 `git status` 不等于放行 `git push --force`），文件类按类型 + 父目录，patch 统一一类；命中敏感路径或高风险规则的操作永不入缓存；切换或关闭会话时清空缓存。
- F4.4 风险规则表（`config/risk_rules.yaml`，仅帮我审核模式生效）：高风险工具类型 `file_delete`；shell 五组正则（删除类、git 破坏性、网络访问、依赖安装、系统级命令）；单次 patch 超过 5 个文件判批量修改；敏感路径 fnmatch（`.env`、`*.pem`、`*.key`、`id_rsa*`、`id_ed25519*`、`secrets*`、`credentials*`，读取写入都算，Windows 路径先归一化再匹配）。
- F4.5 审查智能体：复用对话模型的只读裁决者，输入仅为操作摘要与最近 3 条用户消息，只输出裁决 JSON（allow/reason/suggestion）；解析失败或异常一律安全否决；裁决理由与调整建议留痕在对话时间线，actor 记为 reviewer。
- F4.6 项目沙箱：写路径 resolve 后必须位于项目根目录下（含符号链接与 `..` 展开、Windows 跨盘符即越界）；shell 命令的工作目录锁定到项目根；越界操作直接否决并反馈引擎。
- F4.7 否决路径：沙箱越界或审批否决 → 工具卡片标记「已否决」+ 系统状态卡，任务标记失败；引擎侧把拒绝反馈给模型继续回合，任务最终成败由回合终态决定。
- F4.8 生命周期兜底：应用关闭时所有挂起审批置为否决；对未知审批 id 的裁决返回 `approval_not_found`；已裁决的工具调用不重复门控。

**验收标准**

- 三种模式行为差异明确，切换后立即生效；
- 越界写操作在包括完全允许在内的任何模式下都被拦截；
- 高风险操作在帮我审核模式下不会被静默放行；
- 审批留痕完整，可在时间线回看每次裁决的理由。

### F5 项目与会话管理

**功能点**

- F5.1 项目绑定本地文件夹：新建项目经系统文件夹选择对话框选定目录，默认项目名取文件夹名称，用户可随时改名。同一目录（resolve + 大小写归一）不重复建项目。
- F5.2 项目设置：审批模式与推理档位（低/中/高/极高/最高，对应 low/medium/high/xhigh/max）按项目持久化，可随时调整，改动即时下发到对话模型与引擎。
- F5.3 项目归档：归档项目级联归档其全部聊天；正在执行任务的项目拒绝归档；归档当前项目后自动切到最近的其他项目。归档操作需二次确认。
- F5.4 路径失效处理：项目文件夹被移动或删除时，项目显示「文件夹不可用」警告与横幅，聊天只读但历史完整可读，提供「重新选择文件夹」修复入口；修复后若项目名仍是旧目录名则自动改名，手动改过的名字保留。
- F5.5 多会话：项目内可建多个聊天会话，初始标题「新聊天」，首次完整回复后异步自动命名（见 F1.8）。会话按「运行中 / 今天 / 更早」分组，支持按标题搜索、行内重命名、归档（二次确认）。
- F5.6 会话归属与恢复：会话持久化 pair、模式、归档状态；重启应用后项目、会话、消息、工具记录、队列、引擎会话完整恢复。新会话不继承历史与引擎会话。

**验收标准**

- 新聊天自动得名且不打断对话；手动改名不被覆盖；
- 重启后项目/会话/消息/队列完整恢复；
- 路径失效时历史可读、可修复，不产生数据丢失。

### F6 多账号与本地账户体系

**功能点**

- F6.1 本地注册/登录：多账号并存，用户名唯一，密码 PBKDF2-SHA256 派生存储（200k 迭代 + 随机盐），永不明文。注册密码至少 6 位。账号门支持登录/注册同卡切换，失败就地报错且不清表单。
- F6.2 完整隔离边界：项目、聊天、队列、配置、密钥、Codex 凭据目录（`CODEX_HOME`）、Reasonix 配置目录（`REASONIX_HOME`）全部按账号隔离，业务入口统一校验归属，跨账号访问一律拒绝。
- F6.3 账号操作：免密切换账号、退出登录（回到内置 `default-local` 账号，数据不删除）、修改显示名与头像、修改密码（需校验旧密码）。切换账号流程：取消当前任务 → 重建认证服务与运行时 → 切到新账号最近项目与聊天 → 广播整份状态快照。
- F6.4 账号偏好独立保存：主题、语音开关等按账号存储。
- F6.5 Codex 登录态管理：每账号独立的 auth.json。状态机 logged_out / waiting / logged_in / expired；OAuth 登录启动 `codex login` 子进程并轮询落盘；API Key 登录直接写入（保留已有 ChatGPT token）；退出登录只清本账号凭据。

**验收标准**

- 切换账号后数据与配置完全隔离，互不可见；
- 密码不明文存储、不进入日志；
- 默认账号兜底存在，任何数据库都能打开。

### F7 首次引导

**功能点**

- F7.1 触发条件：非默认账号且未完成引导时，进入整屏三步引导，每步可跳过。
- F7.2 第一步「创建第一个项目」：系统文件夹选择，成功后允许重新选择。
- F7.3 第二步「配置角色模型」：三选一——DeepSeek（默认端点 `https://api.deepseek.com`，模型 `deepseek-v4-flash`）、OpenAI 兼容 API（自定义 Base URL 与模型，保存后走 API Key 登录）、OpenAI OAuth（调起浏览器授权）。「保存并测试」返回人话结果，测试成功才能进入下一步。

**验收标准**：引导完成后进入主界面且项目可用；连接测试失败时给出明确原因；跳过引导的用户后续可在设置中心补齐配置。

### F8 语音交互

**目标**：语音输入与语音朗读双工可用；语音能力基于 DashScope（Qwen 流式 ASR/TTS）+ 本地 Silero VAD，凭据与音色全部内置。

**功能点**

- F8.1 语音输入双方式：自动静音检测聆听（VAD，自动开始/结束说话、误触发丢弃、开口前 pre-roll 补偿）与按住说话（PTT，按下先停播报、松开收尾识别、非空才提交）。
- F8.2 输入矩阵：对角色说话支持 VAD + PTT + 文字三种方式；直发助手只支持 PTT + 文字。
- F8.3 实时转写：识别中间文本实时显示在输入框上方；识别完成后按当前发送对象提交为消息（角色轮或直发助手）。
- F8.4 VAD 降级：VAD 模型缺失或运行库不可用时自动退回按住说话，并明确提示用户。
- F8.5 语音朗读资格：只有角色台词与助手自然语言回复进入朗读队列；命令输出、工具记录、代码块、行内代码、命令/路径行、纯标点一律静音。
- F8.6 朗读队列：FIFO 播放；支持逐条重播（按消息重播，不受资格过滤但仍过滤不可读文本）、跳过当前句、停止并清空队列。助手执行中的阶段性说明提前播报，最终回复落库时按内容指纹去重，不重复播报。
- F8.7 播放互斥：TTS 播放期间暂停向 VAD 喂入音频帧，播放结束重开聆听，避免扬声器尾音误触发。
- F8.8 音色：角色与助手各配一个内置 DashScope 音色（随 pair 配置分发），设置页可分别试听；试听只允许内置音色。
- F8.9 失败处理：合成失败置为失败态、清空待播队列停止连发，等用户手动重播；语音运行时失败只提示错误，不阻塞文字主线。
- F8.10 配置边界：语音凭据、模型、音色、服务地址由应用内置，客户端写入这些键一律拒绝；账号侧只暴露语音总开关与 VAD 开关，关闭总开关立即停听停播。

**验收标准**

- 说话 → 转写 → 发送闭环可用，两种输入方式行为一致；
- 回复朗读自动触发且不朗读任何工具记录与命令输出；
- 关闭语音总开关后输入区语音按钮整体隐藏。

### F9 消息与工作台双空间

**功能点**

- F9.1 双空间布局：「一间房，两盏灯」。角色区常驻；工作台为可开合侧栏，聊天模式收起（宽度 0 但保留 DOM 与滚动位置）、协作模式展开；分割手柄可拖拽（30%–60%），支持键盘操作与完整无障碍标注。
- F9.2 消息归属规则：用户发给角色的消息、角色台词、系统消息归角色区；用户发给助手的指令、助手回复、工具记录归工作台。
- F9.3 消息类型与卡片：用户气泡、角色/助手气泡（各配对自己颜色与来源标签）、思考链折叠条、工具卡片（四态 + 可展开明细）、委派卡（位于角色区底部，展示任务摘要与运行状态，运行中可取消，把角色区的委派与工作台的执行结果连接起来）、审批卡、系统状态卡。

**验收标准**

- 双空间消息归属正确，工具过程实时可见；
- 流式占位在任何终结路径下都不卡死；
- 错误分级符合：可恢复的不打断使用，致命的明确整屏。

### F11 桌面形态、断线重连与稳定性

**功能点**

- F11.1 分发形态：单个 exe + 内置资源（Python Sidecar、Codex 二进制、Reasonix 二进制、VAD 模型、提示词配置）的分发包；NSIS 与 MSI 两种安装器。
- F11.2 Sidecar 守护：Rust 壳启动并守护 Sidecar 进程；非零退出判为崩溃，自动退避重连（立即 → 1s → 2s → 4s → 8s → 15s 封顶，跨崩溃周期延续防忙循环）；正常退出（exit 0）只通知不自动重连，等用户手动重连；应用主动退出时优雅关闭 Sidecar。
- F11.3 手动重连：技术详情抽屉提供「立即重连」（强制重启 Sidecar，30 秒超时明确报错）。
- F11.4 断线体验：断线期间保留全部已加载内容，顶部出连接横幅（「与本地服务失去连接，正在重试…」），不整屏接管；在途请求收到明确的 `backend_disconnected` 错误。
- F11.5 状态恢复：重连成功后前端自动重新水合整份状态快照；事件序号断裂同样触发重水合，保证前后端状态一致。
- F11.6 数据持久化：全部数据本地 SQLite 持久化，无云同步依赖；队列、审批缓存边界、引擎会话引用均可跨重启恢复。
- F11.7 优雅关闭：应用退出时取消所有挂起审批（置否决）、取消后台任务、关闭语音与引擎连接、关闭数据库。

**验收标准**：杀掉 Sidecar 进程后界面自动恢复；重启应用后状态完整；断线期间不丢已加载内容。

## 8. 协议与数据契约

### 8.1 JSONL 协议

桌面壳与 Sidecar 之间以 JSONL（每行一个 JSON 对象）通信，三层信封：

- **请求**：`{"kind":"request","id":<非空字符串>,"method":<命令>,"params":{}}`
- **响应**：`{"kind":"response","id","ok":true|false,"result"|"error":{"code","message"}}`
- **事件**：`{"kind":"event","event":<名>,"sequence":<单调递增整数>,"payload":{}}`

协议错误（空行、非法 JSON、未知方法、参数结构错等）以结构化错误码回收，进程不崩溃。事件序号由 Sidecar 统一发射，是断线重连的对账基准；快照携带当前序号，前端校验后续事件严格 +1，断裂即重新水合。

## 9. 安全与隐私

- 全部数据（账号、密钥、会话、引擎凭据）存储在本机 `%LOCALAPPDATA%\PairHarness` 与项目目录，无任何云端同步。
- 密码 PBKDF2 派生存储；API Key 明文存本地库但界面只显示掩码，不写入日志。
- 助手写操作被项目沙箱约束在项目目录内；敏感路径与高风险命令走风险规则表与审查智能体。
- 语音凭据与音色由应用内置并锁定，客户端不可改写。
- 审查智能体只读：只看操作摘要与最近 3 条用户消息，不能执行、不能再委派；裁决解析失败一律安全否决。

- **P1（体验增强）**：F3 双引擎、F6 多账号、F7 引导、F8 语音、F9 双空间呈现、F10 设置、F12 搭档体系。
- **当前明确不做**：云同步/远程访问、移动端、插件市场、多用户协作、单实例限制（多开会各自拉起 Sidecar）。
- **规划中（不在本文档承诺范围）**：V0.3.0 多搭档目录与选择入口；V0.4.0 正确性与度量；V0.5.0 上下文投影与性能；V0.6.0 SillyTavern 角色卡导入。详见 `docs/V0.3.0-V0.6.0 Plan.md`。
- **已知简化点**：委派卡状态目前只区分运行中/已完成（失败与取消未在卡片上区分）；「日常聊天」入口在导航中禁用占位（即将推出）。
