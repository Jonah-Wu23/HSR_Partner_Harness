# HSR Partner Harness V0.3.2 详细修改计划

> 文档日期：2026-08-16  
> 当前代码版本：0.3.1  
> 目标版本：0.3.2  
> 计划状态：待实施  
> 真实编程助手链路：DeepSeek 模型 → Reasonix ACP → HSR Python Sidecar → Tauri/React

## 0. 实施前强制阅读与禁止猜测

任何实施者在修改语音代码前，必须完整读清楚以下三份项目内文档，不能只看搜索摘要、旧计划或当前脚本注释：

1. `docs/design/千问声音复刻文档.md`
2. `docs/design/千问声音设计文档.md`
3. `docs/design/千问语音识别文档.md`

随后必须对照阅读当前实现：

- `scripts/create_qwen_voice.py`
- `src/pair_harness/settings.py`
- `src/pair_harness/desktop_backend/voice_factory.py`
- `src/pair_harness/adapters/audio/qwen_asr.py`
- `src/pair_harness/adapters/audio/qwen_tts.py`
- `src/pair_harness/core/voice_runtime.py`

开始编码前必须写出并核对一张最小契约表，至少包括：创建接口、`model`、`action`、固定 `target_model`、音频字段、响应中的音色 ID 字段、ASR WebSocket 地址、TTS WebSocket 地址、北京/新加坡 Key 与地址匹配关系。只有文档和当前真实链路共同确认的字段才能进入生产代码。

如果三份文档、DashScope SDK 实际行为和当前代码出现不一致，立即停止该项实现，先把差异和真实请求结果记录到本计划或实施记录，再决定修改方式。严禁自行猜测接口支持、把其他模型系列的 payload 套到当前模型、用兼容分支掩盖失败，或为了让测试通过伪造成功音色 ID。

本版本冻结以下永久产品契约：

- ASR 固定为 `qwen-audio-3.0-asr-flash-streaming`。
- TTS、5 个声音复刻和古代机械声音设计的 `target_model` 固定为 `qwen-audio-3.0-tts-flash`。
- 用户只能配置自己的 DashScope API Key 和服务地址，不能选择、填写或覆盖 ASR/TTS 模型。
- 前端表单、JSONL 命令参数、SQLite 账号配置和 `.env.example` 都不得提供用户侧模型修改入口。
- 后续实施不得因为其他模型支持本地 Base64 或价格不同，擅自切换到 Qwen3-TTS-VC、Qwen3-TTS-VD、CosyVoice 或其他模型。

## 1. 版本结论

V0.3.2 集中解决五件互相关联的问题：

1. 助手工作台必须按真实发生顺序显示多段思考、阶段性回复和工具调用。同一轮任务可以出现多次“思考 → 回复 → 工具 → 再思考 → 再工具 → 最终回复”，一次模型回合也允许并列发起多个工具调用。
2. 按"Let It Go"方案修复 Reasonix 在 Windows 下对只读 PowerShell 管道判定过严的问题：废弃静态 AST 层层拦截，只读任务全面放行（脚本块、计算属性、变量赋值、命令链、命令替换均不再静态拦截），命令执行权与自纠错权交还大模型；语法或环境错误以原生 stderr 回传给模型自行纠正。详见第 6 节。
3. 解除全局单任务限制。用户可以在聊天 A 启动任务后切到聊天 B 继续发送，A、B 同时工作；两个聊天可以属于同一项目，也可以属于不同项目。
4. 同一个桌面窗口可以打开多个聊天标签页；任意聊天还可以拆成独立窗口。多个标签页和窗口共享 Sidecar 权威状态，各自保留当前查看的聊天。
5. 把语音链路改为用户自带 DashScope Key。分发包内置白厄、流萤、萨姆、三月七、第四面镜的参考音频和古代机械的声音设计提示词，用户在语音页填写自己的 Key 与服务地址后，一键在自己的百炼账号下生成 6 个专属音色，后续 ASR、TTS 和音色创建费用全部使用用户自己的账号额度。

本版本以 DeepSeek/Reasonix 为主链路实施和验收。Codex 适配器只做回归检查，不能再把 Codex app-server 的行为当成这三个问题的主要依据。

本文只吸收“先调查、再冻结契约、最后分阶段验证”的工作思路，不启用 Superpowers 工作流，也不增加额外的审批关卡或工作流框架。

## 2. 范围与产品边界

### 2.1 本期范围

- 保留 Reasonix 原始 ACP 流中的 `agent_thought_chunk`、`agent_message_chunk`、`tool_call`、`tool_call_update` 和 `session/request_permission` 的先后关系。
- 把助手一轮任务拆成多个可持久化的工作台消息段，并与工具卡按统一顺序混排。
- 修复 Reasonix 只读命令分类器对常见 PowerShell 只读管道的误杀（按第 6 节"Let It Go"方案精简静态拦截）。
- 同一账号下，不同聊天可以同时运行角色回合或助手任务。
- 同一聊天仍然一次只运行一个回合，后续输入沿用现有聊天队列。
- 一个账号继续复用一个 Reasonix ACP 进程；每个聊天使用自己的 Reasonix `sessionId`。
- 取消、审批、失败、流式收尾和忙碌状态全部按聊天和任务精确归属。
- 项目栏与聊天列表显示各自的运行状态，切换聊天不会停止后台任务。
- 同一个窗口支持多个聊天标签页；普通点击聊天时打开或聚焦对应标签页。
- 聊天支持“在新窗口打开”；同一聊天可以同时出现在多个窗口中，消息、工具、队列和任务状态实时一致。
- 用真实 DeepSeek 配置完成双聊天并发、工具权限和多段时间线联调。
- 语音页开放用户自己的 DashScope API Key 与服务地址，密钥只保存在当前本地账号的 `secret_refs`，不写入 `.env`，也不进入安装包。
- 用内置的 5 份参考音频为固定的 `qwen-audio-3.0-tts-flash` 创建 5 个复刻音色；用内置提示词为同一固定 TTS 模型创建古代机械设计音色。
- 按本地账号保存 6 个生成的音色 ID，切换账号时使用该账号自己的音色映射。
- ASR 继续使用 `qwen-audio-3.0-asr-flash-streaming`，通过用户填写的 Key 和地域匹配的 WebSocket 地址直连 DashScope。
- 删除语音设置页的赞助卡、收款二维码和“作者自费提供语音”文案；同步删除 README 中的二维码、相关截图说明和项目支持文案。
- 同步正式版本号为 0.3.2，并按仓库既有打包流程验证本地制品。

### 2.2 明确不做

- 不引入多 Agent 编排框架，也不启用 Superpowers 工作流。
- 不重写 Reasonix 的任务规划、子任务策略或模型提示词。
- 不用关键词、正则或固定句式判断模型何时应调用工具、何时应继续思考。
- 不把 `review` 或 `request_approval` 粗暴映射成无审批的 `yolo`。
- 不允许同一个 Reasonix `sessionId` 同时执行两次 `session/prompt`。
- 不支持不同账号同时运行；账号切换仍是运行时隔离边界。
- 不做单个窗口内的多聊天分栏平铺。V0.3.2 使用标签页承载单窗口多聊天，使用独立 Tauri 窗口承载并排查看。
- 不实现标签页分组、固定标签、跨窗口拖拽或关闭应用后的整组窗口恢复。
- 不伪造旧记录的工具顺序。升级前已经被压平的历史记录无法可靠还原，只按旧版方式展示。
- 不把普通命令不存在、参数错误或模型工具参数错误包装成权限成功。
- 不建设作者承担费用的 ASR/TTS 转发服务器，也不增加临时文件服务器或对象存储上传链路。
- 不把作者的 `.env`、DashScope API Key 或其他长期凭据写入 EXE、Sidecar、前端资源或 NSIS 安装包。
- 不再把作者账号下预先生成的音色 ID 当作分发版用户可直接调用的音色。
- 不把其他模型系列的 `input.audio.data` payload 套到 `qwen-audio-3.0-tts-flash`。当前模型仍使用 `input.url` 字段，但真实请求已确认该字段接受本地音频生成的 data URI；V0.3.2 默认使用安装包内同一份参考音频，不依赖公网托管。
- 不保留语音页、README 或其他发布材料中的收款二维码和赞助启用流程。

### 2.3 保持不变

- Python 层仍是业务状态权威来源。
- 每个聊天继续独立保存消息历史和引擎会话引用。
- 角色负责对话和结构化委派，助手负责工具执行。
- 工具输出、命令、路径和日志保持静音；只有自然语言回复可进入 TTS。
- 语音只由当前语音所有者窗口播放；用户自建音色不会改变多窗口单实例语音所有权规则。
- 真实失败必须保留失败状态和原始技术详情。
- 不使用 `git add -A`，不混入工作区现有的并行修改。

## 3. 当前链路与已确认事实

### 3.1 DeepSeek/Reasonix 是当前真实编程助手

- `src/pair_harness/desktop_backend/engine_factory.py` 在 DeepSeek 配置下启动 `reasonix acp`。
- 每个账号使用独立的 `REASONIX_HOME`，但账号内由一个 `AcpCodingEngine` 和一个 JSONL transport 复用同一个 Reasonix 进程。
- `src/pair_harness/adapters/acp/engine.py` 把 Reasonix ACP 事件映射为 HSR `EngineEvent`：
  - `agent_thought_chunk` → `ASSISTANT_REASONING_DELTA`
  - `agent_message_chunk` → `ASSISTANT_DELTA`
  - `tool_call` / `tool_call_update` → 工具开始、进度和结束
  - `session/request_permission` → HSR 审批链
- 已保存的 Reasonix session JSONL 证明，同一次用户任务中实际存在多轮思考、说明和工具调用。上游模型能力和 Reasonix ACP 协议并没有把一轮限制成“一次思考、一次回复”。

### 3.2 Reasonix 已经支持不同 session 并发

- `DeepSeek-Reasonix/internal/acp/server.go` 为每个入站请求启动独立 goroutine，并通过写锁保证 JSONL 行不互相穿插。
- `DeepSeek-Reasonix/internal/acp/service.go` 的运行锁位于 `acpSession` 内部。
- `session/prompt` 只在同一个 session 已经运行时返回 `session already has an active prompt`。
- 因此一个 Reasonix ACP 进程可以同时执行 session A 和 session B；无需为每个聊天启动新的 Reasonix 进程。

### 3.3 当前 HSR 把真实时间线压平了

- `application_service._on_engine_event` 对同一任务始终使用 `assistant:{conversation_id}:{task_id}` 作为唯一流式消息 id。
- 思考和正文持续追加到同一个气泡，工具前后的新一段思考不会生成新段。
- `ConversationOrchestrator._execute_once` 用单个字符串累计整轮助手正文和思考，任务结束时再生成一条汇总消息。
- `desktop/src/ui/workspace/Workspace.tsx` 先渲染全部助手消息，再渲染全部工具卡。
- 最终效果只剩“一块思考/回复 + 一组工具”，真实交错顺序消失。

### 3.4 当前多聊天被 HSR 自己串行化

- `GlobalEngineState.active` 只能保存一个 `ActiveTurn`。
- `_chat_submit` 只要发现任意聊天存在活动助手任务，就把新提交放进队列。
- `task.cancel` 不接收聊天或任务 id，只能取消全局活动任务。
- `_active_lifecycle`、启动/结束回调、前端 `activeTask` 都只有一个槽位。
- `_chat_submit` 为后台聊天提交前会调用 `_select_conversation_context`，从而改变全局当前项目、搭档、审批模式和助手提示词。
- `_on_execution_finished` 会清空所有聊天的流式消息记录；并发后会误收尾其他仍在运行的任务。

### 3.5 ACP transport 目前无法安全并发消费通知

- `JsonlProcessTransport` 对响应 id 的关联已经支持并发请求。
- 所有服务端通知和服务端请求却共用一个 `_notifications` 队列。
- 两个 `AcpCodingEngine.run_turn` 同时调用 `next_notification()` 时，会竞争消费同一队列。
- 虽然 `AcpCodec` 会检查 `sessionId`，错误消费者拿到事件后只能跳过，原本所属任务已经永久丢失该事件。

### 3.6 当前分发版语音链路不能供新用户直接使用

- 根目录 `.env` 被 `.gitignore` 排除；`desktop/scripts/build-sidecar.ps1` 只把 `config`、`assets` 和 schema 加入 Sidecar，Tauri 资源也没有 `.env`。
- 开发机能够使用真实语音，是因为 Rust 启动器能找到仓库 `.env` 并把 `PAIR_HARNESS_ENV_FILE` 传给 Sidecar。干净安装环境没有这份文件时不会得到作者的 `DASHSCOPE_API_KEY`。
- 现有 pair YAML 和安装包已经携带作者账号生成的音色 ID，但自定义音色属于创建它的百炼账号，只有 ID 不能替代对应账号凭据。
- 当前 `application_service._config_set` 明确拒绝客户端写入 `voice.api_key`、`voice.base_url` 和语音模型，用户无法在设置页补充自己的语音配置。
- `build_real_voice_runtime` 同时把一个 DashScope Key 交给 ASR 和 TTS；没有 Key 时运行时不会创建，ASR、TTS 都不可用。
- 当前语音页仍展示“语音服务由作者自费提供”的赞助卡和微信二维码，README 也保留同一承诺。这与实际分发行为不一致，V0.3.2 必须撤掉。

### 3.7 三份项目内千问文档给出的直接客户端方案

以下契约以 `docs/design/千问声音复刻文档.md`、`docs/design/千问声音设计文档.md` 和 `docs/design/千问语音识别文档.md` 为依据，不再根据旧脚本行为猜测接口：

- 5 个有参考音频的说话方使用 Qwen-Audio-TTS 声音复刻：
  - 请求 `POST {http_base_url}/services/audio/tts/customization`；
  - `model = voice-enrollment`；
  - `input.action = create_voice`；
  - `input.target_model = qwen-audio-3.0-tts-flash`；
  - `input.prefix` 使用不超过 10 个小写字母或数字的稳定说话方标识；
  - `input.url` 传入安装包本地参考音频生成的 `data:audio/*;base64,...` URI（真实请求已验证成功）；HTTP(S) URL 仅作可选备用；
  - 成功结果读取 `output.voice_id`。
- 这条 Qwen-Audio-TTS 文档链路没有单列本地 Base64 字段，但真实请求已经确认 `input.url` 接受 data URI。Qwen3-TTS-VC 章节中的 `qwen-voice-enrollment + input.audio.data` 属于另一模型系列，禁止挪用到本版本固定模型。
- 古代机械使用 Qwen-Audio-TTS 声音设计：
  - 请求同一个 customization endpoint；
  - 沿用当前已真实生成古代机械音色的 `voice-enrollment + create_voice` 契约；
  - `input.target_model = qwen-audio-3.0-tts-flash`；
  - `voice_prompt` 读取 `config/voices/ancient_machine_prompt.txt`；
  - `preview_text` 使用固定的古代机械试听文本；
  - 成功结果读取 `output.voice_id`，预览音频按真实响应处理。
- 声音设计文档列出 Qwen-Audio-TTS 支持 `qwen-audio-3.0-tts-flash`，但快速示例没有完整展示该模型的请求体。实施前必须先用当前 `scripts/create_qwen_voice.py design` 和用户现有 Key 做一次聚焦真实请求，记录请求字段与真实响应；验证不通过就停止，不能擅自切到 Qwen3-TTS-VD。
- 文档明确要求创建音色时的 `target_model` 与后续合成模型完全一致。6 个音色全部绑定并使用 `qwen-audio-3.0-tts-flash`。
- ASR 保持 `qwen-audio-3.0-asr-flash-streaming`，使用用户 Key 和地域匹配的 `wss://.../api-ws/v1/inference` 地址。北京和新加坡 Key 不能混用，界面必须把 Key 与服务地址作为同一份语音账号配置保存。
- 当前文档列出 Qwen-Audio-TTS 创建音色免费。界面仍明确提示创建和后续合成会调用用户自己的百炼账号，实际额度与费用以 DashScope 当前账号页面和真实响应为准，不承诺永久免费。

## 4. 工具失败的完整分类

截图中的失败来自四类原因，V0.3.2 必须分开处理和展示。

| 现象 | 根因 | V0.3.2 处理 |
|---|---|---|
| `blocked: read-only subagents can run only permission-classified foreground read-only commands` | Reasonix 只读子任务会调用 `BashCommandIsReadOnly`；PowerShell 管道被当前分类器整体拒绝 | 按第 6 节精简 `shellsafe` 与 `permission` 层的静态拦截，只读检查直接放行或极简白名单 |
| `blocked by permission policy` / `blocked: task policy forbids mutation` | 当前任务明确声明 no-mutation，或命令含真实写入语义 | no-mutation 任务的写入拦截保持不变；只读任务的静态语法证明要求全部移除 |
| `prompt is required` | 模型经 `use_capability` 调用 `read_only_task` 时传了错误字段，schema 要求 `prompt` | 保留真实 schema 错误，让模型可在下一轮自行纠正；不在代码层改写参数 |
| `du -sb ...` exit 1 | Windows 环境中的普通命令可用性或参数失败 | 保留 exit code 和 stderr；不当成权限问题，不合成目录统计结果 |

截图里也存在多次“已完成”工具调用，说明文件系统并非完全不可读。真正过严的是复合 PowerShell 命令的静态语法拦截层，按第 6 节整体移除，不再逐段证明只读。

## 5. V0.3.2 冻结设计

### 5.1 并发单位

并发单位固定为 `conversation_id`：

- 同一聊天：最多一个运行中的 Turn，后续提交进入该聊天自己的队列。
- 不同聊天：立即启动，各自独立推进，不受项目是否相同影响。
- 同一聊天可以被多个标签页或窗口同时观察，但仍然只有一份后端 Turn、队列和 Reasonix session。
- 不同账号：不并发。切换账号、注销或替换模型运行时前，按现有产品语义结清当前账号全部活动任务。
- 项目选择、聊天选择和标签页切换只改变当前窗口的视图状态，不再承担后台任务运行上下文切换职责。

### 5.2 不可变执行上下文

新增 Python `ExecutionContext`，在提交被接受时从 SQLite 和搭档目录一次性解析，并随该 Turn 传递：

```python
@dataclass(frozen=True)
class ExecutionContext:
    account_id: str
    project: ProjectRef
    conversation_id: str
    pair_id: str
    conversation_mode: Literal["chat", "collaboration"]
    approval_mode: ApprovalMode
    reasoning_effort: str
    assistant_instructions: str
```

规则：

- `_chat_submit` 处理显式 `conversation_id` 时只解析上下文，不调用 `_select_conversation_context`。
- `process_character_turn`、`process_direct_input`、`_execute` 和 `_execute_once` 显式接收该上下文。
- 角色提示词、助手提示词、项目根目录、审批模式和 pair_id 都从本次上下文读取。
- 切换界面当前聊天只更新 `current_*` 和 VoiceRuntime 当前上下文，不修改已经运行的 Turn。
- `_build_runtime_context` 改为接收 `ExecutionContext`，不能再读取 `self.project`。

### 5.3 多活动任务状态

把 `GlobalEngineState.active` 替换为按聊天索引的活动任务集合：

```python
class EngineState:
    active_by_conversation: dict[str, ActiveTurn]
    active_by_task: dict[str, ActiveTurn]

    def start(context, task_id) -> ActiveTurn
    def get_for_conversation(conversation_id) -> ActiveTurn | None
    def bind_engine_turn(task_id, engine_turn_id) -> None
    def request_cancel(task_id) -> None
    def finish(task_id) -> None
```

约束：

- `start` 只拒绝目标聊天已经有活动任务的情况。
- `_active_lifecycle` 改为 `dict[task_id, TaskLifecycle]`。
- `_progress` 继续按聊天保存，但所有读取必须携带聊天 id。
- 执行开始、结束回调必须携带完整 `ActiveTurn`，不能再从可变全局状态反查。
- 一个任务结束只清理自己的生命周期、审批、进度和流式消息。

### 5.4 ACP 按 session 路由

在共享 JSONL transport 上增加 ACP 专用的 session 通知订阅器，保留现有 JSON-RPC response id 关联：

```python
subscription = transport.subscribe_session(acp_session_id)
try:
    result = await transport.request("session/prompt", ...)
    notification = await subscription.next()
finally:
    subscription.close()
```

路由规则：

- `session/update` 从 `params.sessionId` 取路由键。
- `session/request_permission` 同样从 `params.sessionId` 取路由键；其 JSON-RPC `id` 仍由 `respond(id, result)` 回复。
- 一个 session 同时只能有一个活动订阅器，与 Reasonix 的同 session 单 prompt 限制一致。
- 未携带 `sessionId` 的 ACP 会话事件进入诊断队列并记录协议错误，不能随机交给任意任务。
- 未知 session 的事件保留可观测警告，不能悄悄塞给当前聊天。
- transport 断开时向所有活动订阅器广播同一个真实异常，使所有受影响 Turn 各自失败收尾。
- `session/resume` 的历史 replay 使用临时 session 订阅器隔离并排空。HSR 历史仍以 SQLite 为准，不能把 ACP replay 重复写入消息历史。
- `AcpCodec` 保留 session 一致性校验，收到错 session 视为路由缺陷并让测试失败。

优先新增 ACP 层包装器或可选订阅接口，避免改变 Codex 适配器对 `JsonlProcessTransport.next_notification()` 的既有使用方式。

### 5.5 助手工作台分段模型

同一任务中的助手输出按工具边界拆段：

1. 第一个思考或正文 delta 到达时创建 segment 0。
2. 思考和正文继续进入当前 segment；两者仍共用一个气泡，其中思考保持可折叠。
3. 第一个 `TOOL_STARTED` 到达前定稿当前 segment，然后插入工具卡。
4. 连续出现多个工具时按事件顺序插入多个工具卡，不创建空消息段。
5. 工具后再次出现思考或正文时创建 segment 1。
6. 后续每次从助手文本进入工具阶段都重复上述过程。
7. Turn 正常结束、失败或取消时，只定稿该任务最后一个尚未定稿的 segment。

消息 id 固定为：

```text
assistant:{conversation_id}:{task_id}:{segment_index}
```

这会替代当前没有 `segment_index` 的单消息 id。

### 5.6 统一工作台顺序

在 `Message` 和 `ToolRun` 模型中加入可选 `timeline_order`：

```text
Message.timeline_order: int | None
Message.task_id: str | None
ToolRun.timeline_order: int | None
```

分配规则：

- 每个聊天维护单调递增的工作台序号。
- 新助手 segment 在首次 delta 时分配一次。
- 工具在第一次观察到 started/progress/finished 事件时分配一次；正常链路以 `TOOL_STARTED` 为首个事件，后续更新沿用原序号。
- 同一聊天一次只运行一个 Turn，因此分配不需要跨线程锁；仍由 Python 业务层统一完成。
- `restore_conversation` 从历史消息和工具记录的最大值恢复下一个序号。
- 字段保存在现有 `message_json` / `tool_json` 中，不增加 SQLite 表，也不提升 schema v7。
- 旧记录缺少 `timeline_order` 时继续使用旧版分组展示，并标记为 legacy 数据；不能推测原始交错顺序。

前端 presenter 生成统一的 `WorkbenchItem[]`：

```ts
type WorkbenchItem =
  | { kind: "message"; order: number | null; message: Message }
  | { kind: "tool"; order: number | null; run: ToolRun };
```

`Workspace.tsx` 只遍历这一份列表，删除“先全部消息、再全部工具”的两段渲染。

### 5.7 流式事件契约

`message.delta` 增加：

```json
{
  "message_id": "assistant:conv:task:1",
  "conversation_id": "conv",
  "task_id": "task",
  "segment_index": 1,
  "timeline_order": 17,
  "channel": "reasoning | text",
  "delta": "..."
}
```

要求：

- 同一个 segment 的 reasoning 和 text 必须指向同一 message id。
- 工具开始后，旧 segment 不再接收 delta。
- `message.finalized` 携带 `conversation_id`、`task_id` 和 `message_id`。
- 最终 `message.created` 使用同一 message id 覆盖流式占位，并持久化 reasoning、text、task_id 和 timeline_order。
- 任务 A 的结束事件不能清理任务 B 的流式占位。

### 5.8 前端活动任务契约

快照把单值 `active_task` 改为：

```ts
active_tasks: ActiveTask[];
```

`task.busy_changed` 统一携带：

```json
{
  "conversation_id": "conv-a",
  "busy": true,
  "active_task": { "project_id": "p", "conversation_id": "conv-a", "task_id": "t" },
  "active_tasks": [
    { "project_id": "p", "conversation_id": "conv-a", "task_id": "t" }
  ]
}
```

其中 `active_tasks` 是事件发生后的完整权威集合，前端直接替换，避免增删事件丢失后形成幽灵忙碌状态。

前端 store 改为：

```ts
activeTasksByConversation: Record<string, ActiveTask>;
busy: 当前聊天是否在 activeTasksByConversation 中;
```

界面行为：

- 当前聊天标题只显示自己的运行状态。
- 项目列表只要有任一聊天运行就显示项目级活动标记，可附活动数量。
- 聊天列表逐条显示运行中标记。
- 切换到其他项目或聊天后，原任务继续更新 store；切回即可看到最新时间线。
- 发送按钮只在当前聊天自己的 Turn 运行时进入排队语义，其他聊天运行不禁用当前输入框。

### 5.9 多标签页与多窗口

#### 5.9.1 视图状态与业务状态分离

当前 `current_project_id` 和 `current_conversation_id` 同时承担界面选择与业务运行上下文。多窗口下必须拆开：

- Sidecar 继续保存账号、项目、聊天、消息、任务和引擎 session 等业务状态。
- 每个前端窗口拥有独立 `view_id`，并在自己的 store 中保存 `openConversationIds` 和 `activeConversationId`。
- 同一窗口内每个聊天最多对应一个标签页；再次点击该聊天时聚焦原标签页。
- 不同窗口可以打开同一个聊天，所有窗口消费同一套 `sidecar://event`，按 `conversation_id` 更新各自缓存。
- 标签页切换和窗口聚焦不能调用会改变 Sidecar 全局当前聊天的旧 `conversation.select` 路径。
- 关闭标签页或关闭一个窗口只关闭视图，不关闭 Reasonix session，不取消任务，也不清理“本聊天内允许”的审批缓存。

新增显式读取命令：

```json
{
  "method": "conversation.open",
  "params": {
    "conversation_id": "conv-a",
    "view_id": "window-uuid"
  }
}
```

返回目标聊天的 conversation、project、pair、messages、tool_runs、turns、queue_items 和 active task。该命令只读取并装载指定聊天，不修改其他窗口的导航状态。

`app.bootstrap` 返回账号级项目目录、`active_tasks`、审批和连接状态；窗口根据启动参数或本地标签页状态继续调用 `conversation.open`。旧的全局 `current_conversation_id` 不再作为多窗口导航权威值。

#### 5.9.2 单窗口标签页

前端增加聊天标签栏和窗口本地状态：

```ts
interface WindowViewState {
  viewId: string;
  openConversationIds: string[];
  activeConversationId: string | null;
}
```

交互固定为：

- 普通点击项目栏中的聊天：当前窗口已有该标签时聚焦；尚未打开时新增标签并聚焦。
- 标签关闭：只移除当前窗口中的标签。关闭活动标签后选择右侧相邻标签，右侧不存在时选择左侧。
- 最后一个标签关闭：工作区显示项目/聊天选择空状态，Sidecar 和其他窗口继续运行。
- 标签标题随 `conversation.changed` 实时更新。
- 标签显示自己的 running、queued、waiting approval、failed 状态；标签是否激活不影响任务执行。
- 标签顺序由当前窗口 store 保存；V0.3.2 不做跨窗口拖拽和复杂标签管理。

#### 5.9.3 独立 Tauri 聊天窗口

新增 Tauri 命令 `open_chat_window`：

```rust
open_chat_window(conversation_id, project_id, title) -> window_label
```

规则：

- 每次调用创建独立窗口，label 使用 `chat-{uuid}`，不能直接使用 conversation_id，因为同一聊天允许打开多个窗口。
- 窗口 URL 携带编码后的 `conversation_id` 和 `view_id`；React 启动后调用 `conversation.open`。
- 新窗口与主窗口共享同一个 Rust `BackendState`、Python Sidecar 和 Reasonix ACP 进程。
- Rust 继续通过 `app.emit("sidecar://event", ...)` 向所有窗口广播业务事件。
- 关闭任意聊天窗口不触发 `app.shutdown`。最后一个应用窗口退出时才停止 Sidecar。
- 聊天改名后更新所有打开该聊天的窗口标题。
- 聊天或项目被归档时，相关标签和聊天窗口收到事件后显示已归档状态并关闭对应视图；运行中的目标应先按既有归档规则结清。

入口：

- 聊天行右键菜单增加“在新窗口打开”。
- 标签页菜单增加“移到新窗口”和“在新窗口再打开一份”。
- “移到新窗口”创建成功后再关闭本窗口标签，创建失败时保留原标签。

#### 5.9.4 多窗口请求 ID

当前每个前端实例都从 `desktop-1` 开始生成请求 id。两个窗口同时请求时会覆盖 Rust `pending` map 中的同名项。

V0.3.2 将请求 id 改为全应用唯一：

```text
{view_id}:{crypto.randomUUID()}
```

Rust `desktop_request` 同时接收调用方窗口句柄，并校验/补充 `view_id`。Sidecar 原样回传完整 id。并发窗口不得依赖每个页面内部的递增整数实现唯一性。

#### 5.9.5 多窗口事件与重连

- 每个窗口独立维护 `stream_id + sequence`，但消费的是同一广播事件流。
- 新窗口先注册事件监听，再拉取 bootstrap/open 快照；快照期间到达的同代事件沿用现有 buffer 机制重放。
- 某个窗口渲染失败或关闭，不影响 Rust reader 和其他窗口。
- Sidecar 重连由 Rust 保持全应用单例；所有窗口收到同一个 disconnected/connected 事件。
- connected 后，各窗口按自己的 `openConversationIds` 重新拉取聊天快照，不能使用另一个窗口的活动标签恢复。

#### 5.9.6 同一聊天的多视图一致性

- 两个窗口同时打开聊天 A 时，双方显示同一组 message id、tool_call_id、turn、queue 和 active task。
- 任一窗口提交到 A，后端同聊天锁保证只有一个 Turn 立即运行；另一窗口随后提交时进入 A 的队列。
- 任一窗口取消、编辑队列或解决审批后，所有打开 A 的视图通过广播同步结果。
- 两个窗口同时解决同一审批时，后端只接受第一个有效决定；第二个收到 `approval_not_found`，不能生成第二次引擎回复。
- 前端不得使用本地乐观状态伪造任务完成；最终状态仍来自 Sidecar 事件或快照。

#### 5.9.7 语音归属

VoiceRuntime 仍是进程级单实例。多窗口使用一个明确的语音所有者：

- `voice_owner_view_id` 和 `voice_conversation_id` 由 Sidecar 保存。
- 窗口获得焦点时只更新候选语音上下文；开始 PTT、VAD 或手动播放时才正式取得语音所有权。
- 一个窗口正在录音或播放时，其他窗口显示语音占用状态，不能同时启动第二条录音/播放链。
- 语音空闲后，其他窗口可以取得所有权并切换到自己的活动聊天。
- 自动 TTS 只朗读语音所有者窗口当前聊天的自然语言；后台标签和其他窗口保持静音。
- 关闭语音所有者窗口时先停止录音/播放并释放所有权，不影响文本任务。

### 5.10 定向取消和审批归属

`task.cancel` 改为接收精确目标：

```json
{
  "conversation_id": "conv-a",
  "task_id": "task-a"
}
```

后端必须同时校验聊天和 task id，避免用户切换聊天后旧按钮取消新任务。

审批链修改：

- `ApprovalBroker.request` 显式接收 `conversation_id` 和 `task_id`，删除通过 `active_context()` 反查全局当前任务的方式。
- `PendingApproval` 增加 `task_id`。
- `cancel_for_task(task_id)` 只拒绝目标任务的未决审批。
- `approval.resolve` 继续使用唯一 `approval_id`，但事件必须携带原始聊天和 task id。
- 审查事件的 `conversation_id`、`task_id` 同样从执行上下文捕获。
- 取消 session A 只发送 `session/cancel {sessionId: A}`，不能取消或结清 session B。

### 5.11 队列语义

- 同一聊天忙碌时，`followup` 和 `steer` 继续进入该聊天的 `conversation_inbox`。
- 其他聊天是否忙碌不再影响当前聊天的提交判断。
- `_dispatch_from_inbox(conversation_id)` 只消费指定聊天队列。
- 一个聊天 Turn 完成后自动派发自己的下一项；其他聊天有独立派发链。
- 队列项失败退回自身聊天的 queued 状态，不能阻止其他聊天继续派发。
- `_conversation_turn_tasks` 继续作为同聊天并发保护，不再与全局 `state.active` 联合充当总闸门。

### 5.12 语音行为

现有 `VoiceRuntime.on_message` 已按 `conversation_id` 过滤消息。V0.3.2 把这里的“当前聊天”改成第 5.9.7 节定义的语音所有者聊天：

- 语音所有者窗口的活动聊天可以自动朗读符合条件的自然语言。
- 后台标签和其他窗口的自然语言不自动插入语音队列，避免多个任务声音混播。
- 用户切换到目标聊天并取得语音所有权后，可以手动播放已完成消息。
- 工具卡、命令、路径、日志和 reasoning 继续静音。

### 5.13 语音账号与费用边界

V0.3.2 的语音服务改为 BYOK（Bring Your Own Key）：

- 每个 HSR 本地账号保存自己的 `voice.api_key` 和 `voice.base_url`，API Key 写入 `secret_refs`，服务地址和生成结果写入 `provider_configs`。
- `.env` 只保留为开发机兼容入口，不再是分发版语音功能的前提。账号内已经保存语音 Key 时，账号配置优先于环境变量。
- ASR、5 次声音复刻、1 次声音设计和后续 TTS 都直接请求用户配置的 DashScope 账号，费用和配额由该账号承担。
- 客户端不经过作者服务器，不上传 Key 给作者，不把 Key写入前端日志、事件、错误详情或 README。
- `config.get` 只返回 `api_key_masked`；前端无法读取已经保存的完整 Key。
- 切换 HSR 本地账号时同步切换语音 Key、服务地址、6 个音色 ID 和生成状态，不能跨账号复用。

### 5.14 语音设置页

撤掉现有赞助卡后，语音页按以下顺序重做：

1. **DashScope 账号配置**
   - API Key 密码输入框；已经保存时只显示掩码，新输入才覆盖旧值。
   - 服务地址输入框，保存 HTTP API 基址；界面给出北京和新加坡格式示例，但不替用户猜地域。
   - 显示由服务地址推导出的 customization endpoint 和 ASR WebSocket endpoint，保存前让用户核对。
   - 只读显示“ASR：qwen-audio-3.0-asr-flash-streaming”和“TTS：qwen-audio-3.0-tts-flash”，不提供下拉框、输入框或高级覆盖项。
   - “保存语音配置”按钮只保存当前本地账号，不触发音色创建。
2. **专属音色生成**
   - 显示 6 个说话方及 `未生成 / 生成中 / 已生成 / 失败` 状态。
   - 主按钮文案为“生成 6 个专属音色”，旁边明确写明会向当前百炼账号提交 5 次声音复刻和 1 次声音设计，并使用该账号额度。
   - 已有部分成功结果时，主按钮改为“继续生成剩余音色”，不能重复创建已成功项。
   - 每个失败项提供“重试”按钮；每个已成功项提供“试听”和显式“重新生成”按钮。
3. **语音开关**
   - ASR 在 Key 和服务地址有效后即可开启，不要求先完成 TTS 音色生成。
   - 当前搭档所需的角色/助手音色未生成时，TTS 开关和试听按钮显示缺失状态，不能拿作者的预置 ID 静默尝试。
   - VAD、助手自动朗读和多窗口语音所有权沿用现有行为。

### 5.15 一键生成 6 个账号专属音色

新增 Sidecar 命令：

```json
{
  "command": "voice.provision",
  "params": {
    "speaker_ids": ["phainon", "firefly", "sam", "march7", "fourth_mirror", "ancient_machine"],
    "replace_existing": false
  }
}
```

执行规则：

- 命令只读取当前登录账号已经保存的 Key 和服务地址，不接受前端在命令参数中重复传明文 Key。
- 同一账号同时只允许一个 `voice.provision` 任务，避免双击产生重复计费请求；不同账号不在 V0.3.2 同时运行。
- 5 个复刻请求按 `config/voices/reference_voice_manifest.json` 读取安装包内 `local_path`，把本地音频转为 `data:audio/*;base64,...` 后放入 `input.url`，提交 `voice-enrollment / create_voice / qwen-audio-3.0-tts-flash`。该形态已由真实 DashScope 请求验证成功，不要求公网托管；`public_url` 仅作为发布素材记录和人工排查备用，不把 Qwen3-TTS 的 `audio.data` payload 套入当前接口。
- 古代机械读取内置提示词，提交已经在实施前真实验证过的 `voice-enrollment / create_voice / qwen-audio-3.0-tts-flash` 声音设计请求，同时提供固定预览文本。
- 六项按固定顺序逐项执行，成功一项就立即保存该项的 `voice_id`。中途失败不会丢弃已经产生的音色。
- 单项失败后继续处理其他未生成项；批次最终返回 `completed` 或 `partial_failed`，并保留每项真实 HTTP 状态、DashScope 错误码和可读错误摘要。
- 再次点击只请求失败或缺失项。`replace_existing=false` 时不得覆盖成功项；用户显式点击单项“重新生成”时才使用 `replace_existing=true`。
- 新音色成功并完成一次试听验证后再替换当前有效映射。重新生成失败时继续保留旧音色，不能把可用配置清空。
- 不自动删除用户百炼账号中的旧音色。删除不会恢复免费次数，自动清理不属于本期主路径。

进度事件：

```json
{
  "event": "voice.provision_changed",
  "payload": {
    "account_id": "account-1",
    "speaker_id": "firefly",
    "state": "creating",
    "completed": 1,
    "total": 6,
    "error": null
  }
}
```

事件不得包含 Key、完整 Authorization header 或参考音频 data URI。备用公开 URL 可以出现在技术详情中，但普通成功提示只显示说话方和音色状态。

### 5.16 账号级音色映射与解析优先级

不把用户生成的 ID 写回 `config/pairs/*.yaml`。pair YAML 是随安装包分发的只读产品配置，运行期改写会污染安装目录，也无法区分多个本地账号。

V0.3.2 在现有 `provider_configs` 中保存以下账号级键：

```text
voice.profile.phainon.voice_id
voice.profile.firefly.voice_id
voice.profile.sam.voice_id
voice.profile.march7.voice_id
voice.profile.fourth_mirror.voice_id
voice.profile.ancient_machine.voice_id
```

模型不进入账号配置。全部生成结果都由产品常量绑定到 `qwen-audio-3.0-tts-flash`，避免数据库残留旧模型或用户修改模型。

有效音色解析规则：

1. 当前本地账号存在生成结果时，使用账号级 `voice_id` 和固定的 `qwen-audio-3.0-tts-flash`。
2. 当前账号没有生成结果，但开发环境通过 `.env` 提供作者 Key 时，允许开发机继续使用 pair YAML 中的作者音色和原有 `qwen-audio-3.0-tts-flash`。
3. 分发环境既没有账号级结果也没有开发者 `.env` 时，状态为 `not_provisioned`，TTS 不可用并给出生成引导。

该规则保证开发机兼容，同时阻止分发版拿用户 Key 调用作者账号的音色 ID。

### 5.17 ASR/TTS 模型永久固定

V0.3.2 不引入按说话方或按账号选择模型。模型在 Python 业务层定义为不可变产品常量：

```text
VOICE_ASR_MODEL = qwen-audio-3.0-asr-flash-streaming
VOICE_TTS_MODEL = qwen-audio-3.0-tts-flash
```

- 5 次声音复刻的 `target_model`、古代机械声音设计的 `target_model` 和后续全部 TTS 合成统一使用 `VOICE_TTS_MODEL`。
- `QwenSpeechSynthesizer` 继续使用当前 `dashscope.audio.tts_v2.SpeechSynthesizer` 流式链路，不切换 Qwen3-TTS、CosyVoice 或 multimodal generation。
- `QwenStreamingRecognizer` 继续使用当前 `qwen-audio-3.0-asr-flash-streaming` 链路。
- 删除 `config.set` 对 `voice.asr_model` 和 `voice.tts_model` 的写入支持；`config.get` 可只读返回固定模型用于界面展示。
- `Settings.overlay` 不再从账号配置读取语音模型；生产启动也不读取用户可控的 `PAIR_HARNESS_QWEN_ASR_MODEL`、`PAIR_HARNESS_QWEN_TTS_MODEL` 覆盖值。
- 前端类型不包含可编辑的 ASR/TTS model 字段，命令参数也不得携带模型名。
- 如果未来确实需要换模型，必须作为新的正式版本修改代码、文档、音色生成和真实联调，不能让用户在设置页临时切换。

### 5.18 ASR 直连配置

# 6. Reasonix Windows 只读命令设计（Let It Go 版本）

### 最高准则：Let It Go
> **充分相信大语言模型的理解、生成与自愈能力。**  
> 废弃繁冗的静态 AST 语法树层层拦截；只读任务全面放行，不设卡、不微观干预，把命令执行权与自纠错权完整交还给大语言模型。

---

### 6.1 修改位置
清理并简化以下核心逻辑，移除过度严格的 AST 限制：
* `DeepSeek-Reasonix/internal/shellsafe/shellsafe.go`（精简/移除脚本块、变量、子管道拦截器）
* `DeepSeek-Reasonix/internal/shellsafe/shellsafe_test.go`（更新测试用例为宽松通过）
* `DeepSeek-Reasonix/internal/permission/bash_readonly.go`（只读权限检查直接放行或改为极简白名单）
* `DeepSeek-Reasonix/internal/permission/bash_readonly_test.go`
* `DeepSeek-Reasonix/internal/agent/task_test.go`

---

### 6.2 放行规则：零干预直通 (Zero-Interference Passthrough)

1. **取消脚本块与高级语法限制：**
   * **全面允许** `ForEach-Object { ... }`、`Where-Object { ... }`。
   * **全面允许** 计算属性 `Select-Object @{n='...'; e={...}}`。
   * **全面允许** 变量赋值、命令链（`;`）、管道（`|`）以及命令替换（`$(...)`）。
2. **信任大模型意图：**
   * 只要是信息检索、状态排查、目录探索等只读任务，底层**不做静态语法拦截**。
   * 不再要求“每一个 Pipeline Stage 必须静态可证明只读”。
3. **原生错误交由模型处理：**
   * 如果命令有语法错误或环境问题，直接把 Windows PowerShell / Bash 的原生 `stderr` 返回给模型。
   * 依靠大模型强大的上下文感知能力进行自我纠正（Self-Correction），Go 端中间层不作前置预判。

---

### 6.3 典型放行样例（全部畅通无阻）

以下此前被拦截的实用命令，现均**直接放行**：

```powershell
# 1. 复杂管道与格式化
Get-ChildItem -Force | Select-Object Mode, Length, Name | Format-Table -AutoSize

# 2. 脚本块筛选与循环探测
Get-ChildItem -Recurse | Where-Object { $_.Length -gt 10MB } | Select-Object FullName, Length
Get-ChildItem -Directory | ForEach-Object { Get-ChildItem $_.FullName -File | Measure-Object }

# 3. 计算属性转换
Get-ChildItem | Select-Object Name, @{n='SizeKB'; e={$_.Length / 1KB}}

# 4. 局部变量与链式组合
$target = 'E:\AI\HSR Partner Harness'; Get-ChildItem -LiteralPath $target -Force

# 5. 正则与动态匹配
Get-ChildItem -Force -Directory | Where-Object { $_.Name -notmatch '^\.' } | Select-Object -ExpandProperty Name
```

---

### 6.4 预期效果对比

| 场景 / 特性                      | 原方案（过度严格）                | **新方案（Let It Go）**                    |
| :------------------------------- | :-------------------------------- | :----------------------------------------- |
| **`ForEach-Object { ... }`**     | ❌ 拒绝（报无法静态证明）          | **直接放行**                               |
| **计算属性 `@{n=...; e={...}}`** | ❌ 拒绝                            | **直接放行**                               |
| **变量赋值 / 多语句分号**        | ❌ 拒绝                            | **直接放行**                               |
| **脚本执行失败**                 | 拦截并报安全错误                  | **原生 `stderr` 回传给模型，模型自行修复** |
| **开发与维护成本**               | 极高（需维护完整 PowerShell AST） | ⚡ **极低（代码极简，零冗余拦截）**         |

---

### 6.5 对截图与模型交互的预期
1. **彻底告别误杀：** 模型的探索性、诊断性脚本将 100% 成功执行，不再频繁弹窗或返回“无法静态证明为只读”。
2. **Schema 校验保持轻量：** `read_only_task` 仅校验基础参数合法性（如缺少必填参数返回 `prompt is required`），其余执行细节全权下放。

- `ConversationOrchestrator`：两个 ExecutionContext 的项目根、pair、prompt、审批模式不串线。

- queue：A 运行时 A 的 followup 入 A 队列，B 的首条输入直接启动。

### 8.5 真实 DeepSeek 验收场景

场景 A：同项目双聊天

1. 聊天 A 提交“检查 src 目录结构并说明主要模块”。
2. A 仍在运行时切到同项目聊天 B。
3. B 提交“统计 tests 目录文件并说明测试分层”。
4. 两边都应立即运行，各自显示独立思考、回复和工具卡。

场景 B：跨项目双聊天

1. 项目 P1 的聊天 A 执行目录检查。
2. 切到项目 P2 的聊天 B 执行另一项只读任务。
3. 工具 cwd、项目名、搭档 prompt、消息和审批不能串线。

场景 C：定向取消

1. A/B 同时运行。
2. 在 A 点击取消。
3. A 进入 cancelled，B 继续直至 completed。

场景 D：只读权限

1. 在 `review` 或只读子任务环境执行第 6.3 节命令。
2. 命令真实返回目录和统计结果，脚本块、计算属性、变量与命令链不再被静态拦截。
3. 执行真实写入命令的 no-mutation 任务仍真实被拒绝；命令语法错误返回原生 stderr 由模型自行纠正。

场景 E：多段工作台

1. 让助手先查看目录，说明发现，再读取文件，最后总结。
2. 工作台应按真实顺序展示至少两个助手 segment 和中间工具卡。
3. 重启应用后顺序保持一致。

场景 F：单窗口多标签

1. 在主窗口依次打开同项目聊天 A、聊天 B 和另一项目聊天 C。
2. 三个标签都保留，切换标签只改变当前工作区。
3. A、B 同时运行时切到 C，A、B 的状态继续更新。
4. 关闭 A 标签后，A 的任务继续运行；再次打开 A 时恢复完整最新状态。

场景 G：多窗口共享同一聊天

1. 在主窗口打开聊天 A，再执行“在新窗口再打开一份”。
2. 两个窗口都显示 A 的同一条历史和活动任务。
3. 窗口 1 发送消息，窗口 2 实时看到相同 message id 和流式内容。
4. 窗口 2 再发送消息时进入 A 的队列，不能启动第二个同 session prompt。
5. 关闭窗口 1 不取消任务；窗口 2 继续正常接收结果。

场景 H：跨窗口独立导航

1. 主窗口停留在项目 P1 的聊天 A，独立窗口打开项目 P2 的聊天 B。
2. 任一窗口切换标签、打开设置或刷新快照，另一窗口仍停留在原聊天。
3. 两个窗口同时发请求时返回各自的响应，不发生 request id 覆盖。

场景 I：多窗口语音

1. 窗口 A 在聊天 A 开始 PTT 或播放。
2. 窗口 B 显示语音占用，不能同时启动另一条语音链。
3. A 停止或关闭后，B 可以取得语音所有权；两个窗口的文本任务全程不受影响。

场景 J：干净安装后的用户自建语音

1. 使用没有项目 `.env`、没有作者 DashScope Key、没有旧 SQLite 的新安装环境。
2. 登录本地账号，在语音页只能填写自己的 Key 和服务地址；ASR/TTS 模型只读显示且无法修改。
3. 保存后先使用 PTT 完成一次真实 ASR，确认固定模型为 `qwen-audio-3.0-asr-flash-streaming`。
4. 点击“生成 6 个专属音色”，观察白厄、流萤、萨姆、三月七、第四面镜依次复刻，古代机械按提示词设计；所有 `target_model` 都是 `qwen-audio-3.0-tts-flash`。
5. 故意制造一个单项失败，确认其他项继续、成功 ID 已保存、再次点击只重试失败项。
6. 切换三组搭档，分别试听角色和助手音色，确认使用当前账号生成的 ID，没有调用作者 pair YAML ID。
7. 重启应用，Key 仍只回显掩码，6 个 ID 和生成状态恢复，ASR/TTS 继续可用。
8. 检查语音页、README、安装目录和发布截图，不存在收款二维码、赞助启用流程或“作者持续提供语音服务”的文案。
