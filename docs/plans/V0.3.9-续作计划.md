## 1. 为什么改组

旧模式是产品经理（GPT 6 Astra）→ 逻辑/视觉主管 → 8 名工程师的三层嵌套双轨制，执行中失控：4 名 DeepSeek 工程师集体失败退出后改由 Gemini 接手，视觉主管两次失败重建，台账从未回写实现提交，docs 提交夹带代码改动，4 个工程师分支的内容被以不同 SHA 重新提交进集成分支而原分支从未合并。自 2026-09-10 起改为单轨。

## 2. 团队与调度规则

- 根代理：Kimi K3，唯一指挥，直接派发全部子代理，负责集成、冲突裁决与提交收口。
- 子代理：一律 `deepseek/deepseek-v4-flash-vision-exp`，扁平结构，禁止嵌套（子代理不得再派生子代理）。
- Token 策略：根代理省 token——不逐字读大文件与长日志，只读子代理的紧凑报告；子代理不省 token，按任务需要充分阅读与验证。
- 单轨：唯一工作分支 `feat/v0.3.9-logic`（worktree `E:\AI\HSR-Partner-Harness-v0.3.9-logic`），不再分逻辑/视觉双轨；视觉分支成果一次性并入后收尾。
- 写入同一 worktree 的子代理任务串行执行；只读核对可并行；彼此独立的任务用 AgentSwarm 批量并行。
- 每份委派写明：目标、基线提交、工作目录、允许修改的文件、验收命令、回报格式。提交只 `git add` 明确路径，禁用 `git add -A`。
- 纪律沿用仓库最高准则 Let It Fail / Let It Go：不吞异常、不伪造成功、mock 只证明离线协议、不用关键词或正则猜测模型意图。
