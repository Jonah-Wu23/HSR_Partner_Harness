> 状态：计划已编制，待进入 S0/S1 实施准备。已汇总两侧主管调查；桌面视觉细项仍需 S0 补查。本轮仅编写计划，不代表实现或真实验收已经完成。

## 1. 版本目标与范围

V0.3.9 完成上下文、长期记忆、多聊天并发、诊断与性能收敛，并完成手机远程全矩阵真实验收，将主功能推进到 V0.4.0 发布候选状态。V0.4.0 的正式发布、NSIS 安装包及完整升级发布验收仍按路线图另行执行。

本版必须覆盖以下工作：

1. 核对目标上下文、最后活跃聊天、消息落库顺序、聊天运行代际与后台任务归属。
2. 验证至少两个项目、每个项目至少两个聊天同时运行，队列、取消、审批、工具事件、失败和完成状态互相隔离。
3. 建立持久化对话投影与结构化压缩摘要；压缩后按权威配置重新装配角色、世界书、HSR 扩展及单一助手 Markdown。
4. 明确配对级长期记忆与聊天级摘要边界，避免跨角色、跨项目、跨聊天误共享。
5. 收敛消息、事件和状态的增量批量落库，降低 SQLite 与前端渲染压力。
6. 提供 turn_metrics 或等价指标，以及显式打开的提示词装配诊断视图。隐藏提示不得混入普通对话。
7. 真实验证 DeepSeek/Reasonix 的角色委派、助手多轮工具循环，以及 Codex app-server 的真实事件链路。
8. 完成桌面多任务、长对话、记忆、压缩反馈及移动端弱网、小屏、长列表体验。
9. 对齐桌面语音抢占；回收失联远程设备控制权；将移动 PCM 缓冲溢出报告为真实失败；广播审批超时终态。
10. 完成 Android 浏览器、iOS Safari/PWA、Android 壳的网络、语音、并发、安全、通知及电源真实验收，修复发现的问题。

角色卡、酒馆兼容、世界书、语音与远程 P0/P1/P2 以现有实现为基础回归。发现真实缺陷时纳入本版修复，不重复建设已经完成的能力，不引入与交付无关的架构重写。Python 继续作为业务状态权威，Rust 负责桌面能力与 Sidecar 启动，React 消费真实协议。

每个子代理的思考强度由直接父级决定。产品经理决定两位主管的强度，主管决定每位工程师的强度。创建时查询真实 provider/model 与支持的 reasoning_effort，显式填写可用值；高复杂度契约、并发、审查任务优先选择较高强度，边界明确的组件任务可降低。模型不可用时如实报告，不静默换成另一模型，也不把启动失败写成团队已完成工作。

## 3. 分支和独立 worktree

开工先记录当前目录、分支、工作树状态、V0.3.8 基线提交与已有 worktree。保护用户未提交文件。本轮编计划时已观察到 `AGENTS.md` 有用户本地改动，不纳入计划提交。

逻辑主管从确认后的 main 基线新建 `feat/v0.3.9-logic`，在逻辑工作目录工作。视觉主管在逻辑契约冻结提交上建立 `feat/v0.3.9-visual`，使用独立目录，例如同级的 `../HSR-Partner-Harness-v0.3.9-visual`。视觉轨独立安装依赖、运行检查；不得把主工作目录伪装成视觉 worktree。以下为开工时执行的示例，当前计划编写阶段不执行：

```powershell
# 已核对基线、保存用户工作，并处于可切换的逻辑工作目录
git switch -c feat/v0.3.9-logic <confirmed-main-sha>
# 逻辑主管完成并提交冻结契约，得到 <contract-sha>
git worktree add -b feat/v0.3.9-visual ../HSR-Partner-Harness-v0.3.9-visual <contract-sha>
```

两轨交付后，逻辑主管先核对双方提交、单轨检查结果、共享文件、协议和语义冲突，再在逻辑分支暂存视觉合并结果，完成冲突解决、最终接线、最终检查与测试，通过后创建合并提交。最终得到的 `feat/v0.3.9-logic` 同时包含两轨成果，始终独立于 main。实际合并提交后核对工作树与测试对象一致，并验证最终组合产物，不能只引用合并前单轨结果。

```powershell
git switch feat/v0.3.9-logic
git merge --no-ff --no-commit feat/v0.3.9-visual
# 逻辑主管解决冲突、完成接线并检查，再提交合并
# 对最终组合提交运行检查、测试和构建
```

视觉 worktree 不直接合入 main。真机测试、测试后修复、提交推送和 PR 均围绕逻辑集成分支展开，避免出现“测试一个分支、提交另一个分支”的情况。

### 6.4 工程师交付标准

每个任务包完成时，工程师向主管提交：实际修改路径及提交、对应冻结契约、完成的用例及结果、真实服务接入情况、未解决问题和下游依赖。仅完成 UI 或离线样例时明确标注“未接真实数据”；代码存在但没有真实场景证据时标注“待真实验证”。主管检查后才能把任务状态从开发完成推进到验收完成。

发生跨轨冲突时，逻辑主管检查文件冲突与语义冲突，包括同一事件被消费两次、字段默认值改变、错误转成空状态、运行归属丢失、取消后迟到事件重新激活、样例适配器遗留，以及 UI 展示的能力没有实际后端支持。视觉主管负责确认接线后的交互没有退化。

### 6.5 产品与工程决策记录

真实供应商能力需真实配置验证。假模型、mock HTTP、Scripted/Fake engine 和 mock server 只能证明离线协议行为。失败必须保留原始状态与日志；只修已观察到的根因，不用关键词、正则或历史文本猜测模型委派意图，不合成工具执行或成功回执。

## 9. 提交、PR、CI 与唯一一次 Codex 审查

1. 真机测试结束、问题修复和复验完成后，逻辑主管整理集成分支的提交，只暂存本次明确路径，检查没有用户本地文件、密钥和测试私有数据。
2. 推送 `feat/v0.3.9-logic`，创建指向 main 的 PR。PR 写清范围、两轨来源、冻结契约、自动测试、真机矩阵、全部问题及修复证据。
3. 观测 PR 的 CI。任何失败先读实际日志、定位根因、修复并推送，再观察新提交的 CI，直到全部通过；不得靠跳过必要检查伪造绿色状态。
4. 按用户规定的外部审查流程，CI 全过后接收唯一一次 Codex for GitHub 消息。当前仓库 YAML 没有 Codex review 作业，不能宣称 CI 工作流本身保证消息到达；按项目实际 GitHub App/触发方式处理首次审查，保留其链接。完整读取该次 review、总评和所有行内建议，建立逐条清单，避免只读取阻断项。
5. 所有建议无论是否阻断、优先级高低、是否属于样式或改进，都必须修复。优先级只决定顺序，不决定是否处理。主管分派给对应轨工程师，逻辑主管检查组合影响。含糊建议先核对上下文并给出实际改进；不能用“非阻断”“留待以后”关闭。
6. 对每条建议记录原评论链接、问题、处理方式、变更文件、修复提交和验证结果。重复建议可由同一修复覆盖，但逐条关联证据；不能只回复“已修复”而没有对应工作。
7. 推送所有审查修复，运行相关回归并观测修复后提交的 CI。影响真机行为的改动补做独立复验批次，依然遵守只测不修。
8. 全部建议落实、必要回归完成、当前提交 CI 全过后即可合并 PR，无需请求或等待第二次 Codex。首次消息尚未到达不能假定“没有建议”；第二次消息不作为任何完成条件。
