## F-01 打包版首次运行恒为演示模式，界面配置无法切到真实模型（P1）

**现象**：全新安装状态启动 EXE，在首次引导里保存真实 DeepSeek Key，「保存并测试」返回连接正常并推进到第 3 步，但随后对话返回的是脚本化固定文本。

**复现**：删除 `%LOCALAPPDATA%\PairHarness` 后启动候选 EXE → 注册账号 → 引导第 2 步填入真实 Key → 保存并测试（通过）→ 第 3 步开始使用 → 发一条消息。

**预期**：配置生效后角色由真实模型生成回复。
**实际**：落库回复为 `我听着呢。先在这里陪你把这件事慢慢说清楚。`，会话标题为 `关于你好，今天过得怎么样`——两者都是 `ScriptedDialogueModel` 的固定产物，全程无对外模型请求。

**证据**：
- 进程命令行：`pair-harness-sidecar.exe --demo --serve 8765 --project ...`（`Get-CimInstance Win32_Process`）。
- 同一次会话中 `config.test_connection` 真实探测返回通过（引导推进到第 3 步），说明 Key 与服务可达。
- 落库文本与脚本化适配器常量逐字一致（`.tmp/v039-acceptance-notes.md` 与 F-01 截图）。
- 代码定位：`src/pair_harness/desktop_backend/application_service.py:5501` `candidate = None if self._demo else ...`；同文件 `:5685` `if self._demo: return`（`_rebuild_runtime_for_account` 直接返回）；`desktop/src-tauri/src/lib.rs:399` `use_real_backend` 只认 `PAIR_HARNESS_REAL` 或 `.env`，账号级配置不参与判定。
- 界面无任何演示模式标识（`desktop/src` 内无 demo 相关文案）。

**影响**：分发版用户安装后，界面里配置的任何对话供应商都不会生效，回复始终是脚本化文本；「连接正常」提示进一步让人误判链路已通。与仓库最高准则「真实失败必须暴露」直接冲突。
**严重度**：P1。**频率**：必现。**范围**：Windows 打包版（无 `.env` 时）。
**责任轨**：根/Rust 与 Python 启动判定。**修复方向建议**（不在本批次执行）：让账号级配置参与真实模式判定，或在 demo 模式下明确禁用并标注「演示数据」，不得静默接受真实 Key。

## F-02 全新安装下「默认账号」是死入口（P3）

**现象**：账号门列出「默认账号」，但「进入」按钮要求非空密码；该账号密码为空。
**复现**：全新状态启动 → 账号门选中「默认账号」→ 输入任意非空密码 → 进入 → 提示「密码错误」。
**证据**：`accounts` 表 `default-local/默认账号` 的 `password_hash` 长度为 0；`sqlite_store.py:1072` 空哈希只接受空密码；`desktop/src/ui/gate/AccountGate.tsx:88` `disabled={busy || !selectedId || !password}`。
**影响**：唯一可用路径是被迫注册新账号，「默认账号」条目无出路。**严重度**：P3（首次体验，无数据损坏）。**频率**：必现。

## F-04 `metrics.query` 响应不可序列化，30 秒超时，且同时显示「查询返回 0 条指标记录」（P2）

**现象**：打开诊断抽屉，指标区同时出现红色「指标读取失败：backend_timeout: 等待 Sidecar 响应超过 30 秒」与「查询返回 0 条指标记录。」点「刷新指标」重复同样结果。

**复现**：有真实回合记录（`turn_metrics` 7 行）时打开诊断抽屉 → 指标页。

**预期**：读取到指标；若失败则只呈现失败，不得同时给出「0 条」的结论。
**实际**：确定性 30 秒超时，且失败与「0 条」并列显示。

**根因（原始日志）**：sidecar 侧序列化失败，响应根本没写回：

```
ERROR:asyncio:Task exception was never retrieved
future: <Task finished name='Task-466' coro=<SidecarRouter.handle_line() ...>
exception=ProtocolError('协议消息不可序列化：Object of type datetime is not JSON serializable')
TypeError: Object of type datetime is not JSON serializable
  File "pair_harness\desktop_backend\protocol.py", line 20, in encode_message
  ...
  File "pair_harness\desktop_backend\router.py", line 175, in handle_line
  File "pair_harness\desktop_backend\router.py", line 124, in respond
```

`_metrics_query`（`application_service.py:4532`）返回 `metric.model_dump()`，其中 `started_at / first_event_at / completed_at` 仍是 `datetime` 对象，`protocol.encode_message` 的 `json.dumps` 直接抛错；`handle_line` 的任务异常无人取回，客户端只能等到 30 秒超时。

**界面侧的第二层问题**：`MetricsPanel.tsx:160` 先渲染错误块，随后 `metrics.length === 0` 分支无条件渲染「查询返回 0 条指标记录。」——查询失败时 `metrics` 仍是空数组，于是失败与「0 条」同时上屏，与契约「[] 才是服务端返回真实零条」相矛盾。

**证据**：`output/v039-realdevice-2026-09-10/F-06-metrics-timeout/sidecar-log-excerpt.txt`、同目录 `db-turn-metrics.txt`、`A06-diagnostics/03-metrics-timeout-full-window.png`。
**严重度**：P2（诊断功能不可用，并给出误导性零结果）。**频率**：必现。**范围**：桌面端诊断抽屉。
**修复方向建议**：`model_dump(mode="json")`（或序列化前统一 ISO 化）；失败时不得渲染空结果分支。
