## 二、你的场景与纯Coding Harness 的关键差异

「角色扮演 + Agent 工作」这个组合，和上述文档讨论的 Coding Harness 有本质不同。必须先明确：

### 2.1 角色扮演的特殊需求

1. **Persona 状态管理**：角色有情绪、记忆、关系、立场——这些是独立于任务的持久状态，不是普通 context。
2. **叙事上下文压缩**：不能用普通 token 压缩直接截断，要保留故事节拍、角色状态、世界设定。
3. **System Prompt 架构复杂**：世界观+ 角色设定 + 当前场景 + 行为约束 = 多层 prompt叠加，必须完全自己掌控。
4. **角色一致性约束**：模型在长上下文中容易漂移出角色，需要 Harness 层面主动纠偏，而不是靠模型自觉。
5. **多角色协作**：不同角色可能需要不同 persona，甚至不同模型。

### 2.2 Agent 工作的需求（与文档一致）

- Tool calling（文件读写、bash、搜索、代码执行）
- 任务规划与分解
- 状态持久化与 checkpoint
- 权限审批（人工确认门禁）
- 多Agent 编排

### 2.3 两者叠加后的核心矛盾

| 维度        | 角色扮演                  | Agent 工作                    |
| ----------- | ------------------------- | ----------------------------- |
| 目标        | 沉浸感、一致性、叙事连贯  | 任务完成率、可靠性、可审计    |
| Context策略 | 保留故事语义              | 保留任务上下文                |
| 状态        | 角色情感/关系/记忆        | 任务进度/工具日志/checkpoints |
| 中断处理    | 场景暂停，人物冻结        | 任务挂起，可恢复              |
| 工具        | 世界扩展（图像/TTS/搜索） | 执行工具（bash/git/文件）     |

这意味着你需要一个 Harness，能够**同时管理两套状态机**，并在 agent loop 里按需切换模式。任何成品 Coding Harness 都没有为此设计。

## 四、各关键层的具体实现建议

### 4.1 Persona Engine（角色一致性引擎）

这是纯 Coding Harness 没有的、你必须自己实现的核心组件。

```
Persona State：
  - 角色名称、身份、性格
  - 当前情绪状态
  - 与其他角色的关系图
  - 已知/未知的世界事件
  - 行为约束（绝对不能做的事）

角色一致性校验：
  每次模型输出后，在 Agent Loop 的 Observe 阶段插入校验：
  1. 输出是否符合角色性格？
  2. 是否泄漏了角色不应知道的信息？
  3. 行为是否触发约束？
  → 触发则重新生成或介入
```

### 4.2 Context Engine 的双压缩策略

```
叙事模式压缩（保留语义）：
  - 提取故事节拍（Story Beat）
  - 保留角色状态变化节点
  - 压缩对话为摘要，保留关键决策点
  - 世界设定始终全量保留

Agent工作模式压缩（保留任务链）：
  - 保留任务分解结构
  - 保留已完成工具调用的摘要
  - 保留当前进度 checkpoint
  - 错误历史保留（避免重复犯同一错误）
```

### 4.3 State Store 架构

```
三层记忆架构（借鉴认知科学）：

Working Memory（工作记忆）：
  - 当前场景/任务的活跃上下文
  - 存在Agent Loop 的 context buffer里
  - 每轮刷新

Episodic Memory（情节记忆）：
  - 本session 内的关键事件
  - 存在本地 SQLite / JSON
  - 用于 session 内回溯

Long-term Memory（长期记忆）：
  - 跨 session 的角色积累/世界观演化
  - 向量数据库（LanceDB 或 ChromaDB）
  - 通过语义检索按需注入context
```

### 4.4 Policy Engine（针对角色扮演 + 工作的双模式权限）

```
角色扮演模式权限：
  - 角色不得突破世界观设定
  - 某些话题需要叙事层面的过滤
  - 允许角色「不知道」某些事（信息隔离）

Agent 工作模式权限：
  - 危险命令（rm -rf,网络请求）需人工确认
  - 敏感路径只读
  - 外部 API 调用需审批

模式切换触发条件：
  - 用户明确指令（「现在帮我写代码」）
  - 任务分类器自动判断
  - Dispatch Router 路由后通知 Policy Engine 切换
```

# 一、"迁移到 Pi"的三种含义，先选对哪一种

你的问题里"迁移"是模糊的，它对应三条完全不同的路径，成本和收益差一个数量级。

### 路径 A：把 pi-coding-agent 当第三个引擎子进程

在 `adapters/pi/` 写一个 `PiCodingEngine`，通过 Pi 的 RPC 接口驱动它，和 codex/reasonix 平级。

- 改动量：一个适配器 + 一个 codec + 工厂分支 + Rust 资源发现，约 1 周。
- 收益：**很小**。你只是把"OpenAI 调好的 coding agent"换成"Pi 调好的 coding agent"，仍然继承别人的 agent loop、别人的 system prompt、别人的工具集。省下的 token 有限，多了一个 Node 运行时。
- 价值：**它是必经的验证步骤，不是终点。**

### 路径 B：基于 pi-agent-core + pi-ai 自建一个 Node Agent Host（推荐终点）

不用 pi-coding-agent，只用 Pi 的两个底层包，自己在 Node 侧写一个极薄的 agent host 进程，暴露和现在 codex/acp 一样的事件协议给 Python orchestrator。

```
Python Orchestrator（业务权威，不动）
        │  JSONL over stdio（复用 JsonlProcessTransport）
        ▼
   pi-host（你写的 Node 进程，~1500 行 TS）
        ├─ 你自己的 system prompt（薄）
        ├─ 你自己的 tool registry（只留你场景要的）
        ├─ pi-agent-core：agent loop / tool calling / state
        └─ pi-ai：Claude / GPT / DeepSeek / Gemini / 本地
```

- 改动量：新增一个 Node 子项目 + Python 适配器，约 3–4 周。
- 收益：**这才是真正的性能来源。**薄 prompt、自定义工具集、审批在你自己手里、模型自由路由。
- 风险：Node 运行时进包、你要自己维护 agent loop 的边界情况。

### 路径 C：把 Python Sidecar 整体重写成 TypeScript

不要做。你会重写 orchestrator、approval、sandbox、storage、voice、40 多个命令、全部 contract 测试，收益只是"运行时统一"。这是拿 3 个月换一个架构洁癖。

**我的建议：A 作为 Phase 1 的探路（1 周内跑通管线），B 作为真正的目标形态，C 永久搁置。**

# 二、为什么你的迁移风险其实很低

因为你在 `core/ports.py` 里已经定义了这个东西：

```

├── open_session(project, stored_ref, approval_policy, sandbox, ...)
├── run_turn(session, request) → AsyncIterator[EngineEvent]
├── cancel_turn(session, turn_id)
├── amend_turn(session, engine_turn_id, amendment)

└── native_preexecution_approval: bool
```

这个端口就是你的隔离层。只要 Pi 侧能满足这六个方法的语义，orchestrator 一行都不用改，F2 的委派闭环、F4 的审批链、F5 的会话恢复、F9 的双空间呈现全部自动继承。

**所以整个迁移的核心问题被压缩成一句话：Pi 能不能完整满足这六个方法？**

其中五个我认为没有悬念（open/run/cancel/resolve/native 标志位）。**唯一的高风险项是 `amend_turn`**——你的 F2 要求"任务执行中用户可追加新指令（立即插入优先于排队）"，也就是运行中回合的 steer。Codex app-server 原生支持这个，Pi 是否支持运行中注入用户消息，必须在写任何适配器代码之前先验证。如果不支持，你在路径 B 里可以自己实现（agent loop 每轮迭代前检查注入队列），但在路径 A 里你只能降级成"取消 + 重发"，那会破坏 F2 的验收要点。

# 四、推荐的分阶段路线

## Phase 1：Pi 作为第三引擎（1 周）

目标不是"用上 Pi"，而是**把 Node 进程进你的打包和资源发现管线这件事一次性打通**，并且拿到一组可对比的基线数据。

新增文件，完全对称于你现有的 codex 适配器：

```
src/pair_harness/adapters/pi/
├── __init__.py
├── engine.py        实现 CodingEngine
├── codec.py         Pi 事件 → EngineEvent 映射（对标 codex/codec）
└── home.py          PI_HOME 按账号隔离（对标 CODEX_HOME / REASONIX_HOME）
```

改动点：

- `desktop_backend/engine_factory.py`：`engine` 枚举加 `pi`，加 `resolve_pi_executable`（打包内置 > `PAIR_HARNESS_PI_BIN` > PATH，和现有两个引擎同一优先级规则）
- `src-tauri/main.rs`：`packaged_pi` 发现 + 注入 `PAIR_HARNESS_BUNDLED_PI_BIN`
- `desktop/scripts/build-sidecar.ps1`：`resources/pi/bin/`
- `config/providers.py`：Pi 的推理档位预设归一化
- `tests/contract/test_pi_engine.py`：照抄 codex/acp 的契约测试

前端：F10 设置页的引擎下拉加一项。**没有任何 orchestrator 改动。**

**Phase 1 验收：切到 Pi 引擎后，F2 的委派→执行→角色汇报闭环完整，F4 三种审批模式行为与 Codex 一致，重启后 F5 会话恢复正常。**

同时采集基线（这是 Phase 3 的对照组）：单次典型任务的输入 token 数、首 token 延迟、总耗时、工具调用轮数、成本。三个引擎各跑同一组任务。

## Phase 2：把审批权完全收回 Python（1 周）

这一步不需要 Pi 也能做，但配合 Pi 收益最大。

你现在有个隐性的架构裂缝：Codex 走合成审批事件（`decision` 字段），reasonix 走 `native_preexecution_approval = True`（`outcome.selected` + `optionId`），两条路的门控时机、可拦截范围、取消语义都不一样。你在 architecture.md 里已经用"避免双重门控"打了补丁，但这个不一致会一直是 F4 回归测试的负担。

Pi 引擎设 `native_preexecution_approval = False`，**所有工具调用统一走你自己的 `sandbox → risk_rules → ApprovalManager`**。这样"越界写操作在任何模式下都被拦"这条验收要点变成一个进程内的确定性断言，而不是和外部 agent 的协议协商结果。

顺带把 `risk_rules.yaml` 的匹配从"命令字符串模式匹配"升级为"结构化工具参数匹配"——因为在路径 B 里工具是你自己定义的，你拿到的是 `{tool: "bash", command: [...], cwd: ...}` 这样的结构，比正则匹配 shell 字符串可靠得多，误判和绕过都会明显减少。

## Phase 3：自建 pi-host，真正的性能收割（3–4 周）

新增一个 Node 子项目：

```
pi-host/
├── src/
│   ├── server.ts       JSONL over stdio，协议对齐你现有的引擎事件
│   ├── loop.ts         基于 pi-agent-core 的 agent loop（含 steer 注入点）
│   ├── prompt.ts       薄 system prompt（你自己写，不继承任何成品）
│   ├── tools/
│   │   ├── read.ts  write.ts  edit.ts  bash.ts   ← Pi 原生四件套
│   │   ├── grep.ts  glob.ts                       ← 按需加
│   │   └── gate.ts   每个工具执行前回调 Python 门控
│   └── models.ts       pi-ai provider 路由
└── build: bun compile / node SEA → 单个 pi-host.exe
```

关键设计决策——**门控回调的方向**。你的架构原则是"本地业务权威在 Python"，所以不要把 sandbox 规则复制一份到 Node。做法是每个工具执行前，pi-host 通过同一条 JSONL 通道向 Python 发一个 `approval.request`，挂起等裁决。这多了一次 IPC 往返，但相对模型推理的秒级延迟，本机 stdio 往返是毫秒级，完全不值得为它牺牲"单一权威"这条原则。

这一步的三个性能杠杆：

**杠杆一，prompt 瘦身。** Codex 和 Claude Code 的 system prompt 是为"通用编程 agent"写的，覆盖大量你场景里根本不会发生的情况。你的场景是受控的：项目已绑定、审批模式已知、角色已经把任务结构化成 `TaskRequest` 了。你的 prompt 可以短到只描述工具契约和输出约定。省下来的每一个 input token 都在每一轮 agent loop 里重复计费——这是复利。

**杠杆二，工具集裁剪。** 工具描述全部占 context。列一下你的委派任务实际用到哪些工具，只注册这些。你在文档里提到的场景（"看一下项目""改个东西"）大概率 read/write/edit/bash/grep 五个就够了。

**杠杆三，模型分工。** 你现在角色对话和编程执行共用一套服务商配置。分开路由：角色台词要表达力，执行要工具调用稳定性和便宜。pi-ai 的 provider 抽象让这件事变成一个配置项。

## Phase 4：收敛决策（1 周）

跑完 Phase 3，拿真实数据决定 Codex 引擎的去留。我的建议是**保留但降级**：pi-host 做默认引擎，Codex 保留为"重度工程任务"的可选引擎（F3 的双引擎变成"轻量默认 + 重型可选"）。理由是 Codex 在大规模重构、跨文件推理上的调优你短期复制不了，而你的 `CodingEngine` 端口维持它的成本极低。

# 六、性能提升的真实来源——一个不太顺耳的判断

你问"性能更强"。我要指出：**换引擎能带来的提升，很可能小于你现有架构里几个已经存在的瓶颈。** 如果只做引擎迁移不碰这些，你会失望。

按我从架构文档里读出的可疑点排序：

**1. 每个 delta 一行 JSONL 穿三层进程。** 流式增量走 Python stdout → Rust → Tauri event → 前端 `eventBatcher`。你在前端做了批量，但序列化和 IPC 成本已经在 Python 和 Rust 侧付掉了。建议在 `EventEmitter` 侧做时间窗合并（比如 16–33ms 一个窗口把同一 `message_id` 的 delta 拼起来再发）。这个改动独立于 Pi，收益立竿见影，尤其是长回复。

**2. 角色输出被迫走 `response_format: json_object`。** 为了解析 `{"speech": ..., "delegation": ...}`，你把整个角色回复包在 JSON 里，然后用 `IncrementalJsonSpeechParser` 增量解析。这有两个代价：JSON 转义膨胀 output token，以及首字上屏必须等到 `"speech": "` 这个前缀出现。更好的做法是**让委派走 tool call**——角色模型直接输出自然语言台词，需要委派时调用一个 `delegate` 工具。这样 speech 通道零解析、首 token 直接上屏，解析失败降级路径也可以删掉。这是我认为你当前架构里性价比最高的一处改造，和 Pi 无关。

**3. 委派任务的串行链路。** 角色台词流完 → 落库 → `_execute` → 引擎开 session → 执行 → 回执 → 再起一次角色回应。中间的 `open_session` 如果每次冷启动，用户会感到一个明显的空档。确认引擎会话是复用的，并且考虑在角色台词流式期间就预热 session。

**4. 标题生成。** 你已经处理了推理模型的 token 耗尽问题，但它仍然是首条消息后的一次额外模型调用。改用本地规则先出一个临时标题、模型结果到了再替换，可以让侧栏立即有反馈。

**5. 审批往返的人等机器。** "请求批准"模式下每个工具都要人裁决——这是产品设计不是性能问题，但可以优化呈现：把连续的同类操作合并成一张批量审批卡。

我的建议是**把 1 和 2 放在 Phase 1 并行做**，它们不依赖 Pi，且很可能比换引擎的体感提升更大。
