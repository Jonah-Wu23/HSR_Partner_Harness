# HSR Partner Harness V0.2.0 版本修改方案

状态：方案冻结，尚未开始代码修改。

本方案负责逻辑、协议、数据、联调、验收和发布安排。界面布局、视觉语言、动效与具体组件表现以 [`视觉与交互设计方案-v1.md`](./视觉与交互设计方案-v1.md) 为准，不在这里重复设计。

## 版本目标与边界

V0.2.0 的目标不是重写项目，而是在现有 Tauri 2 + React + Python Sidecar + SQLite 架构上补齐三条主线：

1. 修复当前 14 项实际使用问题，让角色、助手、语音和模式切换稳定可用。
2. 补齐消息生命周期、流式输出、任务队列、账号隔离和配置中心等基础 Harness 能力。
3. 完成 Windows 安装包验证并发布 GitHub `v0.2.0`。

本轮明确采用以下边界：

- Python 继续是业务状态权威；React 负责表现，Rust 负责桌面能力和 Sidecar 生命周期。
- 角色负责对话和结构化委派，助手负责项目读取、文件操作和命令执行。
- 本地注册、本地登录，不引入云端账号服务。
- 配置、项目、聊天、消息、工具记录和助手会话全部按本地账号隔离。
- VAD 模型由所有账号共用并打进安装包，不提供 VAD 模型路径设置。
- 本地 `DeepSeek-Reasonix` 最新克隆是 Reasonix 功能对照的权威来源；网页资料只用于补充通用 Harness 能力，不反向替代本地实现证据。
- **严禁重复造轮子。** `E:\AI\HSR Partner Harness\DeepSeek-Reasonix` 中与本轮需求相关的任何代码都可以复用：语言和技术栈相同则优先直接适配，语言不同则按原实现语义转换后接入当前 Python、Rust 或 TypeScript 层。每项功能开工前必须先检索本地 Reasonix 的现成实现；只有确认不存在、无法适配或会破坏本项目既定产品边界时，才允许重新实现，并在提交说明中写明原因。
- 不把 Reasonix 整套 UI、账号系统或运行内核无差别搬进本项目；复用代码时保留原有出处，并按实际使用情况同步更新 `THIRD_PARTY_NOTICES.md`。

## 方案选择

建议采用“统一事件与状态基座，再逐步接入界面”的路线。

另两种路线不适合当前项目：

- 逐项打补丁：短期能修 1、3、7、14，但队列、流式、账号切换会再次碰到相同状态问题。
- 直接替换成 Reasonix 内核：改动范围过大，也会冲击现有“角色 + 助手 + Python 业务权威”的产品结构。

推荐路线保留当前 Tauri、React、Python Sidecar 和 SQLite，只补齐缺失的消息、运行轮次、队列、审查和账号状态。

### 已冻结的三条联调原则

这三条已经由逻辑方案与视觉方案共同确认，实施时不得再各自推导另一套语义：

1. **模式不是纯前端状态。** `conversation_mode` 由后端按会话持久化，是与推理等级、审批方式、发送对象互不覆盖的独立字段。界面仍按视觉方案完成工作台开合、草稿保留和滚动保留。
2. **即时回显以真实消息为准。** `chat.submit` 在后端同步落库后立刻返回真实 `message_id`，并推送 `message.created`。前端可以覆盖毫秒级空窗，但必须按真实 id 对账，不能长期保留另一套临时消息。
3. **流式结构化 JSON 不直接上屏。** 后端增量解析 DeepSeek 输出，只推送干净的思考与自然语言字段；委派字段进入结构化委派卡。字段尚未解析出来时，界面显示“正在组织语言…”，解析失败详情进入技术信息区。

### 协议与状态的唯一权威

| 数据 | 权威位置 | 前端职责 |
|---|---|---|
| 当前账号、账号级配置 | Python + SQLite | 展示当前快照并发送显式修改命令 |
| 项目、聊天、模式 | Python + SQLite | 不用局部水合结果猜测或覆盖模式 |
| 消息、队列、Turn/item 状态 | Python + SQLite | 按 id 和 sequence 消费事件、重连后重新水合 |
| DeepSeek 结构化输出 | Python 增量解析器 | 只渲染已分流的 reasoning、speech、delegation |
| Codex 登录状态 | Codex app-server，经 Python 映射 | 展示登录、取消、退出和过期状态 |
| 工作台开合、动画、当前滚动位置 | React | 服从持久化模式，不反向修改其他设置 |

所有会改变持久化状态的操作使用独立命令和独立响应。禁止用一份过大的 bootstrap 或 settings 快照顺便覆盖没有被此次操作修改的字段。

## 分阶段修改计划

### M0：建立可复现基线

先把 14 项问题转为现有代码上的固定场景，避免修复过程中互相覆盖。

需要记录：

- 首条消息是否进入 SQLite、是否发出事件、是否被前端接收。
- 模式切换后，哪个 bootstrap 覆盖了 `mode`。
- 1011 来自 ASR、TTS 还是其他 WebSocket。
- 审查模式进入 TTS 的具体文本。
- 角色与助手消息的 `source`、`target` 和呈现位置。

不做大规模测试矩阵，只保留每项主路径回归。

### M1：先修当前最影响使用的问题

覆盖问题 1、2、3、4、5、7、8、14。

#### 1. 消息先保存，再异步处理

`chat.submit` 改为快速接收：

1. Python 原子保存用户消息。
2. 返回 `message_id` 和状态。
3. 发出 `message.created`。
4. 后台开始角色或助手回合。
5. 通过状态事件推进到完成或失败。

前端仍可立即显示发送中气泡，但后端保存的消息才是权威记录。断线或重启后可以从快照恢复。

#### 2. 模式成为独立的会话设置

新增：

```
conversation.set_mode
```

模式继续保存在 `conversations.last_mode`，切换时立即写入。`project.update_settings`、推理等级、审批方式等命令只返回自己的变更，不再用完整 bootstrap 快照覆盖当前模式。

同时把 Composer 的发送对象和草稿收回统一 store，删除组件内部重复状态。

#### 3. 后端真正执行聊天模式边界

当前后端虽然接收 `mode`，仍允许角色形成委派。

调整为：

- 聊天模式：角色输出中的 delegation 一律不执行，并给角色注入明确能力边界。
- 协作模式：角色可以委派。
- 直接交给助手只能出现在协作模式。
- 后端做最终裁决，不能只依赖按钮禁用或角色提示词。

#### 4. 注入项目运行上下文

新增稳定的 `ProjectRuntimeContext`：

```
项目名称
项目绝对目录
本机系统时间
时区
当前模式
```

项目创建、选择、路径修复和账号切换时重建。以“古代机械提供的当前工作环境”作为系统上下文注入角色和助手，不显示成普通聊天消息。

协作模式下问“这个项目是什么”时，角色知道当前已有项目，应形成委派，由助手读取项目后回答。

聊天模式下只能说明当前模式不能查看项目，并引导切换协作模式。

#### 5. 修正消息空间归属

给用户消息增加：

```
target: character | assistant
origin: user | character_delegation | system
```

Presenter 不再单纯按 `source` 切栏：

- `user + target=character`：角色区。
- `user + target=assistant`：工作台。
- `assistant`、`tool`：工作台。
- 角色执行结果回应：角色区。
- 委派任务通过 `delegation_id` 连接两侧。

#### 6. 审查提示由真实生命周期驱动

当前前端只要审批模式为 `review`，就永远显示“审查智能体正在评估高风险操作…”。

新增：

```
review.started
review.completed
review.failed
```

只有审查智能体真正被调用时才显示。低风险直接放行、空闲状态和普通回复不显示审查提示。

#### 7. 修复审核模式 TTS 空文本

目前角色结构化输出解析失败时可能降级成纯省略号 `……`，它仍会作为 `character.speech` 进入 TTS，和 DashScope 的 “input text is invalid” 症状吻合。

修改：

- 最终 speech 为空或只有标点时，不创建可朗读请求。
- 审批、审查、工具和系统消息始终静音。
- TTS 入队前再次检查有效自然语言。
- 语音失败不能把应用全局状态改为错误。

该路径需要一次真实 DashScope 回归才能把根因从“代码强证据”升级为“运行确认”。

### M2：流式、队列、语音与连接恢复

覆盖问题 6、9、10、11，并补齐基础 Harness 主干。

#### 1. 统一运行模型

采用四层结构：

```
Conversation
  └─ Turn
      ├─ Message
      ├─ Reasoning item
      ├─ Tool item
      └─ Review item
```

标准生命周期：

```
queued → accepted → running → completed
                            ↘ failed
                            ↘ cancelled
```

每个事件携带：

```
account_id
project_id
conversation_id
turn_id
item_id
sequence
```

这与成熟 Harness 常见的 session/turn/item 结构一致。Codex app-server 本身也采用 thread、turn、item，并提供 started、delta、completed、failed、interrupt 等事件。[Codex app-server](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)

#### 2. DeepSeek 思考与正文流式传输

现有适配器已经读取：

- `reasoning_content`
- `content`

但 Orchestrator 忽略增量，直到最终 JSON 解析完成才落消息。

改为：

```
dialogue.reasoning.started
dialogue.reasoning.delta
dialogue.reasoning.completed
dialogue.speech.started
dialogue.speech.delta
dialogue.speech.completed
```

DeepSeek 输出是结构化 JSON，不能把原始 `{ "speech": ... }` 直接显示。需要增量 JSON 字段解析器：

- `reasoning_content` 直接进入思考通道。
- 只提取 `speech` 字符串内容进入角色正文。
- delegation 等结构字段继续等最终对象解析。
- 最终完整对象覆盖并确认临时预览。

正式记录与实时预览分离也是常见做法：增量只负责即时显示，最终消息才是持久化权威结果。[Claude Session event stream](https://platform.claude.com/docs/en/managed-agents/events-and-streaming)

#### 3. 持久化消息队列

参照本地最新版：

- `DeepSeek-Reasonix/docs/ACP.zh-CN.md`
- `DeepSeek-Reasonix/reasonix.example.toml`
- `DeepSeek-Reasonix/release-notes/releases.json`

实现精简版 `conversation_inbox`：

```
queue_item_id
account_id
conversation_id
target
text
intent
position
status
created_at
```

默认语义：

- 忙碌时发送：`followup`，当前回合完成后自动处理。
- “立即插入”：转为 `steer`，尝试注入当前助手回合。
- 注入失败：保留为下一条 follow-up，不丢消息。
- 支持编辑、撤回、调序。
- 每条入队先持久化，再向前端确认。

角色和助手使用两条执行通道：

- 角色：按聊天串行回复。
- 助手：全应用同一时刻一个执行任务。
- 助手运行时，角色聊天仍可工作。
- 用户直发助手的新消息默认排队，不再自动当成任务修改。
- 只有明确选择“立即插入”时才调用 Codex steer/amend。

Reasonix 的本地最新版已经提供持久化 Session Inbox、steer/follow-up、编辑、删除、调序和暂停能力。本项目只实现当前界面需要的子集，不搬入完整 Reasonix。

#### 4. 修复语音卡顿

当前 `AudioPlayer.play_blocking()` 每播放一个 PCM 小块都会新建并关闭一次 `sounddevice.OutputStream`，块边界必然容易出现停顿。

修改为：

- 播放任务启动时建立一个长期输出流。
- PCM 块进入有界缓冲。
- 同一条语音和连续队列共享输出流。
- 停止时清缓冲并中止当前 TTS。
- 空闲一段时间后再关闭设备。
- 先保留流式合成。

整段非流式合成作为回退选项，只在连续播放仍不稳定时使用。首选方案延迟更低，也更符合现有播放队列。

#### 5. 1011 错误分类和恢复

先区分错误来源：

```
voice.asr
voice.tts
dialogue.deepseek
codex
sidecar
```

处理方式：

- 同一错误短时间内只显示一次。
- WebSocket 连接使用有限重试和退避。
- 单次语音连接失败只关闭本次语音，不切全局错误页。
- 恢复后发出 `connection.restored`。
- 原始 1011 信息放技术详情。
- 启动期 Sidecar 无法启动才允许整屏失败。

### M3：本地账号与设置中心

覆盖问题 13。

#### 1. SQLite 账号隔离

新增：

```
accounts
account_preferences
provider_configs
secret_refs
conversation_inbox
```

`projects` 增加 `account_id`。聊天、消息、工具记录和引擎会话通过项目/聊天外键继承账号归属，所有读写命令都从当前登录账号过滤。

旧数据迁移：

- 升级时创建一个默认本地账号。
- 现有项目全部归入该账号。
- 保留项目、聊天、消息和 Codex session。
- 用户首次进入新版时为默认账号设置名称和密码。

#### 2. 本地注册登录

支持：

```
account.list
account.register
account.login
account.logout
account.switch
account.update_profile
account.change_password
```

每个账号包括：

- 登录名
- 显示名称
- 头像
- 密码派生结果
- 上次登录时间
- 引导完成状态
- 主题和语音偏好

切换账号时：

1. 停止或明确处理当前任务。
2. 关闭当前模型和语音运行时。
3. 清空 React 当前账号快照。
4. 加载新账号项目和聊天。
5. 按新账号配置重建模型运行时。

#### 3. 配置范围

每个账号独立保存：

- 编程助手：Codex 或 DeepSeek。
- 对话服务商、Base URL、模型、API Key。
- 推理等级。
- 审批模式默认值。
- DashScope Base URL、WebSocket URL、API Key。
- ASR/TTS 模型和双音色。
- 语音、VAD 使用偏好。

VAD 模型文件不进账号配置。

#### 4. Codex OAuth 与 API 登录

直接使用 Codex app-server 当前官方接口：

```
account/read
account/login/start
account/login/completed
account/login/cancel
account/logout
account/updated
```

支持：

- ChatGPT 浏览器 OAuth。
- 设备码登录，作为浏览器回调失败时的备选。
- OpenAI API Key 登录。
- 登录取消、退出和过期提醒。

Codex 官方 app-server 已提供上述认证模式和通知，无需自行实现 OAuth 协议。[Codex Auth endpoints](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md#auth-endpoints)

每个本地账号使用独立的 Codex 数据目录，使 OAuth Token、API Key 和 Codex session 不会串账号。

#### 5. DeepSeek 编程助手

配置中选择 DeepSeek 时，通过单独的 `CodingEngine` 适配器接入。推荐复用本地最新版 Reasonix 的 ACP/流式会话能力作为引擎边界，通过现有 Python Orchestrator 映射成统一工具、审批和消息事件。

这部分单独实施，避免把 Reasonix 的 UI、账号或完整配置系统嵌入本项目。

#### 6. VAD 打包

当前构建脚本已经通过 PyInstaller `--add-data assets;assets` 包含整个 assets 目录，VAD 位于：

```
assets/models/silero_vad_v5.onnx
```

发布阶段仍需验证安装后的实际资源路径和 VAD 初始化，不能只检查源码目录。

按视觉方案的前端阶段推进：

1. 状态基座：发送状态、队列、Toast、连接药丸。
2. 空间重构：常驻角色区、可开合工作台、委派卡。
3. 账号门和设置中心。

这一阶段不重新讨论页面方向，只检查视觉稿需要的接口是否已提供。
