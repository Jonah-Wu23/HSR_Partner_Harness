## 3. 关键发现

1. **首启清理脚本的日志清理从未执行**（V039-R1-001，P3，必现）。脚本为 UTF-8 无 BOM + 中文注释 + LF；Windows PowerShell 5.1 按 CP936 解码时吞掉 2 个换行（116 行 → 114 行），中文注释与下一行 `$logRoot = ...` 合并，该变量恒为 null，第 72 行 `Split-Path -Parent` 收到 null 抛错，删除代码未执行。对照实验（加 BOM / 改 ASCII / 保持原样）三组确证。影响：跨批次 sidecar 日志混入下一批次证据，威胁 §3.3 的全量日志取证。
2. **B-03 的连带效果被真实暴露**：把对话端点指向非 OpenAI 域时，Sidecar 在**启动期**就因 `_require_responses_backend` 抛错退出（退出码 2），候选完全无法启动。这既是名称解析失败形态受阻的原因，也说明该校验位于运行链路的必经之处。
3. **语音侧的 018 误报已消失**：真实抢占下旧合成在第 66 个分片后静默收尾，全过程零 `voice.mobile_tts_failed`。
4. **019 的归因链可用**：一次真实计费往返现在能说清「输出为什么不可用、要不要重试、最终用了哪次」，这正是上一批次无法归因的缺口。

## 4. 过程中的环境副作用（如实说明）

B-01 的代理注入把**全部**出站引到只转发 `api.deepseek.com` 的沙盒，因此该期间 DashScope 的 WSS 合成必然失败（界面出现「语音合成失败：websocket connection could not established within 5s」）。该失败归因于测试沙盒，**不是产品缺陷**。
