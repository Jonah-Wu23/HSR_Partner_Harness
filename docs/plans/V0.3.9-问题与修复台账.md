- 责任轨：移动端前端（`desktop/mobile/src/pages/chat/ChatPage.tsx`、`desktop/mobile/src/lib/useVoiceCapture.ts`）

业务现象：
（前提条件）手机已连接桌面端，语音可用（面板可打开）。

产品设计口径（用户确认，作为本条判据）：**按下时长即采集时长**。长按说话、按住期间持续采集、手指抬起即结束并发送；**短按只能捕捉极短内容或什么都捕捉不到，再按一次就等同于开始一次新的输入**——短按抓不到话是设计使然，不是缺陷。

（操作步骤）用户在语音面板里**长按**「按住说话」，按下的同时正常说话，随后抬起手指期望停止并发送。
（目前结果）**严重错误：按住期间说话没有被捕捉（屏幕上始终没有转写），抬起手指也不会停止采集。** 用户原话复述：**「我点击按住说话之后，说话没有传到屏幕上，再点击没有停止录音。长时间按下和短时间按下的效果在前端上没有区别，令人迷惑。」** 用户对期望交互的描述是：**「应该是长时间按下，按下去的同时说话，手指抬起，语音发送。现在不是这样的。」** 即：语音面板里的「按住说话」**本身**就应当是一个按压-保持控件，而当前它不是——按下时长在该控件上完全没有被使用。

服务端观测（`manual-observation-window.log`，基线之后）：窗口内只有三轮 TTS 合成的记录（`mobile-tts: 触发下发 / 开始合成 / 合成完成`，13/12/13 片），**没有任何 `voice.mobile_ptt_start` / `voice.mobile_audio_chunk` / `voice.mobile_ptt_stop` 相关记录**；同期也没有转写相关记录。即按住说话这条路径在该窗口内没有产生可观测的服务端会话。

静态核对（可复现的代码事实）：

1. `ChatPage.tsx:678-693` 的「按住说话」是**模式切换按钮**，绑定的是 `onClick → voice.activateHold()`；而 `useVoiceCapture.ts:171-175` 的 `activateHold` 语义是 **直接开始采集**：
   `if (!usable) return; setMode("hold"); void startSession("hold");`
   该控件只有 `onClick`，**没有任何指针抬起/取消的释放路径**。
2. 真正的按压-保持控件是**另一个按钮** `ChatPage.tsx:712-735`（`data-testid="voice-hold-btn"`），才绑定了 `onPointerDown → activateHold` 与 `onPointerUp / onPointerLeave / onPointerCancel → deactivateHold`；它的可见文字同样是「按住说话」（`:734`，录制中变成「聆听中…」）。**同一个短语既是模式名又是操作名，两个控件并列出现**：用户按的是 `onClick` 那个，于是「按下时长即采集时长」这条设计在用户实际按到的控件上根本不成立。
3. 停止只有一条路：`useVoiceCapture.ts:177-180` 的 `deactivateHold`（`if (mode !== "hold") return; void stopSession()`），它只挂在那颗**按压-保持按钮**上。用户在模式按钮上再点一次，只会再调一次 `activateHold`，而 `startSession` 在 `capture.state !== "idle"` 时直接返回（`useVoiceCapture.ts:111`），**因此不停止、也不报错**——正是「再点击没有停止录音」。
4. **按键语音侧没有任何采集状态反馈**：对照 `ChatPage.tsx:708-745`，自动检测模式渲染的是「● 准备中… / ● 聆听中，检测到静音自动停止」状态行 +「停止」按钮，而按住说话模式渲染的是那颗大按钮本身（`:734` 只在 `captureState === "recording"` 时把文字换成「聆听中…」）。用户实测：**PTT 面板里既没有「准备中…」也没有「聆听中…」，按下与抬起都不产生任何状态变化**——即 `capture.state` 从未进入 `recording`，该模式没有可用的采集反馈。

对照事实（同一次人工测试，自动检测模式**工作正常**，作为本条的反证，不作为 PTT 的解释）：
- 用户在自动检测模式下实测：打开 → 「● 准备中…」（`02-auto-preparing.jpg`）→ 开始说话后转为「● 聆听中，检测到静音自动停止」（`03-auto-listening.jpg`）→ 停止后回到「准备中…」→ 自动关闭并发送。
- 转写与发送链路真实可用：该模式捕捉到并发送了「我的哎呦，知道。」与「Hello hello hello hello」两条消息，角色按这两个输入正常回复（`04-auto-transcript-and-send.jpg`）。

未决项（需下一步取证）：
- PTT 侧「按下不进入采集」的直接原因尚未定位到具体一行：可能是 `onPointerDown` 未在大按钮上生效（`ChatPage.tsx:717-720`），也可能是 `startSession` 内 `getUserMedia`/`engine.start(stream)` 未完成（`useVoiceCapture.ts:110-160`）。**自动检测模式能正常采集**，说明服务端会话与采集引擎本身可用，因此**排除「ASR 链路整体不可用」**；差异集中在按住说话这条前端路径上。定位需要在真机上直接观测 `capture.state` 与 pointer 事件是否触发，本轮不做猜测性结论。

期望表现：
（预期结果）语音面板里的「按住说话」必须是**按压-保持**语义，且**按下时长即采集时长**：

1. 指针按下（`pointerdown` / 触摸按下）立即开始采集并从麦克风上行；
2. 按住期间持续采集，**不得**因短暂停顿、轻微位移或长按而被取消或提前结束；短按按设计只捕捉极短内容（或什么都捕捉不到），再按一次即开始一次新的采集，这不视为缺陷；
3. **手指抬起（`pointerup`）立即停止识别**，把转写结果按既有协议发出/填入并进入发送流程；
4. 抬起必须可靠送达：`pointercancel`、手指移出控件等边界情况也要收敛到「停止」，不得留在采集态；
5. 该控件**不得**用 `click` 语义绑定（点击语义使按下时长失去意义，且没有释放路径）；
6. 同一面板内若仍需模式选择，模式名与操作名不得使用同一文字，模式切换也不得隐式开始采集；
7. 采集无法启动时必须在面板上如实给出失败原因，不得无反馈；按住说话模式同样需要可见的采集状态（至少与自动检测模式等价的「准备中 / 聆听中」反馈），不得出现「按下去什么也不显示」的静默态。
