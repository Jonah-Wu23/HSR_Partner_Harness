## 结论

看完这四份文档，我的最终建议只有一句：**别再纠结 Pi 了，你要的答案已经在你自己的安装包里——`reasonix.exe` 的上下文引擎。**

DeepSeek-Reasonix 是 MIT、Go、单静态二进制，你现在就通过 ACP 把它当第二引擎在用，而它恰好把「prompt cache 命中率」当成一等工程约束做到了极致，还配了诊断工具和 CI 门禁。它解决的正是你角色路径上最痛的那个问题。你不需要引入第三个运行时去换一套别人的 agent loop，你需要把这套上下文纪律搬到你自己的 `orchestrator` 里。

## 一、先撤回我之前的几处错判

《建议问题解答》对着代码逐条核过了，有几条我说错了，这些会误导你把力气花在错地方，一并纠正：

- **「prefix cache 基本没吃到」说过头了。** 你的组装顺序本来就是稳定 system → 历史 → 任务进度/结果 → 运行上下文 → 当前输入，易变的东西已经在尾部了。角色卡是能复用的。真正的损失只有一处：窗口满了之后每轮滑动一条，历史段的复用崩掉。

- **「去掉 `_history`」撤回**。它承担流式编排和本轮结果收集，改成先写库再追加内存 + 一致性测试就够了。
- **「6k 固定预算 + 每 6 轮跳一次」作废**，被下面 Reasonix 的方案完整取代——《解答》指出的「跳步会突然遗忘一大块」是对的，而 Reasonix 早就把跳步点和摘要点合并了。

## 二、把 Reasonix 的上下文引擎搬到角色路径

### 它做对的四件事

**1. 前缀字节级冻结，所有会变的东西骑在用户回合上。** 目标、plan 标记、记忆更新、后台任务通知，全部 prepend 到 user turn 文本前，绝不碰 system 和工具 schema。有一条细节特别值得抄：会话中途写入的记忆只骑在当轮，**下一个会话才折进系统前缀**——立刻生效，又不弄脏缓存键。

**2. 序列化净化。** `provider.Message` 里混着 `RawContent`、`ToolExecution`、`CreatedAt`、审批回执、`LocalOnly` 等本地元数据，发送前全部剥离。你的 `message_json` 整对象存库，一样有这个风险：任何一个只影响 UI 的字段漏进请求体，前缀就废了。

**3. 追加式增长 + 单次压缩 + 持久化投影。** 上下文一路追加到阈值前**完全不动**，缓存全程热；到阈值做一次摘要事务，装成 `稳定前缀 + 一个结构化摘要 + 最近逐字尾`；**canonical transcript 永不重写，投影是独立视图并持久化 `ProjectionVersion`，重启后恢复同一投影**。

这条对你是天作之合：你的 SQLite 已经是 canonical transcript，12 条窗口就是一个每轮重算、从不持久化的投影。把投影落库，你顺带拿到「重启后缓存不白费」。

**4. 缓存可见性是内建的。** `PrefixShape` 对 system + tools 做哈希跨轮比对，`CompareShape` 区分「本地元数据变了」和「真正的 provider 可见重写」；计费侧把 DeepSeek 的 `prompt_cache_hit/miss_tokens` 和 OpenAI 的 `cached_tokens` 归一成统一字段；还有端到端命中测试和 PR 的 `Cache-impact` 字段门禁。

《解答》说「没有度量，成本降幅无法验证」——这就是度量该长的样子。而且它比单纯记 token 强：它告诉你**为什么** miss，不只是 miss 了。

### 落到 HSR 的具体形态

新增一张投影表（你有 `SCHEMA_VERSION` 逐级迁移，成本很低）：

```
conversation_projections(
  conversation_id, projection_version,
  summary_json, covered_through_message_id, created_at)
```

角色请求的组装顺序改成：

```
[稳定前缀]  角色卡 + 搭档身份 + 输出协议（未来 + delegate tool schema）
            + 跨聊天记忆本（变化极慢；本轮更新的部分骑用户回合，下会话才折进来）
[投影摘要]  <compaction-summary> 结构化槽位，仅在跳步时更新
[逐字尾部]  covered_through_message_id 之后的完整往返
[易变块]    任务进度 / 结果回执 / 运行上下文（时间、模式、项目名）
[当前输入]  用户消息（带 target=character 过滤）
```

摘要槽位换成叙事导向，但保留 Reasonix 的纪律（固定标题、短句、标识符和文件名数字原样、不虚构、标签包裹）：

已确立的事实（称呼、身份、偏好、约定）/ 角色当前状态与情绪 / 关系与关键节点 / **共同完成的工作** / 未兑现的承诺与悬而未决 / 世界设定增补。

第四个槽位由 `CharacterResultSummary` 回执直接喂入——这一条同时解掉了《解答》§3.6 说的「缺少结构化工作结论」，不用再多加一种气泡。

还有两个校验必须一起抄，否则你一定会踩：**候选摘要必须比源小**，以及**摘要期间会话若发生变化就丢弃候选并封锁本代重试**（Reasonix 的 `errCompressStaleContext`）。角色扮演是高频交互，用户在摘要生成中途又发一条是常态，没有这个守卫你要么白付钱，要么装进一个过期投影。

### 必须为角色扮演改掉的两处

**阈值不能照抄 0.85。** Reasonix 面向的是「放着跑」的自主编码，丢上下文是灾难，所以它让上下文长到窗口 85% 才压缩。你的场景是人在对面等着，**每轮的输入体量直接换算成首字延迟**，缓存命中只是打折不是免费。所以对角色路径应该设一个**绝对上限**而不是窗口比例——先测分布，起步值我会取历史段 12–16k token 触发压缩，压缩后尾部不超过上限的一半（对应它的 `checkpointCeilingRatio`）。

**逐字尾部要有最小保底轮数。** 保证最近若干轮完整往返永远不进摘要。编码 agent 可以把三步之前的操作压成一行，角色扮演不行——刚才那句话的语气丢了，人格立刻塌。

**不要抄的**：双模型执行器/规划器、90 个包的分层 + `repolint` ratchet、`Cache-impact` PR 门禁。那套治理是配它的体量的。你用「组装后 prompt 的 golden snapshot 测试 + 前缀哈希断言」就能拿到九成效果。

## 三、PenguinHarness 给了你一个价格标签和一条不该走的路

**传输层不要换。** 它选同源 HTTP/SSE 换来的是多用户认证、Web 前端复用、远程访问潜力——而你的 PRD §6 明确写了不做云同步、远程访问、多用户协作。这三样收益你一样都不要，却要为它付出重写协议层、放弃事件序号对账契约的代价。你的 stdio JSONL + 单调序号 + 断线重新水合，在桌面单机场景下是更强的设计，保持。

## 四、Pi 的最终定位：降级，且有更好的替代

《解答》把 Phase 0 八项查清了，结果很有意思：**能力项全部有解**（steer / abort / session file + switch_session / thinking 事件 / LF-JSONL / DeepSeek 都支持），**剩下的两个未知恰好是最要命的两个**——审批语义能否在 stock RPC + 扩展下保住，以及 Windows 单文件分发官方没有承诺。

这两个都不是能力问题，是架构和打包问题，而且都由你独自承担。再叠加上面那个 225MB 的价格标签，我的结论是：**Pi 从「三到四周自建 pi-host」降级为「受度量门控的独立实验」**，除非下面的数据出来后证明引擎侧真的是你的前二瓶颈。

而如果你的动机是「我要一个能自己掌控的引擎内核」——**更好的候选是扩展 Reasonix，不是 Pi**：

- 打包风险归零：Go、`CGO_ENABLED=0`、单静态二进制、一条命令交叉编译六个目标。Pi 的 Windows 单文件是空白。
- 集成成本归零：ACP 适配器你今天就有，`reasonix.exe` 今天就在包里。
- MIT 开源、可读、可 fork。
- 它有 **Extension Protocol v1 sidecar，能拦截运行时事件、提供 Provider 和结构化 UI**——这正对 Pi 那个未解的审批 go/no-go。如果 EP v1 能承载你的异步审批，你就能把 reasonix 的 `native_preexecution_approval` 从 `True` 改成 `False`，让 codex 和 reasonix 两条路统一走 Python 侧的 `sandbox → risk_rules → ApprovalManager`，把之前那个「双重门控/两套语义」的架构裂缝一次补上。
- 附赠上面整套缓存纪律。

代价是 Go，以及它是个 90 包的完整 agent 而不是「极简原语」。所以这条路服务的是**掌控 + 性能**，不服务「我要从原语开始亲手写 agent loop」。后者才该走 Pi，且要认打包这笔账。

EP v1 能否承载异步审批同样需要一次 spike——和 Pi 那两项是同一风险等级，别把它当已知。

# 一、什么叫"完全掌控 agent loop"

## 1. 先把 loop 本身说清楚

Agent loop 就是这么一个循环：

```
组装请求 → 调模型 → 解析输出
    ├─ 有工具调用 → 执行工具 → 把结果追加进上下文 → 回到"组装请求"
    └─ 没有工具调用 → 判定结束
```

四行代码的事。所以"掌控 agent loop"从来不是指"能不能写出这个循环"——谁都能写。它指的是**这个循环里有大约八个决策点，每一个都由谁来定**。

| #    | 决策点           | 具体是什么                                                   |
| ---- | ---------------- | ------------------------------------------------------------ |
| 1    | 请求怎么组装     | system 里放什么、什么进前缀、什么骑用户回合、历史怎么排      |
| 2    | 工具集和 schema  | 注册哪些工具、描述怎么写、参数结构长什么样                   |
| 3    | 工具执行前的门控 | 能不能拦住、能不能异步等人裁决、拦截点在参数解析后还是执行前 |
| 4    | 上下文怎么维护   | 什么时候压缩、压成什么形状、丢弃哪些、投影存不存             |
| 5    | 什么时候停       | 轮数上限、无进展判定、模型说完就停还是继续追问               |
| 6    | 出错怎么办       | 工具超时、模型吐畸形 tool call、连续失败、context 溢出       |
| 7    | 中途能不能插话   | steer 注入点在哪一轮的哪个位置                               |
| 8    | 模型和参数       | 哪一轮用哪个模型、温度、思考开关、usage 怎么统计             |

**掌控 = 这八项你都能改，而且改动是你自己代码里的一行，不是给上游提 issue、不是靠 prompt 去劝一个成品 agent 改行为。**

## 2. 你现在掌控了多少

你的项目有**两个** loop，情况完全不同。

**角色路径**：`process_character_turn` → 一次模型调用 → 解析 `{"speech", "delegation"}` → 有委派就转执行。严格说这不算 loop，是单发。但上面八项里的 1、4、5、6、8 全在你 `orchestrator.py` 和 dialogue adapter 里，**你已经 100% 掌控**。

**执行路径**：`_execute` → `open_session` → `run_turn` → 消费事件流。真正的 loop 在 `codex.exe` 或 `reasonix.exe` 进程里转。你在外面能做的是：审批门控（第 3 项，而且 reasonix 那条路还是 `native_preexecution_approval = True`，你是被通知不是做决定）、取消、steer（第 7 项，但注入时机由引擎定）。**1、2、4、5、6、8 全部不在你手里。**

所以在你这个项目里，"完全掌控 agent loop"只有一个所指：**把编程助手那个内层循环接管过来。** 除此之外没有别的意思。

## 3. 接管过来能拿到什么，代价是什么

能拿到的，按对你的实际价值排序：

- **第 4 项和第 1 项**——上下文维护和前缀布局。这是唯一真正值钱的。执行路径现在每轮塞多少 token、什么时候压缩、压成什么形状，你完全看不见也管不着。
- **第 3 项**——审批。接管后 codex 和 reasonix 两套语义的裂缝自动消失，"越界写操作在任何模式下都被拦"从跨进程协议协商变成进程内断言。
- **第 2 项**——工具集裁剪。成品 agent 带的工具描述是为通用场景写的，你的场景是受控的。
- **第 5、6 项**——终止和错错误处理。这两项接管后是**净负债**：无限循环、工具超时、畸形 tool call、context 溢出，四类边界情况从此归你兜。成品 agent 在这上面的调优是真金白银堆出来的。

**关键在于：真正值钱的第 4 项和第 1 项，在角色路径上你本来就全权掌控，而且那条路径才是你产品的主线。** 我上一轮建议的第三阶段——追加式增长、单次压缩、投影落库、前缀冻结——那件事本身就是在行使 agent loop 的控制权，只不过是在你已经拥有控制权的那条路径上。

所以"想要完全掌控"这个动机，正确的检验方式是问自己：**执行路径上，具体哪一项让你难受过？** 如果说不出具体的，那这个动机大概率是架构洁癖，不是工程需求。如果说得出（我猜最可能是第 3 项审批语义不统一，其次是第 4 项看不见执行侧 token），那这两项都有比重写 loop 便宜得多的解法——审批走 Reasonix 的 EP v1 拦截，token 可见性走 usage 字段透传。

# 二、主力是 DeepSeek，这个信息改了什么

改的东西比想象中多。

## 1. 直接作废一条：多模型分工

我最早那份报告里，Pi 的一大卖点是"角色用表达力强的模型、执行用便宜的 coder 模型"，`pi-ai` 的 provider 抽象天然支持。**你单一 DeepSeek，这个杠杆价值归零。** Pi 的推荐分数因此再降一档——剩下的理由只有"极简 loop"，而那个理由要用一个 Node 运行时进包来换。

反向看，Reasonix 是 DeepSeek 预设、任意 OpenAI 兼容端点作配置项，它的整套缓存工程就是照着 DeepSeek 的自动前缀缓存设计的。你和它的模型侧假设完全重合。

## 2. 上下文改造的收益被放大了

DeepSeek 的前缀缓存是**自动的**，不需要你声明 cache breakpoint（Anthropic 那种要手动打点），命中的部分按一个低得多的单价计费，同时省掉预填充时间——**省钱和降首字延迟是同一个动作**。

这意味着上一轮定的第三阶段，在 DeepSeek 上的回报率比在其他家更高。具体到实现，有四个 DeepSeek 特有的点：

**缓存有最小粒度（官方文档写的是 64 token，按你当前版本核对一下）。** 两个后果：一是不必为了几个 token 的微小差异去做前缀洁癖，低于粒度的抖动本来就不影响；二是**你的稳定前缀必须足够长才有意义**——角色卡加搭档身份加输出协议肯定远超这个量级，没问题，但"跨聊天记忆本"如果只有两三条，单独放在前缀里几乎不产生缓存收益，要么攒够量要么就别急着做。

**缓存会因闲置而失效。** 这是 Reasonix `cacheColdAfter` 那个字段存在的原因。你的产品形态是桌面应用，用户"打开聊两句、关掉、几小时后再开"是常态——**每次冷启动后的第一轮必然 miss，这是物理规律不是你的 bug**。度量上线后一定要按"距上轮的时间间隔"分桶统计命中率，否则你会看到一个被冷启动稀释得毫无意义的平均值，然后误判改造无效。

**usage 字段是 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。** 你归一化的时候注意：这两个字段是**互斥拆分**的（相加等于总 input），和 OpenAI 的 `cached_tokens`（是 input 的子集）语义不同。搞混了统计会直接错一倍。

**上下文窗口比 Claude/Gemini 小。** 所以我上一轮说的"压缩阈值取绝对值而不是窗口比例"在你这里不是偏好问题，是必须——Reasonix 的 0.85 比例阈值是给它自己的可配置模型算的，你照抄会让历史段涨到一个首字延迟明显劣化的体量。**具体阈值等第二阶段的真实分布出来再定，我给的 12–16k 只是起步猜测，别当结论。**

## 3. 两个 DeepSeek 特有的技术风险

**推理模型的 `reasoning_content` 绝对不能回传。** DeepSeek 明确要求下一轮请求里不带上一轮的思考内容，带了会报错。你现在的做法是对的（`payload.reasoning` 只存库供界面展示，不进角色上下文），**但第三阶段做投影和摘要时要特别小心**：投影是从 canonical transcript 生成的，而你的 `message_json` 是整对象存的，里面就有 reasoning。序列化净化那一步（Reasonix 的 `ModelMessages` 剥离）在你这里不是可选优化，是**正确性要求**。

**`delegate` tool call 方案的真实门槛在这里。** 这个提案的前提是：你用的 DeepSeek 模型要能在**开启思考的同时稳定支持 tool calling**，并且和你现在的 `response_format: json_object` 路径能平滑切换。这在 DeepSeek 的推理模型上历来是有约束的组合，各版本行为不一致。所以 A/B 之前先加一道能力探测：**用你实际配置的模型 + 实际的推理档位，跑一次带 tool schema 的请求，确认思考通道和工具调用能同时出来。** 这一项不通过，整个提案作废，不用做 A/B。

顺带说，这个提案的收益论据在 DeepSeek 上更强：JSON 包装的转义和字段脚手架吃的是 **output token，永远不缓存、单价最高**；换成 tool schema 之后这部分结构成本挪进了**可缓存的 input 前缀**，也就是从最贵的一档挪到了最便宜的一档。

## 4. 引擎侧的连带影响

你的 reasonix 引擎本来就复用角色对话的 DeepSeek 服务商和密钥（`REASONIX_HOME` 里的 `config.toml` + `.env`）。也就是说：**你现在这套 DeepSeek 单一供应商 + Reasonix 引擎的组合，密钥、端点、模型全线打通，没有任何多余的配置面。** 引入 Pi 会新增一套 provider 配置、一个 Node 运行时、一份打包风险，换来的是同一个 DeepSeek 后端。

而 Codex 引擎在你这个配置下是个例外——它走 OpenAI 生态，需要单独的 OAuth 或 API Key。这不是问题（保留它作为重型可选引擎的理由仍然成立），但你应该清楚它在你的默认路径之外。

# 三、结合这两条，最终建议收紧成

**动机上**：如果你说不出执行路径上具体哪一项卡过你，"完全掌控 agent loop"这个动机就不成立，直接排除引擎改造。如果卡你的是审批语义不统一，那走 Reasonix EP v1 拦截的 spike，一两周的事，不需要重写任何 loop。

**技术上**：DeepSeek 单一供应商让 Pi 仅剩的卖点（多模型路由）失效，同时让上下文改造的回报被自动前缀缓存放大。**第二、三阶段的优先级进一步压过一切引擎工作。**

**执行顺序不变**，只是第二阶段的度量要加两个 DeepSeek 专属要求：`hit/miss` 互斥拆分的正确归一，以及**按闲置时长分桶**看命中率。第三阶段的序列化净化从"优化"升级为"正确性要求"（reasoning 不得回流）。`delegate` 提案前置一道能力探测。

还有一个问题我需要你确认才能把阈值定下来：**你角色路径实际用的是哪个 DeepSeek 模型、开不开思考、推理档位默认设在哪一档？** 思考本身吃 output token 且不缓存，如果角色对话默认开着高档推理，那你当前成本结构的大头可能根本不在历史窗口上，第三阶段的预期收益要重算。

两件事性质不同，拆开来说。

## Token可见性：可以现在就做，不需要 spike

这一条是纯透传，不改任何业务逻辑。

### DeepSeek 流式响应的 usage 字段

DeepSeek 在流式模式下，usage 出现在最后一个 chunk。你的`openai_compatible.py` 目前大概率忽略了它。要启用，请求里加：

```python
"stream_options": {"include_usage": True}
```

最后一个 chunk 的结构：

```json
{
  "usage": {
    "prompt_tokens": 1840,
    "prompt_cache_hit_tokens": 1600,
    "prompt_cache_miss_tokens": 240,
    "completion_tokens": 312
  }
}
```

注意：`hit + miss = prompt_tokens`，这是**互斥拆分**，不是 OpenAI 那种 cached 是 prompt的子集。归一化时：

```python
# DeepSeek
cache_hit   = usage.get("prompt_cache_hit_tokens", 0)
cache_miss  = usage.get("prompt_cache_miss_tokens", 0)
input_total = cache_hit + cache_miss

# OpenAI 兼容端点（不是 DeepSeek）
input_total = usage.get("prompt_tokens", 0)
cache_hit   = usage.get("prompt_cache_hit_tokens")# 可能没有这个字段
```

还有 `reasoning_tokens`（思考 token），在 `completion_tokens_details.reasoning_tokens` 里，是output 的子集，**永远不缓存，单价最高**，一定要单独记。

### ACP 侧（reasonix）的 usage

ACP `session/update` 事件的最终 `agent_message_chunk` 或 `agent_thought_chunk` 里带 `usage` 字段，结构和 DeepSeek chat completions 一致（因为 reasonix 内部转发了模型响应的 usage）。在你的 `acp/` 适配器的事件循环里捕获最后一个带 usage 的事件即可。

###存哪里

在 SQLite 加一张轻量指标表，单独一张不塞进messages，迁移干净：

```sql
CREATE TABLE turn_metrics (
  id            INTEGER PRIMARY KEY,
  turn_id       TEXT NOT NULL,
  conversation_id TEXT NOT NULL,
  engineTEXT NOT NULL,          -- 'dialogue' | 'codex' | 'acp'
  model         TEXT,
  input_tokens  INTEGER,
  cache_hit_tokens  INTEGER,
  cache_miss_tokens INTEGER,
  output_tokens INTEGER,
  reasoning_tokens  INTEGER,
  first_token_msINTEGER,
  total_msINTEGER,
  history_count INTEGER,                -- 本轮实际送了几条历史
  recorded_at   INTEGER NOT NULL
);
```

`turn_id` 关联 orchestrator 的回合，`engine` 区分角色路径和执行路径。

### 前缀哈希

Reasonix 的 `PrefixShape` 思路值得抄。在 dialogue adapter 里，每轮组装完messages 之后，对前N 条（即稳定前缀部分，角色卡 +搭档+ 输出协议）的内容做一个简单哈希，存在 `turn_metrics` 里，和上一轮比对：

```python
import hashlib, json

def prefix_hash(messages: list[dict]) -> str:
    # 只取system 消息，剥掉所有本地元数据字段后序列化
    stable = [{"role": m["role"], "content": m["content"]}
              for m in messages if m["role"] == "system"]
    raw = json.dumps(stable, ensure_ascii=False, separators=(",", ":"))
    return hashlib.sha256(raw.encode()).hexdigest()[:16]
```

连续两轮哈希不同 → 记一次 miss原因（system 变了、工具变了、还是历史体量把前缀挤掉了）。调第三阶段的压缩逻辑时你会需要这个。

### 这一条的开发者视图

在 `desktop_backend/commands.py` 加一个 `debug.turn_metrics` 命令，返回最近N 轮的这些数字。不需要做成 UI，开发期在控制台查就够。**这是第二阶段整个计划的度量地基，第三阶段的窗口阈值要从这里读出来再定。**

## EP v1 审批拦截：需要一次spike，但目标和步骤是清楚的

### 现状的真实问题

先说清楚现在的裂缝在哪。你的审批链对两个引擎的代码路径是：

```
Codex：
  Python收到 requestApproval 事件
  → sandbox检查（Python侧，进程内断言）
  → ApprovalManager（三模式）
  → 向 codex 回复 decision

Reasonix（现状）：
  reasonix 自己判断"这个操作需要问"，然后发session/request_permission
  → Python 收到，sandbox 检查，ApprovalManager
  → 向 reasonix 回复 outcome.selected + optionId
```

区别不是"Python 有没有参与"——两条路Python 都参与了。区别是**谁决定问什么、什么时候问**：Codex 路是Python 先拿到工具参数、自己判断要不要问、然后自己问用户；Reasonix 路是 reasonix 先决定要问了，才通知 Python。结果是：

1. `risk_rules.yaml` 里的匹配逻辑只对 Codex 路的**结构化工具参数**生效，对 reasonix 路只能匹配已经被reasonix 格式化后的请求描述文本——不够准。
2. "帮我审核"模式下，低风险操作 reasonix 可能根本不发`request_permission`（因为它自己判断了），你的审查智能体没机会介入。
3. 完全允许模式下，Python 传`yolo` 给 reasonix，reasonix 自行处理——这其实绕开了 sandbox 的最后一道进程内校验。

EP v1 的目标是把 reasonix 路改成和 Codex 路一样：**Python 在工具被 reasonix 决定执行之前先拦下来，拿到结构化参数，走完整的sandbox → risk_rules → ApprovalManager链，再决定放不放行。**

### Spike 要验证的三件事

这三件任何一件不成立，EP v1 路线就要换方案，所以这三件要在动代码前全部确认：

**一：tool_call 拦截是阻塞的，不只是观察性的。**
EP v1 sidecar 拦截到 `tool_call` 事件后，能否让 reasonix 真正挂起等待 sidecar 的放行信号？还是说只是旁观一下、reasonix 照跑？文档说"拦截运行时事件"，但"拦截"在实现层面可以是两种意思。这个必须跑一个最小 demo 确认。

**二：sidecar 和 reasonix 的通信延迟能不能承受异步审批。**
EP v1 sidecar 是进程外的。异步审批的场景是：工具参数发过来 → sidecar hold 住 → Python ApprovalManager 发审批请求到前端 → 用户点允许 → 前端发命令到 Python → Python 通知 sidecar → sidecar 放行。这个链路可能是几秒到十几秒，reasonix 那边的 hold 有没有超时？超时行为是什么？

**三：sidecar 和 Python 之间用什么 IPC。**
最理想的是复用已有的 ACP JSONL 通道——sidecar 不单开新连接，而是 Python 把 EP v1 sidecar 作为 orchestrator 的一部分启动，通过 stdio 或 Unix socket 通信。如果 EP v1 要求 sidecar 是一个独立的 HTTP server或 WebSocket endpoint，Python 侧要新开一个监听，可以做但成本变高。

Spike 的最小实现：写一个能打印工具参数的 EP v1 sidecar，接入到你现有 reasonix 实例，跑一次文件读写操作，确认三点都通。两天以内应该能得到结论。

### Spike 通过后的实现形态

```
Python Orchestrator
  ├─启动 reasonix.exe acp（带 EP v1 sidecar 配置）
  └─ 启动 ep1_approval_sidecar（你写的，和 orchestrator 同生命周期）
                │
                │ EP v1 协议（reasonix ↔ sidecar）
                ↓
        工具拦截桥（sidecar 收到 tool_call 事件）
                │
                │ 内部调用（不走网络）
                ↓
        Python ApprovalManagersandbox → risk_rules → 三模式审批
                │
                ↓
        sidecar 回复 allow/deny → reasonix 继续/放弃
```

实现完成后：
- reasonix 的 `native_preexecution_approval` 改成 `False`
- `approval.py` 里 reasonix 路和 codex 路的区分逻辑删掉，合并成同一条
- `risk_rules.yaml` 的匹配可以从字符串模式匹配升级为结构化参数匹配（因为你现在拿到的是解析后的 `{tool: "bash", command: [...], cwd: "..."}` 而不是格式化后的描述文本）

Spike 失败（拦截不阻塞或者 IPC 不可行）的备用方案：在 ACP 适配器里把 reasonix 配成 `--approval-policy=ask` 强制所有工具都发 `request_permission`，然后在 Python 侧统一处理，至少让"谁都不问"的全自动路径被封掉。这条路 sandbox 的保底拦截仍然有效，只是结构化参数匹配拿不到。

### 审批统一后的额外收益

一旦两路审批走同一条链：

1. `risk_rules.yaml` 只需要维护一份，而且可以换成结构化匹配，减少误判和绕过。
2. "帮我审核"模式的审查智能体只需要一套调用逻辑，不需要区分引擎。
3. `approval.py` 的测试覆盖可以合并成一套，不用分codex 和 acp 两套路径的contract test。

Token 可见性不需要等spike，可以现在并行开。EP v1 的 spike 先跑，spike 结论出来后再动审批逻辑，不要在 spike 结果未知的情况下改`approval.py`。

## 结论

你补的这两个参数把优先级整个翻过来了：**在 V4 Flash 的定价结构下，你最大的成本和延迟来源是「最高档思考」，不是历史窗口。** 思考降档是改一个参数，上下文改造是两三周——顺序应该反过来。

而且 1M 上下文这一条也推翻了我上一轮的一个论据（我当时以为 DeepSeek 窗口偏小）。V4 Flash 是 100 万 token 上下文[^1]，容量根本不是约束。这反而让第三阶段的目标要重新定义。

## 一、把定价摊开算一遍

V4 Flash 当前每百万 token：**缓存命中输入 0.02 元、缓存未命中输入 1 元、输出 2 元**[^2]。注意这个比例——命中和未命中差 **50 倍**，而输出是命中输入的 **100 倍**。

关键点：**思考 token 按 output 计费，而 DeepSeek 明确要求 `reasoning_content` 不得回传下一轮。** 也就是说在你的整个成本结构里，思考是唯一一项**永远按最高单价计费、永远不进缓存、每轮从零重烧**的开销。前缀再长都能打到 0.02，思考一个 token 都省不下来。

用一组假设数字算给你看（前缀 2000 + 历史 3000 + 当前输入 100 = input 5000，台词 300 token。这些是我拍的，不是实测）：

| 场景                                    | input 成本 | output 成本 | 单轮合计      | output 占比 |
| --------------------------------------- | ---------- | ----------- | ------------- | ----------- |
| 现状：滑动窗口，命中率 30%，思考 1200   | 0.0035 元  | 0.003 元    | **0.0065 元** | 46%         |
| 只做上下文改造：命中率 90%，思考仍 1200 | 0.0006 元  | 0.003 元    | **0.0036 元** | **84%**     |
| 再加思考降档：命中率 90%，思考 200      | 0.0006 元  | 0.001 元    | **0.0016 元** | 63%         |

上下文改造把总成本降到 55%，思考降档再降到 44%。但两者的**代价完全不对等**：前者两三周工程加一张投影表，后者改一个请求参数。

而且 90% 以上的缓存命中率不是理论值——有实测案例一下午跑 740 万 token、命中率 98%、总花费 0.78 元[^3]，也有报道说 V4 Flash 的命中率常稳定在 90% 以上[^4]。你的目标基准线可以直接定在 90%。

## 二、思考降档怎么做

**延迟这一侧比成本更要命。** 角色扮演里用户能接受的等待是一两秒，1200 token 思考在 flash 上要几秒，而且首 token 延迟里几乎全是它。更糟的是这笔延迟买不到什么——角色扮演不是数学题，扮演质量靠的是角色卡和上下文，不是链式推理。

但不能一刀切关掉，因为你的角色单次调用同时承担两件事：出台词，和判断要不要委派、生成 `TaskSpec`。后者是真需要推理的。

建议**用 fallback 而不是预判**：默认低档或关闭思考；解析出 `delegation` 之后校验 `TaskSpec`（目标、验收标准、涉及文件是否完整），只在校验不过时用高档思考重试一次。这比事前猜「这轮是不是委派」准得多，而且绝大多数闲聊轮次直接走最便宜最快的路径。

如果后面 `delegate` tool call 那个改造做了，分档就更自然：台词生成和工具决策可以分开配置。

## 三、1M 上下文把第三阶段的目标改了

之前我说压缩阈值取绝对值、别抄 Reasonix 的 0.85 比例——结论对，但理由错了。真正的理由不是窗口容量（1M 根本装不满），而是**首字延迟和冷启动最坏情况**。

顺着定价再想一层：命中状态下多带 5000 token 历史的边际成本是 **0.0001 元**，几乎免费，预填充也快。所以在前缀稳定的前提下，**「让角色多记住」这件事在 DeepSeek 上接近零成本**。

这带来两个调整：

**逐字尾部可以做得比我之前说的大得多。** 之前给的 12–16k 太保守了，24–48k 都在合理区间。摘要压缩的紧迫性因此下降,滚动摘要从「必须做否则记忆断崖」降级为「优化项」。

**但跳步和摘要仍然要做，目的换了——控冷启动最坏情况。** 48k 尾部在缓存 miss 的那一轮是 0.048 元加上几秒预填充，是正常轮次的三十倍。你的产品是桌面应用，「开一会儿、关掉、几小时后再开」是常态，每次冷启动第一轮必然全 miss，这是物理规律不是 bug。所以摘要真正的作用是**压住冷启动那一轮的体量**，不是省稳态成本。

对应到度量：命中率一定要**按距上轮的时间间隔分桶**统计，否则平均值会被冷启动稀释到看不出改造效果。

---

## 四、三个我上一轮没考虑到的运营现实

**峰谷定价。** 高峰时段（工作日 9:00–12:00、14:00–18:00）价格是平时的 2 倍[^5]。这恰好是用编程搭档的主要时段。`turn_metrics` 表要加时段标记，否则你的成本统计会因为调用时间分布不同而无法横向比较。

**容量风险是真实的。** 8 月初 V4 Flash 因访问量出现 503 和响应超时，官方自己建议用户临时切换其他服务商[^6]。对你这个产品，表现就是角色说不出话。需要退避重试加上用户可见的「服务繁忙」状态——你已经做到的「用户消息先落库」在这里价值凸显，重试是安全的。

如果要做备用端点，注意一个陷阱：第三方部署的 V4 Flash 对**缓存命中请求的收费可达官方十倍**[^4]，而你正好是高命中率场景，failover 过去成本会跳得很厉害。所以备用端点应该是临时的、对用户可见的，不能静默常驻。

**即将涨价。** 8 月 6 日 DeepSeek 公告将整体上调 API 定价，「预计涨幅较大」，方案尚未公布[^7]。两个动作：把单价做成配置项而不是硬编码；`turn_metrics` 存**原始 usage 数字**而不只是算好的金额，这样涨价后能重算历史数据。同时别把架构决策建立在 0.02 这个极端优惠上——它是当前定价，不是长期假设。

---

## 五、`delegate` tool call 的风险下降了，但探测还是要做

V4 Flash 正式版原生支持 Responses API、Tool Calling、思考/非思考双模式[^1][^8]，V4 Pro 也同时支持 JSON Output 和 Tool Calls[^9]。所以「思考和工具调用能否并存」的官方答案是肯定的，比我上一轮估计的乐观。

但探测仍然要跑，因为有明确的反例：V4 Pro 的 FIM 补全**仅限非思考模式使用**[^9]。说明「某些能力与思考模式互斥」在这个模型家族里确实存在。花二十分钟用你实际配置的模型和推理档位发一次带 tool schema 的请求，确认思考通道和 tool call 能同时出来，再决定做不做 A/B。

顺带说，这个改造的收益论据在当前定价下特别强：JSON 包装的转义和字段脚手架吃的是 output token（2 元），换成 tool schema 之后这部分结构成本挪进可缓存的 input 前缀（0.02 元）——从最贵一档挪到最便宜一档，差 100 倍。

## 六、修正后的执行顺序

**立刻（改参数，当天可验）**：角色路径思考降档到低档或关闭，加 `TaskSpec` 校验失败时的高档重试。同时人工过一遍角色回复质量——这一步是有质量风险的，必须看效果，不能只看账单。

**第一批（一两天，零风险）**：`target == character` 过滤；`last_opened_at`；`_message()` 改成先写库后追加内存。这三项不变。

**第二批（约一周）**：`stream_options: {include_usage: true}` + usage 归一（记住 `hit + miss = prompt_tokens` 是互斥拆分）+ `reasoning_tokens` 单独记 + 前缀哈希 + 时段标记 + 原始 usage 留存。按闲置时长分桶看命中率。加「本轮实际发送的 prompt」开发者视图和 golden snapshot 测试。

**第三批（两到三周）**：阶梯式窗口 + 前缀冻结 + 序列化净化（reasoning 不得回流，这是正确性要求不是优化）+ 投影落库。尾部体量按实测延迟定，起步可以比之前激进。摘要的目标定为压住冷启动最坏情况。

**并行**：Reasonix EP v1 审批拦截 spike，两天出 go/no-go。这条和上面互不阻塞。

---

## 七、还需要你确认两件事

一是**思考降档之后角色回复质量掉多少**。这是唯一有产品风险的改动，也是整个方案里我完全无法替你判断的部分。建议同一组对话在最高档和关闭思考两种配置下各跑一遍，你自己读。如果质量掉得明显，那就退回「默认中档 + 委派时高档」。

二是**你现在单轮的 `reasoning_tokens` 实际是多少**。我上面所有算术都建立在「思考 1200 token」这个拍出来的数字上。第二批度量上线后第一个要看的就是这个数——它决定思考降档到底能省多少，也决定第三批的尾部体量该定多大。
