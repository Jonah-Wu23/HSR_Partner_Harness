## 1. 命令契约

命名微调已定稿：新增命令 `card.peek_import`（新规范名）、`card.import_png`、`card.export_png`、`power.get_status`。**`card.peek_import_json` 保留为 `card.peek_import` 的别名**（同一 handler、同一行为），既有前端路径不破坏，标记 deprecated。

### 1.1 `card.peek_import`（升级，含 PNG 分派）

- params：`{ "path": string }`
- 分派规则：先读文件前 8 字节与 PNG 签名 `\x89PNG\r\n\x1a\n` 比对（文件签名优先，不信任扩展名）；PNG 签名命中 → PNG 分支；否则按 UTF-8 文本 → JSON 分支。
- JSON 分支：行为与现状一致（`load_card_json`），preview 增补 `format: "json"`、`avatar_width: null`、`avatar_height: null`。
- PNG 分支：字节 → `read_png_card(data)`（ccv3 优先、chara 回退）；头像尺寸经 `png_image_dimensions(data) -> tuple[int, int] | None`（`png.py` 新增纯函数，解析 IHDR 宽高，解析失败如实返回 None 并入 warnings）。preview 字段：`format: "png"`、`avatar_available: true`、`avatar_width/height`（IHDR 值，None 表示未能解析）。
- preview payload 完整形状（两分支统一）：

```jsonc
{
  "preview": {
    "name": "string",
    "spec_version": "string（缺省 \"2.0\" 维持现状）",
    "format": "\"json\" | \"png\"",
    "avatar_available": "bool",
    "avatar_width": "int | null",
    "avatar_height": "int | null",
    "greeting_count": "int",
    "world_book_entries": "int",
    "tags": "string[]",
    "report": { "applied": [], "preserved": [], "not_executed": [], "normalized_from_root": [], "warnings": [], "errors": [] }
  }
}
```

- 错误：`OSError` / `PngCardError` / `CardImportError` 一律包装为 `ServiceError(code="card_import_failed")`，message 携带原始错误文本，不吞不改写。

### 1.2 `card.import_png`

- params：`{ "path": string, "as_duplicate"?: bool }`
- 流程（定稿顺序）：
  1. 读字节 → `read_png_card`（解析失败如实报错，同上）。
  2. `repository.import_card(card, as_duplicate=as_duplicate)` 生成 card_id（新 uuid、state="imported"、source="tavern_import"；`as_duplicate=True` 名称追加「（副本）」。名称冲突策略与 JSON 导入一致：**不查重、不自动改名**，仅 `as_duplicate` 改名）。
  3. `asset_service.store_asset(card_id=..., data=PNG 原始字节, kind="avatar", mime_type="image/png", source="png_import", source_ref=path.name)`——PNG 字节即头像，入受管理资产目录。
  4. `card.hsr.avatar_asset = AvatarAsset(asset_id, source="png_import", source_ref=path.name, mime_type="image/png", exported_in_png=True)`，经 `repository.update_card` 回写。
- result：`{ "card_id", "name", "state", "report" }`（与 `card.import_json` 同形）。
- 错误：解析失败 → `card_import_failed`；资产写入失败 → `card_import_failed` 携带 `CharacterAssetError` 原文（导入已落库时如实报告半程状态，不回滚不伪造成功）。

### 1.3 `card.export_png`

- params：`{ "card_id": string, "path": string }`
- 前置：卡存在且可写（内置卡 `card_read_only`）；**卡当前头像必须可取回**（`hsr.avatar_asset` 存在且 `get_asset` 成功）。无头像 → `ServiceError(code="card_export_failed")`，message「卡未设置头像，请先设置头像后再导出 PNG」，不合成默认图。
- 流程：`dump_card_v3(card)` → `write_png_card(card, avatar_bytes)`（只写 `ccv3` 块，图像块原始字节复制）→ 写入 path。
- result：

```jsonc
{
  "exported": true,
  "path": "string",
  "name": "string",
  "spec_version": "string",
  "greeting_count": "int",
  "world_book_entries": "int",
  "extensions": "string[]（sorted(card.extensions 键) ∪ {\"hsr\"（若 card.hsr 存在）}）"
}
```

- 错误：PNG 合成失败 / 写文件失败 → `card_export_failed` 携带原文。

### 1.4 `card.update`（决策：形状不变）

保持「整卡 v3 JSON 替换」契约：params `{ "card_id", "card": 完整 v3 JSON }`，校验 = `load_card_payload`。世界书条目增删改排序、mufy 高级块编辑**均通过整卡 JSON 承载**，不新增颗粒度子命令。视觉轨的世界书/高级编辑器按此契约产出完整卡 JSON。

### 1.5 `power.get_status`

- params：`{}`
- result（Windows 读取成功）：

```jsonc
{
  "supported": true,
  "platform": "windows",
  "plan_name": "string（getactivescheme 括号内名称；读不到名称时为空串且 warnings 记录）",
  "ac_sleep_timeout_seconds": "int",
  "dc_sleep_timeout_seconds": "int",
  "remote_serve_enabled": "bool（--serve 是否开启）",
  "threshold_seconds": 900,
  "at_risk": "bool",
  "reason": "string（确定性事实拼接，见 §8）",
  "checked_at": "ISO8601 本地时间"
}
```

- result（非 Windows）：`supported: false`、`platform: <sys.platform>`、`plan_name: ""`、两个超时字段 `null`、`at_risk: false`、`reason: "当前平台不支持电源状态检测"`。**如实返回 unsupported，不抛错、不伪造数值。**
- Windows 下 `powercfg` 调用失败或输出不可解析 → `ServiceError(code="power_status_unavailable")` 携带原始 stderr/解析上下文（Let It Fail，不猜数值）。

## 2. 事件契约

### 2.1 `power.status_changed`

- 扇出：普通 `emitter.emit`（需到达手机端，走 WS 扇出订阅，不用 remote_only 通道）。payload 与 `power.get_status` result 完全同形。
- 发射节奏（定稿）：仅 `--serve` 模式启动电源监视（`__main__.py` 内守护线程）：
  1. serve 启动后立即读取并 emit 一次；
  2. 此后每 **60 秒**轮询一次，仅当 `(supported, plan_name, ac, dc, remote_serve_enabled)` 元组变化时 emit；
  3. serve 停止时 emit 一次 `remote_serve_enabled=false` 的终态。
- 非 serve 模式不启动监视；桌面端可随时主动 `power.get_status`。
- 应用只提示与指引，**永不修改电源设置**（不调用 `powercfg /change` 等写操作）。

### 2.2 不新增的其他事件

装配诊断（世界书命中、预算占用、未展开宏）进入装配器输出模块列表与日志，不新增事件；诊断 UI 归 V0.3.9。

### 2.3 Android 本地通知不新增 Sidecar 协议

壳消费现有事件流（任务完成 = `message.finalized`/`turn.status_changed`、委派结果 = `message.finalized`（委派 target）、审批请求 = `approval.requested`），通知规则在壳内本地处理；通知只承载状态摘要，不是事件来源，点击进壳后按既有 `sequence` 对齐增量。

## 3. 世界书运行时激活契约（`character_cards/activation.py`）

纯函数模块，不依赖 Sidecar/SQLite。语义以 ST v1.18.0 为准，行号对照见 §3.9。

### 3.1 冻结的 API

```python
@dataclass(frozen=True)
class ActivatedEntry:
    entry: WorldBookEntry
    position: str            # "before_char" | "after_char" | "atDepth"
    depth: int | None        # 仅 atDepth
    role: str                # 仅 atDepth：system | user | assistant
    text: str                # 条目 content（宏展开前原文）
    matched_keys: list[str]
    tokens_estimate: int
    not_run_fields: list[str]

@dataclass(frozen=True)
class DepthEntryGroup:
    depth: int
    role: str
    entries: list[ActivatedEntry]   # 同 (depth, role) 分组，桶内拼接序

@dataclass(frozen=True)
class ActivationDiagnostics:
    scan_depth: int
    scanned_message_count: int
    budget_total: int
    budget_used: int
    overflow_entries: list[str]     # 被预算排除条目的 comment/entry_id
    not_run_fields: list[str]       # 存而不运行字段清单（entry 级聚合）
    warnings: list[str]             # 非法正则退化等
    activated_count: int

@dataclass(frozen=True)
class ActivationResult:
    before_char: list[ActivatedEntry]
    after_char: list[ActivatedEntry]
    depth_entries: list[DepthEntryGroup]
    diagnostics: ActivationDiagnostics

def token_estimate(text: str) -> int: ...
def activate_world_book(
    book: CharacterBook,
    scan_texts: Sequence[str],        # 时间正序的最近对话文本（user/character）
    *,
    context_tokens: int = 8192,
) -> ActivationResult: ...
```

### 3.2 扫描缓冲

- 输入 `scan_texts` 由调用方提供（见 §4.5：orchestrator 传最多 50 条 user/character 消息文本，时间正序，含开场白，不含助手/工具/思考/委派回显）。
- 生效扫描深度 `N = book.scan_depth ?? 2`（对齐 ST 全局默认 `world_info_depth = 2`，world-info.js:69）；取 `scan_texts` **最后 N 条**拼接为一个 haystack，连接符 `"\n"`（对齐 ST JOINER）。
- 条目级 `scanDepth`（extensions 内）不在核心子集，存而不运行并记录。

### 3.3 主关键字

- `entry.keys` 为空 → 跳过（ST :4793-4796）。
- 任一 key 命中即通过（ST :4802-4805 `find`）。
- 每个 key 的匹配方式（ST :337-366 `matchKeys`）：
  1. key 匹配 `/pattern/flags` 形态 → 编译为正则，flags 限 `gimsuy` 子集（ST :2821-2846 `parseRegexFromString`）；编译失败 → **退化为字面包含匹配并记 warning**（对齐 ST 回退）。
  2. 非 `/…/` 形态且 `entry.use_regex` 为 True → 将 key 本身作为正则编译，flags = 大小写敏感时 `""` 否则 `"i"`；失败退化字面 + warning。（注：ST 无 `use_regex` 概念——v2 卡字段的定义性扩展，见 §3.10 偏差表。）
  3. 否则字面包含匹配；`case_sensitive ?? False`（ST :268-271，全局默认 :77），两侧小写化后包含。

### 3.4 次关键字

- 启用条件：`entry.selective` 为真且 `secondary_keys` 非空（ST :4812-4816）。
- `selectiveLogic` 取值：`entry.extensions.get("selectiveLogic", 0)`（模型无类型化字段，权威位置在 extensions；缺省 0 = AND_ANY，对齐 ST :4827 与卡导入 :5527）。非 0-3 的值记 warning 并按 0 处理。
- 四逻辑布尔表（ST :4831-4866，主 key 已命中的前提下）：
  - AND_ANY(0)：任一次 key 命中 → 激活
  - NOT_ALL(1)：并非全部命中（存在未命中）→ 激活
  - NOT_ANY(2)：全部未命中 → 激活
  - AND_ALL(3)：全部命中 → 激活

### 3.5 常驻与禁用

- `enabled=False` → 跳过（ST :4689-4692）。`constant=True` → 无条件激活，不做关键字匹配（ST :4781-4785），且不受预算溢出排除（ST `ignoreBudget` 之外的豁免仅此一种，`ignoreBudget` 字段本身存而不运行）。

### 3.6 位置

- 支持值与映射：`"before_char"` / 0 → before_char；`"after_char"` / 1 → after_char；`"atDepth"` / 4 → atDepth（ST :855-864 枚举）。
- **其余位置（ANTop/ANBottom/EMTop/EMBottom/outlet，2/3/5/6/7 及对应字符串）存而不运行**：条目被排除（不注入），逐条目记入 not_run_fields，兼容报告列出。不静默挪位。
- atDepth 的 depth 与 role 权威取值：`depth = extensions.get("depth") ?? extras.get("depth") ?? 4`（ST DEFAULT_DEPTH=4，:96、:5118）；`role = extensions.get("role") ?? extras.get("role") ?? "system"`，数值映射 `0→system、1→user、2→assistant`（ST extension_prompt_roles）。非法 role 值记 warning 按 system。
- 同 `(depth, role)` 聚合为一组（ST :5116-5128 WIDepthEntries）。

### 3.7 顺序与拼接

- **激活优先序 = `insertion_order` 降序**（大者优先，ST :88 `sortFn = (a,b) => b.order - a.order`）；同级 tie 按 entry_id 升序（无 entry_id 按书内列表下标）。
- **桶内最终拼接序 = `insertion_order` 升序**（ST 降序排好后逐桶 `unshift` :5084-5119 的净效果：小 order 在前、大 order 靠后）。tie 同上。
- before_char / after_char 桶输出为有序条目列表；depth 桶按组输出。

### 3.8 书级预算

- `budget = book.token_budget`（卡声明即生效）；未声明时 `budget = round(0.25 × context_tokens)`，`context_tokens` 默认 **8192**（冻结常数；全局上下文预算归 V0.3.9，届时替换此常数）。即默认预算 **2048**。
- token 计数：`token_estimate(text) = CJK 字符数 + ceil(非 CJK 字符数 / 4)`（CJK 判定含中日韩统一表意文字及扩展 A 区、假名、谚文）。无真实 tokenizer，这是冻结的近似算法；误差边界：中文 ±30%、英文 ±20%（相对 cl100k 经验值），仅用于预算门控与诊断，验收时按诊断数据核对。
- 计费与溢出（对齐 ST :4940-4953）：按激活优先序（降序）逐条累计 `已激活文本 + "\n" + entry.content` 的 token 估算；当累计值 ≥ budget 时**该条目被整体排除**（不是内容部分截断，ST 行为即跳过），记入 `overflow_entries`；其后所有非 constant 条目一并排除（ST :4902-4907）。constant 条目不受预算排除。`diagnostics.budget_used` = 最终实际注入内容的 token 估算。

### 3.10 与 ST 的定义性偏差（兼容报告如实标注）

1. `use_regex`（v2 卡字段）：ST 无此概念；本契约规定 bare key 在 use_regex=True 时按正则编译。
2. token 计数：ST 用真实 tokenizer（tokenizers.js:443 `getTokenCountAsync`）；本契约用 §3.8 近似算法。
3. 预算基准：ST 预算基于真实 maxContext；本契约 V0.3.7 用冻结常数 8192。
4. 扫描源：ST 额外扫描 persona/作者注释等全局字段；本契约只扫描对话消息。
5. 递归/min-activations/概率/互斥/sticky 等扩展语义：存而不运行（见 §3.11），ST 行号 :4763-4791、:4909-4936、:4991-5007、:5173-5356。
6. `world_info_cache`：ST 缓存世界书文件数据（:882、:2041-2055）；本契约激活结果不做跨回合缓存（见 §4.6）。

## 4. 装配契约更新（`core/character_prompt_assembler.py` 与对话链路）

### 4.1 两段式装配（定稿）

- **基座装配**（静态，按 `(card_id, updated_at)` 缓存，维持现状机制）：标准字段 + HSR 五块分节文本 + 数据宏展开 + 装配诊断。世界书与 depth_prompt **不进基座**。
- **回合装配**（每次请求现算，不缓存）：基座 + 世界书激活结果 + 确定性触发 → 完整 `AssembledPrompt`。理由：激活结果依赖回合上下文，跨回合缓存会伪造命中（ST 每次提示构建重算，world-info.js:4632）。

### 4.2 冻结的装配 API

```python
@dataclass(frozen=True)
class DepthInjection:
    depth: int          # 距对话末尾第 N 条之前插入；0 = 追加到最后
    role: str           # system | user | assistant
    text: str

@dataclass(frozen=True)
class AssemblyModule:   # 扩展（现有字段不动）
    kind: str; source_field: str; title: str; content: str; char_count: int
    char_start: int | None = None   # 在 system_text 中的字符区间 [start, end)
    char_end: int | None = None
    diagnostics: dict | None = None # 世界书模块：matched_keys/tokens_estimate/position/insertion_order/not_run_fields

@dataclass(frozen=True)
class AssembledPrompt:  # 扩展（现有字段不动）
    system_text: str
    modules: list[AssemblyModule]
    first_mes: str
    depth_injections: list[DepthInjection] = ...
    diagnostics: dict = ...        # budget_total/budget_used/overflow_entries/unexpanded_macros/not_run_fields/warnings

def assemble_character_prompt(card) -> AssembledPrompt: ...            # 基座（向后兼容，depth_injections 恒空）
def assemble_turn_prompt(card, scan_texts, *, turn_index, context_tokens=8192) -> AssembledPrompt: ...  # 回合装配
```

### 4.3 system_text 模块顺序（定稿）

`你扮演 {name}。` 框架行 → `world_book.before`（激活条目，桶内拼接序）→ 角色设定 → 性格 → 场景 → `world_book.after` → 系统提示 → 历史后指令 → HSR 五块（world_architecture → character_architecture → narrative_rules → relationship_system → event_system）→ `hsr.event_trigger`（确定性触发命中内容，若非空）。

映射理由：ST 中 worldInfoBefore 先于角色定义区、worldInfoAfter 紧随其后（script.js 拼接顺序），对应「角色定义三件套」（description/personality/scenario）的前与后。

### 4.4 depth 注入 splice 语义（锁定测试）

- 注入对象：卡级 `depth_prompt`（`extensions.depth_prompt`，depth 缺省 4、role 缺省 system）＋ 全部 atDepth 世界书分组；同 `(depth, role)` 文本 `"\n"` 合并为一条 `DepthInjection`。
- splice（对齐 ST script.js :5569-5617 `doChatInject`）：注入发生在 `build_messages` 映射后的对话消息列表（user→user、character→assistant）上——**在「距末尾第 depth 条消息之前」插入** `{"role": role, "content": text}`；depth=0 表示追加到最后一条消息之后（ST 倒序数组 index 0 = 最新消息之前 = 时间序最末尾之后）；depth ≥ 消息数时 clamp 到列表最前。多条注入按 depth 降序依次执行（等价 ST 的 running offset）。
- role 语义：system/user/assistant 直接作为 OpenAI 消息 role。

### 4.5 链路接线（定稿）

- `DialogueRequest` 新增 `turn_index: int = 0`（本轮序号：该会话**含当前用户消息**的用户发起消息累计数；greeting 不计）。
- `character_prompt_resolver` 签名改为 `(conversation_id, recent_messages: tuple[Message, ...], turn_index: int) -> AssembledPrompt | None`；`openai_compatible._system_prompt` 从 request 取两者传入。
- orchestrator `process_character_turn`：`recent_roleplay_context(self._history[cid][:-1], limit=50)`（上限从 12 提到 50，供 `scan_depth > 12` 的书使用；激活引擎内部再取最后 N 条）；`turn_index` = history 中 `source==USER 且 origin==USER` 的消息数（不含当前条，+1 后传入）。
- `build_messages` 在映射 recent_messages 之后、追加 progress/result/runtime 上下文之前应用 `depth_injections`（§4.4 splice）。**助手侧消息构建路径完全不改动**；`assert_single_assistant_markdown` 守卫不动。
- 卡删除/未绑定：resolver 返回 None，回退内置角色（现状不变）。

### 4.6 装配诊断字段（进模块列表与日志，不进 UI）

每条世界书模块 `diagnostics`：`{matched_keys, tokens_estimate, position, insertion_order, entry_ref}`；装配级 `diagnostics`：`{scan_depth, scanned_message_count, budget_total, budget_used, overflow_entries, not_run_fields, unexpanded_macros, warnings, activated_count}`。

### 4.7 HSR 高级块分节渲染（L8 定稿）

`_block_lines` 保留为嵌套层渲染规则；顶层 dict 的每个键升级为 `### {键名}` 小节行，后接该键值的既有渲染（键序不变、不翻译、不删除任何键，只排版不改写原文）。顶层 list 与标量沿用现状。

### 4.8 问候与 creator_notes 边界（定稿）

- `first_mes`：会话创建插入开场白时经数据宏展开（见 §5.3）；装配器 `first_mes` 输出同样展开。
- `alternate_greetings` / `group_only_greetings`：**存储与导出保真，运行时无随机/轮换**。经 `card.get` 完整透出给前端，开场白选择（若视觉轨提供）属会话创建参数，本阶段不加新命令。
- `creator_notes`：作者面向的元数据，**永不进入任何提示词**，仅存储与透出。

### 5.1 冻结 API

### 5.2 白名单（定稿）

| 宏 | 展开为 |

- 导入时扫描：`codec` 导入对全卡文本字段扫 `{{…}}` token，非白名单宏写入 CompatReport `not_executed`（形如 `macro:{{setvar::x::1}} @ data.personality（未展开）`，同宏多处合并计数）。

## 6. mufy 确定性触发契约（L9 定稿）

### 6.1 声明格式（机器可读，作者显式声明）

HSR `event_system`（递归整个子树）中，任意 dict 若含**保留字段** `runtime_trigger` 且其值为

```jsonc
{ "kind": "turn", "turn": 12, "once": true }
```

则该条目为确定性触发声明：`turn` 为 1 起算的正整数回合；`once` 缺省 true。命中回合时，该条目作为 `hsr.event_trigger` 模块注入角色提示词（位置见 §4.3 末位）。

- 条目内容取值：dict 含字符串字段 `content` → 取 content；否则将整个 dict（剔除 `runtime_trigger`）按 `_block_lines` 渲染。内容经数据宏展开。
- 非 `turn` kind（如 `{"kind": "time", ...}`）：**V0.3.7 存而不运行**（墙钟触发需要持久化已触发状态，本阶段不引入；游戏内「第 7 天」类时间本属角色模型语义），如实进兼容报告 not_executed。计划 L9 允许「冻结定案」，此为定案结果与理由。
- **散文触发不解析**：mufy 模板中 `time: "第7天"`、`trigger_after: "3天"`、`condition: "…"` 等自由文本字段，代码一律不做正则/关键词解析（Let It Go 禁止文字意图猜测）；这类条目保持全文可用——其所在结构照常进入 HSR `event_system` 模块渲染，角色模型自行按内容执行。
- 回合定义：`turn_index` 同 §4.5（用户发起消息累计数，1 起算，含当前回合）。`once=true` 仅在 `turn_index == turn` 那一回合注入；`once=false` 在 `turn_index >= turn` 的每回合注入。

### 6.2 与世界书的关系

触发条目不占用世界书预算、不参与关键字激活；两套机制独立。

## 8. 电源契约（`desktop_backend/power.py` 新模块）

- 读取实现：`subprocess` 调 `powercfg`，两步：
  1. `powercfg /getactivescheme` → 行内 GUID 正则 `([0-9a-fA-F-]{36})` 与括号内名称（缺失则 plan_name=""，warnings 记录）。
  2. `powercfg /query SCHEME_CURRENT SUB_SLEEP STANDBYIDLE`（GUID 238c9fa8… / 29f6c1db-86da-48c5-9fdb-f2b67b1f44da）→ 解析输出中的十六进制电源设置索引行，**按出现次序取最后两个 `0x…` token 依次为 AC、DC**（真实输出为 8 位十六进制如 `0x00000708`；16 位严格正则为主分支保留，可变宽度兜底为次分支，两分支均有测试锁定）。值为 0 表示「从不」。
  3. 解析失败（找不到索引行、powercfg 非零退出、超时 10s）→ 抛 `PowerStatusError`（携带 stderr/输出摘要），命令层转 `power_status_unavailable`。**不猜数值、不降级伪造。**
- 输出解码（2026-09-02 实测定案）：本地化 Windows 的 powercfg 输出为 ANSI/GBK 编码，而运行环境常被 `PYTHONUTF8=1` 强制 UTF-8——`text=True` 会按 UTF-8 解 GBK 静默得到空输出。定案：捕获**字节**输出，按「首选编码 → gbk」链解码并归一 `\r\n`；解码失败按原始失败如实报错。
- `at_risk` 判定（确定性数据推导，非语义猜测）：`supported && remote_serve_enabled && 任一 t ∈ {ac, dc} 满足 t != 0 且 t < 900`。
- `reason` 生成规则（事实拼接）：触发时「AC 睡眠超时 {t} 秒低于阈值 900 秒」（DC 同理，命中几条列几条）；未启用远程服务 → 「远程服务未开启」；正常 → 「AC/DC 睡眠超时均不低于阈值」；不支持 → 「当前平台不支持电源状态检测」。
- 阈值 **900 秒**、轮询 **60 秒**、事件节奏 **§2.1**——三者冻结。
- 非 Windows（`sys.platform != "win32"`）：返回 unsupported 形状（§1.5），不调用 powercfg。
