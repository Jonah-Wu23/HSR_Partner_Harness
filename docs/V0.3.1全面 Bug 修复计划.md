# HSR Partner Harness 全面 Bug 修复计划

## 1. 文档状态

- 文档用途：把四份静态扫描和补充交叉检查整理为可直接实施的修复顺序、代码边界与验收标准。
- 当前阶段：仅制定计划，暂不修改产品代码。
- 调查原则：采用现有扫描结论，只抽查会改变实施方案的少量代码。没有重新开展全仓审计。
- 代码基线：以实施开始时的工作树为准。当前工作树有大量未提交改动，后续每个阶段只能暂存本阶段明确列出的文件，禁止使用 `git add -A`。

## 2. 总体结论

本轮修复分为三条主线。

第一条主线处理永久卡死：后台任务异常、编排器全局 active 残留、审批请求失联、Sidecar 请求无限等待、Codex 回合没有终态。

第二条主线收拢状态权威和协议：账号与供应商切换必须原子完成；Python Sidecar 继续掌握业务状态；Rust 负责进程代次和连接生命周期；React 只投影当前代次内有序事件。

第三条主线清理用户直接可见的问题：草稿丢失、首次引导误跳步、推理等级保存无效、聊天模式仍能提交助手任务、语音提交落入错误会话。

修复顺序固定为：

1. P0 卡死与任务状态。
2. P0 跨层传输和重连。
3. P1 账号、配置与运行时生命周期。
4. P1 审批、持久化和会话归属。
5. P1 前端交互一致性。
6. P2 适配器边界和低风险清理。

## 3. 本轮保持不变的边界

- 保留 Tauri 2、React、Python Sidecar、stdio JSONL 和 SQLite。
- Python 层继续作为业务状态权威。Rust 不接管会话、Turn、审批或队列业务。
- 编程引擎继续保持单任务串行。本轮不会开放多个 Codex 或 Reasonix 回合并行执行。
- 角色输出和意图仍由模型负责。代码只处理协议、状态和审批结果，不增加关键词词典、正则意图判断或台词改写。
- 不重构整套编排器，不更换状态库，不引入新的服务进程。
- 不扩充 benchmark、遥测、审计日志和通用恢复框架。
- Shell 边界只使用引擎原生策略和审批能力。本轮不写命令关键词拦截器。
- 开发迭代按仓库现行节奏更新直接 EXE。NSIS 只在用户指定的安装包版本节点生成。

## 4. 已统一的争议点

### 4.1 账号切换

当前代码先调用 `_set_current_account()`，随后才重建运行时。运行时重建一旦失败，持久化账号已经改变，内存里的项目、会话和模型仍可能属于旧账号。切换成功后又只调用 `_restore_current_conversation()`，没有完整复用 `_select_conversation_context()` 的项目、搭档和语音上下文切换。

计划采用候选运行时方案：先读取目标账号配置并构建候选运行时，确认可用后再一次性交换账号、项目、会话和运行时引用。失败时保留原账号的完整状态。

### 4.2 跨会话队列和角色聊天

继续保持一个编程引擎任务在运行。角色对话按会话串行，可以在编程任务运行期间继续回复。角色在此期间形成的新委派写入持久化队列，保留 `delegation_id` 和 `origin`，等全局编程引擎空闲后派发。

所有编程任务完成后由统一派发器检查可运行队列，不能只唤醒当前会话。这样同时解决跨会话队列滞留和共享 transport 并发消费风险。

### 4.3 Sidecar 重启后的事件序号

序号仍可在 Python 进程重启后从零开始，但必须和连接代次一起判断。

- Rust 每次拉起 Sidecar 都创建新的 `stream_id`，并通过环境变量传给 Python。
- Python 的事件与快照同时携带 `stream_id` 和代次内 `sequence`。
- React 按 `(stream_id, sequence)` 去重和查缺。新 `stream_id` 会重置旧序号并触发 bootstrap。
- Rust 的 `connection.status` 属于连接控制事件，先于业务序号过滤处理，并携带对应 `stream_id`。
- 旧 reader 线程只能关闭自己的代次，不能把新进程重新标成 disconnected。
- bootstrap 期间暂存同一代次的新事件；快照水合后，只重放序号大于快照序号的事件。

这个方案不把事件序号写入 SQLite，也不会让 JavaScript 长期累积一个跨进程的超大整数。

### 4.4 前端协议里没有生产者的事件

当前生产链使用 `turn.started`、`turn.status_changed` 和 `connection.status`。扫描确认 Python 没有发出 `turn.completed`、`config.changed`、`connection.restored`。

实施时先再次搜索事件生产者。确认仍无生产者后，从 TypeScript 联合类型和相关死分支中删除这三个名字，并补一条协议契约测试。不会为了迁就声明而新增重复事件。

### 4.5 ACP / Reasonix Shell 边界

当前 `ProjectSandbox.enforce_cwd(None)` 不能限制命令中的绝对路径，这是已知边界。实施阶段先确认当前 ACP 能否原生传入工作目录和 sandbox/approval policy。

- ACP 支持时，直接传入项目根和原生策略。
- ACP 不支持时，Reasonix 的 Shell 操作进入现有审批链；`full_auto` 下也不能宣称已获得 workspace-write 隔离。
- 文档保留能力差异，界面不展示虚假的沙箱状态。

## 5. 里程碑 M1：解除永久卡死

### M1.1 原子化 `chat.submit`

涉及文件：

- `src/pair_harness/desktop_backend/application_service.py`
- `tests/unit/test_concurrent_entries.py`
- `tests/unit/test_desktop_router.py`

实施内容：

1. 为每个会话维护一个 `asyncio.Lock`。锁覆盖“检查忙碌、持久化用户消息、登记 Turn、创建并登记后台任务”这段临界区。
2. 同一会话已有未完成任务时，第二条提交只能进入队列，不能再创建新的回合链。
3. `_track_turn_task()` 发现同一会话已有未完成任务时直接抛出状态错误，禁止覆盖旧任务引用。
4. `_on_done()` 必须读取 `completed.exception()`。取消任务单独处理，真实异常写入 stderr 日志，并触发最终状态核对。
5. 正常异常处理留在 `_run_submit_chain()` 和 `_run_submit_turn()` 内。done callback 只承担最后一道异常观测，不能把失败改成成功。

验收：

- Router 并发送入两条同会话 `chat.submit`，只能有一条 Turn 进入 running。
- 第二条消息可见且处于 queued，不丢文字，也不覆盖第一条任务跟踪。
- 角色目标和助手目标分别覆盖。

### M1.2 所有回合出口都落入终态

涉及文件：

- `src/pair_harness/desktop_backend/application_service.py`
- `src/pair_harness/core/orchestrator.py`
- `src/pair_harness/core/engine_state.py`

实施内容：

1. 给 `_run_submit_chain()` 增加最外层 `try/except/finally`，确保派发前异常也能把 Turn 和消息推进到 failed 或 cancelled。
2. `_dispatch_from_inbox()` 记录当前 queue item。只有 Turn completed 才删除；异常和取消统一在 `finally` 中把仍为 processing 的项目退回 queued。
3. 将 `_execute_once()` 中 `state.start()`、执行起始回调、角色委派起始消息写入纳入同一个受保护生命周期。
4. 用局部 `state_started` 标记决定是否调用 `state.finish()`。凡是成功 start 的任务，任何后续异常都必须清除 active、`_active_lifecycle` 和 `_progress`。
5. `bind_engine_turn()` 遇到已经结束的本地任务时，不复活 ActiveTurn。迟到的引擎 turn id 记录为迟到协议事件并请求取消。
6. `cancel_active_task()` 先取消本地任务句柄。引擎 turn id 尚未绑定时记录取消意图，绑定后立即发送 interrupt。

验收：

- 分别在 `state.start` 之后、委派消息写库时、`open_session` 前和引擎事件循环中注入异常，下一次 bootstrap 都不再返回 busy。
- 任何异常都有 failed Turn、失败消息或明确的系统状态，原始异常进入日志。
- 取消派发中的队列项后，数据库状态回到 queued。

### M1.3 Codex 回合终态和旧异常隔离

涉及文件：

- `src/pair_harness/adapters/codex/engine.py`
- `src/pair_harness/adapters/codex/transport.py`
- `src/pair_harness/desktop_backend/engine_factory.py`

实施内容：

1. `run_turn()` 使用可配置的空闲超时。每收到一条属于当前 turn 的通知就重置计时；默认连续 10 分钟没有任何事件即判定 transport 无响应。
2. 超时后先请求 `turn/interrupt`，再产生带原始原因的 `TURN_FAILED`。interrupt 失败也写入错误详情。
3. `TransportClosed`、EOF、读循环异常转换为失败终态，错误类型和原文保留在 payload 和 stderr。
4. transport 重连时创建新的通知队列和连接代次。旧 reader 的异常只能结束旧队列，不能进入新队列。
5. 连接重建后把 `_initialized` 复位，下一次调用重新执行 initialize。

验收：

- app-server 存活但不发事件时，测试用短超时能结束 Turn，不会无限等待。
- app-server 中途退出时，UI 收到 failed，消息、Turn、任务回执三者一致。
- 重连后的第一条通知来自新连接，旧异常不会毒化新回合。

### M1.4 ACP 取消和共享 transport

涉及文件：

- `src/pair_harness/adapters/acp/engine.py`
- `src/pair_harness/desktop_backend/engine_factory.py`

实施内容：

1. 每轮创建的 `notification_task` 都在 `finally` 中 cancel 并 await。
2. `_ensure_initialized()` 增加异步锁，并绑定 transport 代次。断线重建后必须重新 initialize。
3. 编程任务继续由全局派发器串行执行，ACP drain 窗口内不会出现第二个回合消费者。
4. Codec 能提供 session/turn 标识时继续核对归属。发现不匹配事件时记录协议错误，不能把它投影到当前会话。

验收：

- 连续取消 20 次 ACP 回合后没有 pending task 警告。
- 两个会话各有队列项时，运行期始终只有一个 transport 消费者。

### M1.5 审批请求不能失联

涉及文件：

- `desktop/src/ui/approval/ApprovalBar.tsx`
- `desktop/src/stores/desktopStore.ts`
- `src/pair_harness/core/approval.py`
- `src/pair_harness/core/orchestrator.py`
- `src/pair_harness/adapters/codex/codec.py`
- `src/pair_harness/adapters/codex/engine.py`
- `src/pair_harness/adapters/acp/engine.py`

实施内容：

1. 删除组件内长期保存的 `resolvedIds`。审批条完全依据 store 中的 pending 和 resolving 状态渲染。
2. 点击裁决后只进入 resolving 并禁用按钮。请求成功且收到 `approval.resolved` 后移除；请求失败时恢复按钮并显示错误。
3. Codec 收到缺失或非数字的原生 `approval_id` 时立即产生可见协议失败，禁止到 `int()` 转换时才崩溃。
4. Turn 取消时遍历该 Turn 的未决审批，向引擎发送 deny/cancel 结果，完成本地 future 并发出 resolved/cancelled 事件。
5. `ApprovalManager.gate()` 的回调异常和取消路径都清理 `_pending`。

验收：

- 模拟 `approval.resolve` 请求失败后，同一审批仍能再次点击。
- 在审批条停留时取消 Turn，前端不再保留 pending，app-server 侧请求也结束。
- 缺失 approval id 时 Turn 明确失败，Sidecar 保持可用。

### M1.6 Rust 请求超时和阻塞写入

涉及文件：

- `desktop/src-tauri/src/main.rs`

实施内容：

1. `desktop_request` 等待响应的默认上限设为 30 秒。超时后按原请求 id 删除 pending，并返回 `backend_timeout`。
2. pending 表保存请求 id，EOF 失败回包必须带回各自 id。
3. stdin 的 `write_all/flush` 移入专用阻塞任务或单写入线程。Tokio worker 不再持有 `std::sync::Mutex` 执行阻塞 I/O。
4. 写失败时删除对应 pending，并立即发布 disconnected。

验收：

- Sidecar 接收请求后不回包，30 秒后 Promise 必须 reject，pending 表为空。
- 并发发起多个桌面请求时，连接状态和其他异步命令仍能响应。

## 6. 里程碑 M2：重连、进程和 stdout 协议

### M2.1 引入连接代次

涉及文件：

- `desktop/src-tauri/src/main.rs`
- `src/pair_harness/desktop_backend/events.py`
- `src/pair_harness/desktop_backend/application_service.py`
- `src/pair_harness/desktop_backend/__main__.py`
- `desktop/src/contracts/protocol.ts`
- `desktop/src/stores/desktopStore.ts`
- `desktop/src/app/AppController.tsx`
- 对应 Python、Rust、Vitest 协议测试

实施内容按 4.3 节执行。补充要求：

1. Rust 只接受当前 `stream_id` reader 产生的 EOF 和事件。
2. `connection.status` 在前端进入业务事件批处理前处理。
3. 新代次到达后立即标记 `needsBootstrap`，并暂存这段时间的业务事件。
4. 快照水合时核对 `stream_id`。旧代次快照不能覆盖新代次状态。
5. 同代次序号重复直接丢弃；序号出现缺口时触发 bootstrap，并保留缺口后的事件等待快照核对。

验收：

- Sidecar 序号从 100 重启到 0 后，新代次的 `message.delta`、`approval.requested` 和 `voice.state_changed` 都能保留。
- 旧 reader 迟到的 disconnected 不会覆盖新连接的 connected。
- 同一代次重复事件只应用一次。

### M2.2 stdout 只有一个写入器

涉及文件：

- `src/pair_harness/desktop_backend/__main__.py`
- `src/pair_harness/desktop_backend/router.py`

实施内容：

1. `__main__` 创建唯一 `JsonlWriter`，事件 emitter 和 Router 复用同一个实例。
2. `run_stdin()` 接收 writer，不能根据 stdout 再创建第二个锁。
3. `BrokenPipeError` 视为传输已经关闭。writer 原子标记 closed，通知主循环执行 Sidecar 关闭流程，并把错误写入 stderr。
4. stdout 断开不能反向把已经成功落库的业务消息改成 failed。传输失败和任务失败分别记账。

验收：

- 多线程同时发事件和响应，逐行 JSON 均能解析。
- 桌面端关闭 stdout 后，Sidecar 有序退出；已落库消息状态保持原值。

### M2.3 区分致命配置错误和可恢复崩溃

涉及文件：

- `src/pair_harness/desktop_backend/__main__.py`
- `desktop/src-tauri/src/main.rs`
- `desktop/src/stores/desktopStore.ts`

实施内容：

1. 为启动配置错误保留明确的 fatal 退出分类，例如退出码 2，并在 `error.reported` 中携带 `fatal: true`。
2. Rust 收到 fatal 后停止自动重启，把原始错误送到启动失败页。
3. EOF、意外异常和一次性子进程崩溃继续使用有上限的退避重连。
4. 手动重连先把当前连接状态置为 false，再启动新代次，不能读取旧 watch 值提前返回成功。

验收：

- 错误配置只启动一次，界面直接显示 fatal 原因。
- 临时崩溃仍能自动恢复。
- 手动重连只有在新进程发出 ready 后才返回成功。

### M2.4 有界关闭 Sidecar 和子进程

涉及文件：

- `desktop/src-tauri/src/main.rs`
- `src/pair_harness/adapters/codex/transport.py`
- `src/pair_harness/desktop_backend/application_service.py`

实施内容：

1. Rust 发出 `app.shutdown` 后等待 Python 有限时间退出。超时后再强制结束。
2. Python shutdown 依次取消业务任务、结清审批、关闭语音和模型运行时。
3. transport 的 `process.wait()` 增加超时；普通 terminate 无效时再进入强制结束。
4. Windows `.cmd/.bat` 启动链必须覆盖真实子进程，防止只结束 cmd shim 后留下 app-server。

验收：

- 正常退出不留下 codex、reasonix 或 Sidecar 子进程。
- 子进程拒绝退出时，关闭流程在限定时间内结束并记录真实错误。

2. `command.current_dir()` 和 `--project` 不再复用同一个 root。

## 7. 里程碑 M3：账号、配置和运行时生命周期

### M3.1 原子账号切换

涉及文件：

- `src/pair_harness/desktop_backend/application_service.py`
- `src/pair_harness/desktop_backend/engine_factory.py`
- 账号切换单元与集成测试

实施步骤：

1. 获取账号切换锁，禁止切换过程与 `chat.submit`、配置保存并发。
2. 取消当前任务并等待其进入终态。取消失败要中止切换并显示原因。
3. 只读加载目标账号配置，构建候选 dialogue、reviewer 和 coding engine。
4. 读取目标账号项目和会话，准备 pair config、审批模式、助手提示词和语音上下文。
5. 候选全部成功后，才更新 `current_account_id`、项目和会话，并交换运行时引用。
6. 调用与 `_select_conversation_context()` 相同的完整上下文选择逻辑。
7. 发出 account.changed 和新账号快照，随后异步关闭旧运行时。
8. 任一步失败都关闭候选运行时，原账号和原上下文保持不变。

验收：

- 目标账号配置损坏时，重启前后仍停留在原账号。
- 成功切换后，账号、项目根、pair、审批模式、last_mode、角色提示词和语音音色全部属于目标账号。

### M3.2 运行时替换和 session 失效

实施内容：

1. 将 `_rebuild_runtime_for_account()` 改为可等待的候选构建与替换流程。
2. 新旧引擎类型、供应商、项目根任一发生变化时，使受影响会话的 `EngineSessionRef` 失效。
3. 旧 dialogue model、reviewer、HTTP client、Codex transport 和 Reasonix transport 都调用各自的 `aclose()`。
4. transport 与 session 带运行时代次。旧运行时迟到事件不能进入新会话。
5. 项目根修改后禁止用旧 cwd 恢复线程；下一次任务新建 session。

验收：

- Codex 切到 DeepSeek 后，下一次任务新开 ACP session。
- 连续保存配置 20 次，外部子进程和 HTTP client 数量不持续增长。
- 修改项目根后，真实任务只在新目录执行。

### M3.3 配置保存先验证后提交

涉及文件：

- `src/pair_harness/desktop_backend/application_service.py`
- `src/pair_harness/storage/sqlite_store.py`

## 10. 里程碑 M6：适配器和低优先级清理

### M6.1 对话适配语义

- DeepSeek 空正文重试继续传递 `_delegation_retry`。
- CodexDialogueModel 使用公开的共享解析入口，覆盖空正文、截断 JSON 和委派纠偏。
- Codex 对话流取消时调用 engine cancel，并清理对应 `_sessions`。
- Codex `turn/completed status=cancelled` 映射为 cancelled，不能映射为 failed。
- 原生引擎已经完成工具执行但没有助手文本时，按明确协议决定终态。若协议要求最终文本，保留失败；若引擎允许工具型完成，则生成 completed 回执并把“无文本”作为真实结果，不能伪造助手回复。

### M6.2 音频运行时

- Qwen TTS 关闭线程使用有界等待并记录未退出线程，避免快速跳过时持续累积。
- DashScope 的全局 api_key/base URL 修改放入现有进程级锁。当前仍按单账号活动运行时设计。
- 删除 Silero VAD 没有消费者的 pre-roll 状态前，先用 `rg` 再确认调用方；确认无调用后做纯删除。

### M6.3 性能和边界项

- `incremental_json.py` 的 O(n²) 解析列为性能优化，只有实际长输出基准证明它影响体验时才改。
- `tauriDesktopBackend.ts` 的 `Number.isFinite(sequence)` 在 `stream_id` 协议落地时一起调整。代次内序号保持在 JavaScript 安全整数范围。
- Tauri CSP 单独建立后续任务。当前本地文本渲染没有已观察到的注入链，本轮不让它阻塞卡死修复。
- `tauri-with-first-run-reset.ps1` 的大小写敏感子串匹配在下一次安装包验证前调整，本轮只保证现行首次运行清理流程继续执行。
- `.env` 自动切真实后端和 CLI 简化解析属于开发体验问题，放在 P2。修复时要求存在明确的 `PAIR_HARNESS_REAL` 或有效供应商配置，不能只凭空 `.env` 文件切换。

## 14. 完成标准

本计划完成需要同时满足以下条件：

- 任意 Turn 成功、失败或取消后都能进入终态，Sidecar 不会永久 busy。
- 审批和队列没有永久 processing/pending 项。
- Sidecar 重启不会丢失新代次的真实事件，也不会被旧 reader 反向改写连接状态。
- 账号或配置切换失败时，旧账号运行时保持完整可用。
- 运行时替换和应用关闭后没有持续累积的外部子进程、HTTP client 或 asyncio task。
- 草稿、引导步骤、推理等级和 Composer target 与后端真实状态一致。
- Python、前端和 Rust 全量测试通过；相关真实 provider smoke 通过。
- 开发 EXE 完成首次运行清理后的打包验证。安装包仍按既定发布节点处理。
