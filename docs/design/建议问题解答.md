# 《建议.md》与《建议2.md》问题解答

日期：2026-08-13  
范围：以当前工作区代码和 Pi 当前官方文档为准。本文件回答问题，不代表这些改动已经实现。

## 一、结论

当前架构可以继续使用。Python 编排器、SQLite 状态库、审批链和桌面协议已经构成项目自己的 Harness，整体迁移到 Pi 没有必要。Pi 适合放在 `CodingEngine` 端口后面，作为新的编程引擎候选。

两份建议中最需要处理的是角色上下文策略：

1. `recent_roleplay_context()` 确实漏掉了 `target` 条件。用户直接发给助手的消息会进入角色历史，这是实际 bug。
2. 固定保留 12 条消息会造成长度波动和记忆断层，应改为带硬上限的 token 预算，并按完整对话轮裁剪。
3. 当前没有滚动摘要和跨聊天角色记忆。长对话及多个聊天之间都会遗忘。
4. 重启后选择的是最近有消息的聊天，不一定是最后打开的聊天。
5. 项目没有记录角色请求的 token、缓存命中和首字延迟。建议文件中的成本降幅暂时无法验证。

建议先修上下文污染和重启选中项，再补度量。窗口策略和摘要等到拿到真实 token 分布后实施。Pi 保持为独立实验，不与角色记忆改造绑在一起。

## 二、当前架构是否需要迁移到 Pi

### 2.1 当前 Harness 已经掌握在项目自己手里

《建议.md》后半部分对当前项目的修正判断基本成立。项目自己的核心资产包括：

- `src/pair_harness/core/orchestrator.py`：角色回复、委派、任务执行和结果回流。
- `src/pair_harness/core/approval.py` 与 `sandbox.py`：审批和项目目录边界。
- `src/pair_harness/storage/sqlite_store.py`：项目、聊天、消息、工具记录和引擎会话。
- `src/pair_harness/core/ports.py`：角色模型与编程引擎的适配端口。
- Sidecar JSONL 协议、事件序号和前端水合链路。

Pi 若替代 Python 编排器，会重复实现现有业务。当前合适的接入点是 `CodingEngine`，角色对话适配器可以保持原状。

### 2.2 Pi 能否满足 `CodingEngine` 的六项能力

| `CodingEngine` 能力 | Pi 当前官方能力 | 结论 |
| --- | --- | --- |
| `open_session` | RPC 提供 session id、session file、`switch_session`，CLI 也支持 `--session` | 可以映射。`EngineSessionRef` 保存 Pi session file 或 id |
| `run_turn` | `prompt` 接收任务，事件流提供文本、思考、工具调用和终态 | 可以映射 |
| `cancel_turn` | RPC 提供 `abort` | 可以映射；正在执行的自定义工具仍需响应取消信号 |
| `amend_turn` | RPC 提供 `steer` | 可以映射。它会等当前 assistant turn 的工具调用结束，再在下一次模型调用前注入，不会强行中断当前工具 |
| `resolve_approval` | 扩展的 `tool_call` 事件可以阻止工具，RPC 模式支持扩展 UI 子协议 | 可以实现，但需要 Pi 扩展或自定义 host 配合，单写事件 codec 不够 |
| `native_preexecution_approval` | Pi 核心没有固定权限弹窗，官方建议用扩展自行实现 | 接入初期应按 `False` 处理，审批语义由 HSR 的 Python 侧掌握 |

Pi RPC 使用严格的 LF 分隔 JSONL，和当前子进程协议相近。流式事件包含 `thinking_delta`、`text_delta`、工具开始和工具结束，也带 provider 上报的 usage。DeepSeek 已有内置 API key 与兼容层支持。

### 2.3 Phase 0 八项问题的当前答案

| 问题 | 当前答案 |
| --- | --- |
| 运行中 steer | 官方支持，注入点在当前工具调用完成之后 |
| 工具执行前等待审批 | 扩展可以在 `tool_call` 阶段阻止；与 Python 异步审批的桥接仍需 spike |
| 会话恢复 | 官方支持 session file/id 和 `switch_session` |
| 独立思考事件 | 官方支持 `thinking_start/delta/end` |
| 取消 | 官方支持 `abort`；工具自身需要响应取消信号 |
| stdio JSONL | 官方支持，且规定只用 LF 分帧 |
| Windows 单文件分发 | 官方没有承诺。自建薄 host 可以尝试 Bun 或 Node SEA，必须实际打包验证 |
| DeepSeek | 当前 `pi-ai` 支持 DeepSeek 和 OpenAI 兼容端点 |

原建议把 steer、思考通道和 DeepSeek 都列为未知项。按当前官方实现，这三项已经有明确答案。真正的 go/no-go 项剩下两个：Python 审批能否在 stock RPC + 扩展模式下保持现有语义，以及 Windows 安装包能否稳定携带 Pi 运行时。

本机当前找不到 `pi` 命令，全局 npm 包中也没有 Pi。因此这次只能确认官方接口和本地接入边界，尚未运行 Phase 0 spike，也没有 Pi 在 Windows 上的真实打包结果。

### 2.4 推荐接入路线

当前不建议直接投入三至四周编写 `pi-host`。先做一个边界明确的第三引擎实验：

1. 用 Pi RPC 加一个最小 `PiCodingEngine`。
2. 只验证委派、steer、取消、审批和重启恢复。
3. 使用同一组任务记录 input token、cache read、首字延迟、总耗时和工具轮数。
4. 数据确认 Pi 有明确收益后，再决定是否自建薄 host。

Python Sidecar 整体改写成 TypeScript 没有收益，继续搁置。Codex 建议保留，它已经接入现有端口，也能承担复杂工程任务。Pi 有实测优势时，可以调整默认引擎，无需删除 Codex。

建议文件询问的“迁移动机”和“典型任务 token 量级”无法从代码推断。当前没有这组运行数据，因此不能给出可信的节省比例。角色适配器是可配置的 OpenAI 兼容端点，并对 DeepSeek 做了专门处理；实际主要服务商取决于账号配置，不能仅凭源码确认。

## 三、《建议2.md》提出的问题

### 3.1 `target` 过滤：确认是 bug

`Message` 已经用 `target=character|assistant` 区分发送对象，见 `src/pair_harness/core/contracts.py:72-81`。但 `src/pair_harness/core/context.py:8-15` 只检查 `source`：

```python
if message.source in (MessageSource.USER, MessageSource.CHARACTER)
```

用户直接发给助手的消息仍是 `source=user`，因此会进入下一次角色请求。助手回复的 `source=assistant` 会被排除，角色看到的是一条没有对应回答的用户消息。

建议改为：

- 角色消息继续保留。
- 用户消息只保留 `target=character`。
- 兼容旧数据库中 `target=None` 的历史用户消息，迁移完成前可把它们视为角色消息。

这项应排在第一位，且需要补一个回归测试：先向助手发送任务，再向角色说话，角色请求的 `recent_messages` 中不能出现助手任务。

### 3.2 固定 12 条：问题成立

`recent_roleplay_context(..., limit=12)` 按消息条数裁剪。角色台词长度差异很大，12 条无法约束 token，也不能充分利用短消息留下的空间。

推荐规则：

1. 设定角色历史的硬 token 预算，并为当前输入、角色卡及输出预留空间。
2. 从最新消息向前选择完整的用户与角色往返。
3. 目标是至少保留若干完整轮，但模型上下文硬上限始终优先。
4. 设置最大轮数，避免大量短消息无限扩张。
5. 相邻同角色消息在组装 prompt 时合并，不修改数据库原文。

建议2提出“至少六轮，哪怕超预算”。这里需要保留模型上下文的硬限制。最低轮数可以作为目标，不能越过请求上限，否则会直接造成调用失败。

### 3.3 Prefix cache：有问题，但原判断说得过头

当前消息顺序见 `src/pair_harness/adapters/dialogue/openai_compatible.py:123-154`：

```text
稳定 system（角色卡 + 搭档简介 + 输出协议）
近期历史
任务进度 / 任务结果
运行上下文
当前用户消息
```

因此：

- 角色卡处于最前面，且内容稳定，可以命中公共前缀缓存。
- 历史窗口未满 12 条时，旧消息保持不变、新消息向后追加，缓存条件也比较好。
- 窗口满后每轮滑动一条，公共前缀通常会在第一条历史处断开，历史部分的缓存命中会明显下降。
- 时间精确到秒，但运行上下文位于历史之后。它不会让角色卡缓存归零，只会使运行上下文之后的内容无法复用。

所以“缓存基本完全没吃到”缺少依据。准确结论是：稳定角色卡能够复用，满窗口后的历史复用较差，实际比例未知。

阶梯式窗口可以改善连续轮次的前缀稳定性，但应和 token 预算、完整轮次及滚动摘要一起设计。单独改成每六轮跳一次，会让窗口在跳步时突然遗忘一大块内容。

### 3.4 时间精度与角色卡文件缓存

运行上下文由 `src/pair_harness/core/orchestrator.py:194-209` 生成，时间格式精确到秒：

```python
local_time=now.strftime("%Y-%m-%d %H:%M:%S")
```

角色对话一般不需要秒级时间。改成日期与时段，或者只在确实涉及时间的问题中注入，会减少无意义变化。

角色卡每轮会从文件读取。一次 `stream_reply()` 只组装一次消息，不存在同一轮前后多次读取角色卡造成内容不一致的问题。两个小型 Markdown 文件的 IO 也不是当前主要瓶颈。按 mtime 缓存可以做，优先级低于上下文污染、记忆摘要和度量。

### 3.5 第 13 条之前的记忆消失：确认存在

SQLite 保存完整聊天，但角色请求只取最近 12 条合格消息。旧内容仍可在界面查看，模型下一轮看不到它们。目前没有滚动摘要、故事状态或记忆检索。

推荐新增会话级结构化摘要，至少包含：

- 已确认的用户事实和偏好。
- 当前场景及角色状态。
- 关系变化和关键事件。
- 未兑现的承诺与待继续话题。
- 新增的世界设定。

摘要应记录覆盖到哪个 `message_id`，只在窗口需要前移时更新。原始消息继续保留，摘要用于 prompt 组装。第一版不需要向量数据库。

### 3.6 委派结果是否完全没有进入角色记忆

这个问题只成立一部分。

`CharacterResultSummary` 本身是临时 system 消息，不写入消息表，见 `src/pair_harness/core/orchestrator.py:1081-1104`。角色依据它生成的结果台词会通过 `_message()` 写入数据库，见同文件 `1110-1124`。因此角色短期内能看到自己刚才的结果汇报。

缺少的是结构化工作结论。角色台词可能省略文件、检查结果和限制，而且这条台词最终也会被 12 条窗口淘汰。

推荐把回执结论纳入会话摘要的输入，保存一条简短结构化工作记录。它不必再显示成重复气泡，可以由上下文构建器作为“共同完成的工作”注入。

### 3.7 跨聊天角色记忆：确认没有

每个 conversation 有独立消息和独立 `_history`。同一项目或同一 pair 的其他聊天不会注入当前角色请求。

会话级摘要稳定后，可以再增加 `(account_id, pair_id)` 级角色记忆本。建议满足以下条件：

- 数量有上限，只保存长期有用的事实。
- 用户能查看、修改和删除。
- 每条记忆记录来源聊天和更新时间。
- 注入时放在角色卡之后，当前聊天摘要之前。

跨聊天记忆应晚于当前聊天摘要实施。向量检索暂不需要。

### 3.8 重启选中的聊天：确认有问题

`SQLiteStore.list_conversations()` 按 `updated_at DESC` 排序。消息落库会更新 `updated_at`，单纯选择聊天不会更新它。启动时 `application_service.py` 取列表第一项，因此最后打开但没有发送消息的聊天不会成为下次启动项。

推荐在 `app_state` 按账号保存 `last_active_conversation_id`。启动时确认它属于当前账号且未归档，然后恢复；无效时再回退到最近活跃聊天。`updated_at` 继续表示聊天活跃度，无需改动含义。

### 3.9 `_history` 与数据库双份状态：风险存在

`_message()` 当前先把消息追加到 `_history`，再写数据库。数据库写入失败时，内存会比持久层多一条消息。当前写入口比较集中，风险尚未扩散到多个业务模块，但建议指出的分叉路径确实存在。

暂时不需要移除 `_history`。它还承担流式编排、并发回合和本轮结果收集。较小的修正是：

1. 先完成数据库写入，再追加内存历史。
2. 写入失败时让本轮明确失败，不继续调用模型。
3. 增加回归测试，核对每轮结束后的数据库消息 id 与 `_history` 一致。

直接每轮同步查询 SQLite 也能工作，但会扩大本次改动面，当前收益有限。

## 四、《建议.md》提出的性能问题

### 4.1 Delta 穿透三层：判断成立

`EventEmitter.emit()` 每收到一次增量就立即调用 sink，见 `src/pair_harness/desktop_backend/events.py:34-53`。前端 `desktop/src/services/eventBatcher.ts` 用 40 ms 窗口批量刷新 React，但 Python 到 Rust、Rust 到 WebView 的序列化已经发生。

可以在 Sidecar 出口合并同一 `message_id + channel` 的连续 delta，再分配事件序号并发送。该优化需要保留终态事件立即发送，且不能打乱不同消息之间的先后顺序。实施前先记录每轮 delta 数量和 IPC 时间，否则无法判断收益。

### 4.2 角色输出 JSON 包装：现状确认，是否改 tool call 需要实验

DeepSeek 请求会设置 `response_format={"type":"json_object"}`，所有角色提示词也要求返回单个 JSON 对象。当前 `IncrementalJsonSpeechParser` 会从流式 JSON 中提取 `speech`，见 `openai_compatible.py:341-425`。

它确实会增加 JSON 字段和转义成本。让角色直接输出台词，再通过 `delegate` tool call 形成委派，有机会简化协议。但这会改变角色模型的输出契约，也要求每个对话供应商稳定支持工具调用与自然语言并存。

建议保留当前实现，先做一组 A/B：

- 普通聊天的首个可见字符延迟。
- 含引号、换行时的 output token。
- 委派识别成功率。
- 错误台词和错误委派率。

数据确认 tool call 方案更好后再替换。

### 4.3 编程引擎是否每次冷启动

编排器会按 conversation 缓存 `_sessions`，每次执行把已有引用传给 `open_session()`，并把返回引用写入 `engine_sessions`。重启后也会恢复同类型引擎的 session，见 `orchestrator.py:752-766`。

`JsonlProcessTransport` 同样复用已经启动的子进程连接。因此“每次任务都冷启动”并不符合当前实现。仍可以记录首次打开和恢复 session 的耗时，确认各引擎适配器没有在内部重复初始化。

### 4.4 标题生成与审批批处理

标题生成确实会在首次完整回复后额外调用一次模型。它不阻塞主角色回复，优先级低于上下文问题。可以立即显示本地临时标题，再异步替换，但属于体验改进。

批量审批会改变现有逐工具裁决语义。只有实测表明连续同类审批经常出现，再设计批量范围和撤销方式。

## 五、建议实施顺序

### 第一阶段：修正确定问题

1. 给角色上下文增加 `target` 过滤和回归测试。
2. 用 `app_state` 保存每个账号最后打开的聊天。
3. 调整 `_message()` 的数据库与内存写入顺序，并补一致性测试。

### 第二阶段：拿到真实数据

在 dialogue adapter 记录开发诊断数据：input token、output token、cached token、首字延迟、总耗时、历史条数和估算 token。开发者视图可以展示本轮组装后的消息结构，API key 和思考原文不进入该视图。

同时建立角色 prompt 快照测试，覆盖普通聊天、助手直发后的角色聊天、协作委派和任务结果回流。

### 第三阶段：改上下文策略

根据真实分布设定 token 预算，按完整轮次选取历史，并采用阶梯式窗口。随后加入会话级结构化滚动摘要，把委派回执结论也纳入摘要。

### 第四阶段：可选增强

- 增加用户可编辑的跨聊天角色记忆本。
- 试验角色 `delegate` tool call 协议。
- 测试 Sidecar delta 合并。
- 启动 Pi 第三引擎 spike。
